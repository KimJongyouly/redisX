# Redis 최근 개발 동향 (unstable 브랜치) 소스 분석

> 분석 기준: `unstable` 브랜치 (HEAD ≈ 2026-04-13, PR #14987 이후)

---

## 1. 개요

Redis unstable 브랜치에는 Redis 8.x → 9.x를 향한 대형 신기능 6개와 다수의
성능 개선이 동시 진행 중이다. 신규 `.c/.h` 파일이 대거 추가되었고(cluster_asm.c
3809 lines, ebuckets.c 2725 lines, keymeta.c 940 lines 등) 기존 t_hash.c, t_stream.c
도 수천 줄 확장되었다.

## 2. 신기능 상세 분석

### 2.1 GCRA 레이트 리미터 (`src/gcra.c`, 241 lines)

**무엇인가?**  
GCRA(Generic Cell Rate Algorithm) – 누수 버킷(leaky bucket) 계열이지만 버킷을
주기적으로 드레인하는 대신 *Theoretical Arrival Time(TaT)* 을 계산해 허용 여부를
결정한다.

**새 커맨드**
```
GCRA key max_burst tokens_per_period period [TOKENS count]
```

| 파라미터 | 설명 |
|---|---|
| `max_burst` | 순간 허용 토큰 수 (버스트) |
| `tokens_per_period` | period 동안 허용 토큰 수 (지속률) |
| `period` | 초 단위 기간 (double) |
| `TOKENS count` | 이 요청의 비용 (기본값 1) |

**응답 (5-element array)**
```
1) 0/1  - 제한 여부 (0=허용, 1=차단)
2) N    - max_burst 값
3) N    - 즉시 가능한 잔여 토큰
4) N    - 재시도 가능한 초 (-1=영구 차단)
5) N    - 전체 버스트 리셋까지 초
```

**구현 핵심 (gcra.c:129–224)**
```c
long long emission_interval_us = (long long)(period_us / tokens_per_period + 0.5);
long long variance_us = emission_interval_us * max_burst;   // 버킷 용량
long long allow_at    = new_tat_us - variance_us;           // 이 시점 이후면 허용
```
- TaT 값을 **STRING 키**에 저장 (μs 단위 정수), 자동 PXAT expire
- 복제 시 `SET key tat PXAT when` 으로 rewrite하여 타이밍 차이 제거

### 2.2 키 메타데이터 프레임워크 (`src/keymeta.c/h`, 940 lines)

**무엇인가?**  
kvobj(키 객체)에 최대 **8개의 메타데이터 슬롯**을 붙이는 확장 프레임워크.
기존 expire 메커니즘을 class 0으로 흡수하고, class 1–7을 모듈에 개방한다.

**메타데이터 클래스 체계 (`keymeta.h:49–58`)**
```c
#define KEY_META_ID_EXPIRE       0   // 예약: 만료 시각 (기존 TTL)
#define KEY_META_ID_MODULE_FIRST 1   // 모듈 등록 시작
#define KEY_META_ID_MODULE_LAST  7   // 모듈 등록 끝
#define KEY_META_ID_MAX          8   // 슬롯 총 수
```

각 클래스마다 `KeyMetaClassConf` 구조체로 콜백을 등록:
```c
typedef struct KeyMetaClassConf {
    uint64_t flags;          // KEY_META_FLAGS_RDB_MASK(3bits) 등
    uint64_t reset_value;    // 메타 없음 시 sentinel 값
    int  (*copy)(...)  ;     // COPY 커맨드 시
    int  (*rename)(...);     // RENAME 커맨드 시
    int  (*move)(...);       // MOVE 커맨드 시
    void (*unlink)(...);     // DEL/논리 삭제 시
    void (*free)(...);       // 실제 메모리 해제 시
    int  (*rdb_load)(...);   // RDB 로드 콜백
    void (*rdb_save)(...);   // RDB 저장 콜백
    void (*aof_rewrite)(...);// AOF 재기록 콜백
    ...
} KeyMetaClassConf;
```

**저장 레이아웃**: kvobj 앞에 붙는 8-byte prefix blocks (metabits 비트맵으로 활성 슬롯 추적)  
**모듈 API**: `keyMetaClassCreate()`, `keyMetaSetMetadata()`, `keyMetaGetMetadata()`, `keyMetaRemoveMetadata()`

### 2.3 해시 필드 만료 (HFE, Hash Field Expiry)

**관련 파일**: `src/t_hash.c`, `src/ebuckets.c/h`, `src/estore.c/h`

#### 2.3.1 새 커맨드
| 커맨드 | 설명 |
|---|---|
| `HSETEX key [FNX\|FXX] [EX s\|PX ms\|EXAT ts\|PXAT ms-ts\|PERSIST] FIELDS n f1 v1 …` | 필드 단위 만료와 함께 설정 |
| `HGETEX key [EX s\|…\|PERSIST] FIELDS n f1 …` | 필드 조회 + 만료 갱신 |
| `HEXPIRE key s FIELDS n f1 …` | 필드 TTL 설정 (초) |
| `HPEXPIRE / HEXPIREAT / HPEXPIREAT` | 밀리초·절대 시각 변형 |
| `HTTL / HPTTL` | 필드 TTL 조회 |
| `HPERSIST` | 필드 만료 제거 |

**FXX/FNX 플래그**: 필드 존재 여부에 따른 조건부 세트 (t_hash.c:2387)

#### 2.3.2 ebuckets – 만료 버킷 (`src/ebuckets.c`, 2725 lines)

```
ebuckets
└── rax-tree (key = 6-byte 만료 시각)
    └── bucket (시간 구간)
        └── segment (최대 EB_SEG_MAX_ITEMS개 아이템, 단방향 순환 링크드리스트)
            └── item (ExpireMeta 임베드)
```

- segment 가득 찰 때 **split** (만료 시각 중간값으로 분할)  
- 모든 아이템 TTL이 동일하면 **extend** (extended-segment 체인)  
- rax 키 6바이트 = 충분한 만료 시각 표현 (수천 년)

#### 2.3.3 estore – 만료 스토어 (`src/estore.c`, 496 lines)

- ebuckets 배열 + **Fenwick Tree(fwtree)** 로 구성
- 클러스터 모드: 슬롯별 독립 ebuckets 버킷
- Fenwick tree로 O(log N) 버킷 탐색 → activeExpireCycle에서 최소 TTL 해시 효율 탐색

#### 2.3.4 Fenwick Tree (`src/fwtree.c/h`, 237 lines)

```c
fenwickTree *fwTreeCreate(int sizeBits);          // size = 2^sizeBits
void         fwTreeUpdate(ft, idx, delta);         // O(log n)
unsigned long long fwTreePrefixSum(ft, idx);       // O(log n) 누적 합
int          fwTreeFindIndex(ft, target);          // N번째 아이템 위치
int          fwTreeFindFirstNonEmpty(ft);          // 최초 비어있지 않은 버킷
```
- 1-based 내부 인덱싱, public API는 0-based
- KVSTORE(딕셔너리 슬롯별 키 수)와 ESTORE(만료 버킷별 아이템 수) 모두 활용

### 2.4 Atomic Slot Migration (ASM) (`src/cluster_asm.c/h`, 3809 lines)

**무엇인가?**  
기존 MIGRATE 기반 슬롯 이동의 한계(긴 블로킹, 부분 실패 위험)를 해소하는
**원자적 슬롯 마이그레이션** 프레임워크.

**새 커맨드**
```
CLUSTER MIGRATION ...    // 마이그레이션 태스크 관리
CLUSTER SYNCSLOTS ...    // 슬롯 동기화
SFLUSH slots …           // 특정 슬롯만 선택적 flush
```

**핵심 API (cluster_asm.h)**
```c
void asmInit(void);
void asmBeforeSleep(void);             // 이벤트 루프 매 사이클
void asmCron(void);                    // 주기적 유지보수
void asmSlotSnapshotAndStreamStart();  // 슬롯 스냅샷 + 스트림 시작
void asmSlotSnapshotSucceed/Failed();  // 스냅샷 결과 처리
int  asmMigrateInProgress(void);
int  asmImportInProgress(void);
```

**Trim 방식 3가지**
```c
#define ASM_TRIM_METHOD_NONE    0   // 즉시 삭제 없음
#define ASM_TRIM_METHOD_BG      1   // 백그라운드 trim
#define ASM_TRIM_METHOD_ACTIVE  2   // 활성 trim (블로킹 방지)
```

**안전 보장**: `isSlotInAsmTask(slot)` / `isSlotInTrimJob(slot)` → 마이그레이션 중인 슬롯 커맨드 라우팅 제어  
**복제 지원**: `asmReplicaHandleMasterTask()` → 레플리카도 동일 작업 추적

### 2.5 스트림 멱등성 (IDMP, Idempotency) (`src/t_stream.c`)

**무엇인가?**  
네트워크 재전송 등으로 인한 XADD 중복을 서버 측에서 방지하는 멱등성 레이어.

**XADD 새 파라미터**
```
XADD key ... PIDX producer-id [IIDX iid] ...
```
- `PIDX` (Producer ID): 특정 프로듀서 식별 문자열
- `IIDX` (Idempotent ID): 요청 고유 ID

**내부 구조 (t_stream.c:765)**
```c
robj *idmp_pid;  // XADD 파싱 시 추출한 프로듀서 ID
robj *idmp_iid;  // 멱등 ID
```

스트림 내부:
```c
stream {
    rax *idmp_producers;        // 프로듀서별 rax 트리
    long long idmp_duration;    // IDMP 유효 기간 (초)
    long long idmp_max_entries; // 프로듀서당 최대 추적 항목
}
```

**서버 설정**
```c
server.stream_idmp_duration;   // 기본 IDMP 유효 기간
server.stream_idmp_maxsize;    // 기본 최대 엔트리 수
```

RDB/AOF 지원: `XIDMPRECORD` 커맨드로 IDMP 상태 복원

### 2.6 XNACK 커맨드 (`src/t_stream.c:3858`)

**무엇인가?**  
컨슈머 그룹에서 처리 실패한 메시지를 PEL(Pending Entry List)로 반납하는 커맨드.

**문법**
```
XNACK key group <SILENT|FAIL|FATAL> IDS numids id [id ...]
```

**3가지 모드 (t_stream.c:802–820)**
```c
#define XNACK_SILENT 0  // delivery_count -= 1 (전달 취소)
#define XNACK_FAIL   1  // delivery_count 변경 없음 (실패 기록)
#define XNACK_FATAL  2  // delivery_count = LLONG_MAX (영구 실패)
```

XNACK 처리 후 즉시 다시 claim 가능한 상태가 된다.

### 2.7 HOTKEYS 추적 (`src/hotkeys.c`)

**무엇인가?**  
실시간 인기 키(Hot Key)를 Top-K 알고리즘으로 추적하는 기능.

**새 커맨드**
```
HOTKEYS START [COUNT n] [DURATION ms] [SAMPLE ratio] [SLOTS ...]
HOTKEYS STOP
HOTKEYS GET
HOTKEYS RESET
HOTKEYS HELP
```

**CHK (Count-Heavy-Keeper) 알고리즘 (`src/chk.h`)**
```c
#define CHK_LUT_SIZE              256  // 사전 계산 LUT
#define CHK_HEAVY_ENTRIES_PER_BUCKET 2
#define CHK_NUM_TABLES            2    // Cuckoo 테이블 수
```
- `chkTopKCreate(count * 10, nearestNextPowerOf2(count * 100), 1.08)`
- k × 10개 후보 추적 → 정확도 향상
- decay 기반 카운트 감쇠 (LUT로 O(1) 조회)

**추적 메트릭 2가지**
```c
#define HOTKEYS_TRACK_CPU   // rusage 기반 CPU 점유
#define HOTKEYS_TRACK_NET   // 네트워크 바이트 기반
```

슬롯 범위 필터링 지원 (`slotRangeArray *slots`)
