# Redis 성능 특성 (Performance Characteristics) 소스 분석

## 개요

Redis 성능 특성은 크게 세 영역으로 나뉜다.

| 영역 | 내용 |
|------|------|
| **모니터링 도구** | Latency Monitor, HDR Histogram, Slow Log, Duration Stats |
| **튜닝 파라미터** | Hz, Active Expire, Rehash, 인코딩 임계값, 메모리 축출 |
| **네트워킹 최적화** | IO 스레드, 파이프라인, 버퍼 크기 |

## 1. 레이턴시 모니터링 (`src/latency.h`, `src/latency.c`)

### 1.1 이벤트 기반 레이턴시 샘플링

```c
// 측정 매크로 (server.latency_monitor_threshold 비활성화 시 no-op)
latencyStartMonitor(var)           // var = mstime()
latencyEndMonitor(var)             // var = mstime() - var
latencyAddSampleIfNeeded(event, var)  // var >= threshold 이면 기록
```

**설정**: `latency-monitor-threshold` (기본값 0 = 비활성화, ms 단위)

### 1.2 자료구조

```c
struct latencySample {
    int32_t  time;    // 샘플 수집 시각 (Unix timestamp, 4바이트)
    uint32_t latency; // ms 단위 레이턴시
};

struct latencyTimeSeries {
    int idx;          // 다음 기록 위치 (링 버퍼 인덱스)
    uint32_t max;     // 이 이벤트의 최대 레이턴시
    struct latencySample samples[LATENCY_TS_LEN]; // LATENCY_TS_LEN=160
};

struct latencyStats {
    uint32_t all_time_high; // 최초 리셋 이후 절대 최대값
    uint32_t avg;           // 현재 샘플 평균
    uint32_t min, max;
    uint32_t mad;           // 평균 절대 편차 (Mean Absolute Deviation)
    uint32_t samples;       // 비 零 샘플 수
    time_t   period;        // 첫 이벤트 이후 경과 시간(초)
};
```

**링 버퍼**: 이벤트별 최근 160개 샘플 유지. 새 샘플이 오면 가장 오래된 것을 덮어씀.

### 1.3 측정 이벤트 목록 (주요)

| 이벤트 이름 | 측정 대상 |
|------------|----------|
| `command` | 커맨드 실행 시간 (slowlog 연동) |
| `aof-write` | AOF 버퍼 write() 시간 |
| `aof-write-pending-fsync` | fsync 대기 중 write |
| `aof-write-active-child` | child 프로세스 존재 중 write |
| `aof-fsync-always` | AOF_FSYNC_ALWAYS 모드 fsync |
| `fork` | fork() 시스템 콜 |
| `module-acquire-GIL` | 모듈 GIL 획득 |
| `while-blocked-cron` | 블로킹 중 cron 실행 |

### 1.4 이벤트 루프 Duration 통계 (4종)

```c
typedef enum {
    EL_DURATION_TYPE_EL   = 0,  // 전체 이벤트루프 사이클
    EL_DURATION_TYPE_CMD  = 1,  // 커맨드 실행 누적
    EL_DURATION_TYPE_AOF  = 2,  // AOF flush 누적
    EL_DURATION_TYPE_CRON = 3,  // serverCron+beforeSleep 누적
} DurationType;
```

`INFO latencystats`로 조회 가능.

## 3. Slow Log (`src/slowlog.h`, `src/slowlog.c`)

```c
typedef struct slowlogEntry {
    robj **argv;
    int argc;
    long long id;        // 고유 ID (단조 증가)
    long long duration;  // 마이크로초 단위 실행 시간
    time_t time;         // 실행 Unix timestamp
    sds cname;           // 클라이언트 이름
    sds peerid;          // 클라이언트 네트워크 주소
} slowlogEntry;

#define SLOWLOG_ENTRY_MAX_ARGC   32   // 저장하는 최대 인자 수
#define SLOWLOG_ENTRY_MAX_STRING 128  // 인자당 최대 저장 바이트
```

**설정 파라미터**:

| 파라미터 | 기본값 | 의미 |
|----------|--------|------|
| `slowlog-log-slower-than` | 10000 (μs) | 이 시간 초과 커맨드만 기록 (-1: 비활성, 0: 모두 기록) |

**주의**: Slow Log의 `duration`은 **커맨드 실행 시간만** 포함 (I/O 대기 시간 제외). 클라이언트가 느려서 응답을 못 받는 것과 무관.

## 4. serverCron Hz 조정

### 4.1 기본 Hz

```c
#define CONFIG_DEFAULT_HZ  10    // 초당 10회 (100ms 간격)
#define CONFIG_MIN_HZ       1
#define CONFIG_MAX_HZ     500
```

**`run_with_period(_ms_)` 매크로**:
```c
#define run_with_period(_ms_) \
    if (((_ms_) <= 1000/server.hz) || \
        !(server.cronloops % ((_ms_)/(1000/server.hz))))
```
Hz=10 기준: `run_with_period(100)` = 매 호출, `run_with_period(1000)` = 1초마다.

### 4.2 Dynamic Hz (자동 조정)

```c
// server.c:1519
if (server.dynamic_hz) {
    while (listLength(server.clients) / server.hz >
           MAX_CLIENTS_PER_CLOCK_TICK)  // = 200
    {
        server.hz *= 2;
        if (server.hz > CONFIG_MAX_HZ) { server.hz = CONFIG_MAX_HZ; break; }
    }
}
```

**동작**: 클라이언트 수가 많아지면 Hz를 자동으로 높임. `clients/hz > 200`이면 Hz 2배. 최대 500Hz.

**이유**: 클라이언트 많을 때 타임아웃 처리가 지연되지 않도록 cron 주기를 높임.

## 5. 능동 만료(Active Expire) 성능 특성

### 5.1 상수 (`src/expire.c:96`)

```c
#define ACTIVE_EXPIRE_CYCLE_KEYS_PER_LOOP     20  // DB당 샘플링 키 수
#define ACTIVE_EXPIRE_CYCLE_FAST_DURATION   1000  // μs (1ms)
#define ACTIVE_EXPIRE_CYCLE_SLOW_TIME_PERC    25  // CPU 최대 사용률
#define ACTIVE_EXPIRE_CYCLE_ACCEPTABLE_STALE  10  // 허용 만료 키 비율(%)
```

### 5.2 타임리밋 계산

```
# SLOW 모드
timelimit = 25% × 1,000,000μs / server.hz / 100
           = 250,000 / server.hz μs
# hz=10 → 25,000μs (25ms)
# hz=100 → 2,500μs (2.5ms)

# FAST 모드
max = ACTIVE_EXPIRE_CYCLE_FAST_DURATION (1ms 기본)
```

### 5.3 `active-expire-effort` (1~10, 기본 1)

effort가 높을수록 더 공격적으로 만료:
- `config_cycle_fast_duration = 1000 + 1000/4 × effort` μs
- `config_cycle_slow_time_perc = 25 + effort` %
- `config_cycle_acceptable_stale = 10 - effort` %

**트레이드오프**: effort↑ → 만료 빠름, CPU 사용↑, 레이턴시 스파이크↑

### 5.4 루프 종료 조건

```
각 DB에서 20개 키 샘플링 → 만료된 것 삭제
만료율 < ACCEPTABLE_STALE(10%) → 다음 DB로
시간 초과 → 루프 중단
```

## 6. 점진적 리해시 성능

```c
#define INCREMENTAL_REHASHING_THRESHOLD_US  1000  // 1ms (beforeSleep당)
#define CRON_DBS_PER_CALL                     16  // serverCron당 처리 DB 수
#define CRON_DICTS_PER_DB                     16  // DB당 처리 dict 수
```

**`beforeSleep()`에서 리해시**: 각 호출 시 1ms 이내에서 버킷 이동. I/O 대기 중 유휴 시간 활용.

**커맨드 실행 중**: 커맨드마다 리해시 1버킷 수행 (`dictRehash(d, 1)`).

**리해시 완료 확인**: 커맨드 실행 시 `ht[0].used == 0` 이면 리해시 완료.

## 7. 적응형 인코딩 임계값 (기본값)

데이터 구조가 임계값을 초과하면 메모리 효율적인 인코딩에서 성능 최적화된 인코딩으로 자동 업그레이드.

| 자료구조 | 인코딩 | 임계값 파라미터 | 기본값 |
|---------|--------|---------------|--------|
| **Hash** | LISTPACK → HT | `hash-max-listpack-entries` | **512** |
| | | `hash-max-listpack-value` | **64** bytes |
| **ZSet** | LISTPACK → SKIPLIST | `zset-max-listpack-entries` | **128** |
| | | `zset-max-listpack-value` | **64** bytes |
| **Set** | LISTPACK → INTSET → HT | `set-max-listpack-entries` | **128** |
| | | `set-max-listpack-value` | **64** bytes |
| | | `set-max-intset-entries` | **512** |
| **List** | LISTPACK → QUICKLIST | `list-max-listpack-size` | **-2** (8KB/노드) |
| | LZF 압축 | `list-compress-depth` | **0** (비활성) |

**`list-max-listpack-size` 음수 값**:
- `-1` = 4KB, `-2` = 8KB, `-3` = 16KB, `-4` = 32KB, `-5` = 64KB (노드당 최대 크기)
- 양수 = 노드당 최대 원소 수

**성능 영향**:
- 소규모: LISTPACK → 메모리 연속, 캐시 친화적 (느리지만 메모리 효율)
- 대규모: HT/SKIPLIST → O(1)/O(log N) 연산 (빠르지만 메모리 오버헤드)

## 8. 네트워킹 성능

### 8.1 핵심 버퍼 크기

```c
#define PROTO_IOBUF_LEN          (1024*16)  // 16KB: 기본 I/O 버퍼
#define PROTO_INLINE_MAX_SIZE    (1024*64)  // 64KB: 인라인 커맨드 최대 크기
#define PROTO_MBULK_BIG_ARG      (1024*32)  // 32KB: 빅 인자 임시 버퍼 임계값
#define NET_MAX_WRITES_PER_EVENT (1024*64)  // 64KB: 이벤트당 최대 쓰기 크기
```

**`PROTO_MBULK_BIG_ARG` 최적화**: 32KB 초과 인자는 클라이언트 쿼리 버퍼에 복사하지 않고 임시 버퍼 사용 → 대용량 SET/RPUSH 시 메모리 복사 절감.

### 8.2 IO 스레드

```c
// io-threads: 기본 1 (싱글스레드), 최대 128
// io-threads-do-reads: 읽기도 IO 스레드에서 처리
createIntConfig("io-threads", ..., server.io_threads_num, 1, ...)
```

**IO 스레드 활성화 시 효과**: 네트워크 읽기/파싱과 쓰기를 병렬 처리 → 코어가 많은 서버에서 처리량 향상.

**IO_THREAD_MAX_PENDING_CLIENTS = 16**: 스레드당 최대 대기 클라이언트 수.

### 8.3 파이프라인 통계

```c
// 클라이언트별
size_t stat_avg_pipeline_length_sum; // 파이프라인 길이 합산
size_t stat_avg_pipeline_length_cnt; // 샘플 횟수

// 서버 전역 (원자적)
redisAtomic long long stat_avg_pipeline_length_sum;
redisAtomic long long stat_avg_pipeline_length_cnt;

// 프리페치 최적화
int lookahead; // 각 파이프라인에서 미리 디코드할 커맨드 수
```

`INFO clients`에서 `avg_pipeline_length`로 확인 가능.

## 9. 메모리 축출(Eviction) 성능

### 9.1 샘플링 기반 근사 LRU/LFU

```c
// maxmemory-samples: 기본 5, 최대 64
createIntConfig("maxmemory-samples", ..., server.maxmemory_samples, 5, ...)
```

| samples | 정확도 | 오버헤드 |
|---------|--------|---------|
| 3 | 낮음 | 최소 |
| 5 | 양호 (기본) | 낮음 |
| 10 | LRU에 근접 | 중간 |

**Eviction Pool**: 16개 후보 키 누적 → 가장 오래된/드문 키 선택.

### 9.2 LFU 카운터 설계

```
Morris Counter (8비트):
  접근마다 1/(현재값 × lfu_log_factor + 1) 확률로 +1
  → 8비트로 수백만 접근 횟수 근사 표현

  lfu_log_factor=10 (기본): 약 1백만 접근까지 구분 가능
  lfu_decay_time=1 (기본): 분당 카운터 감소
  LFU_INIT_VAL=5: 신규 키 초기값 (즉시 축출 방지)
```

## 11. Lazyfree (비동기 해제) 성능

```c
// 모두 기본값 0 (비활성), DEBUG_CONFIG
lazyfree-lazy-eviction   = 0   // eviction 시 비동기 해제
lazyfree-lazy-expire     = 0   // 만료 키 비동기 해제
```

**비동기 해제 흐름**:
```

  → dbAsyncDelete()
  → BIO_LAZY_FREE 큐에 작업 추가
  → bio_lazy_free 스레드가 실제 해제
  → 메인 스레드는 즉시 반환 (레이턴시 최소화)
```

**비동기 해제 통계**:
```c
lazyfreeGetPendingObjectsCount()  // 해제 대기 중인 객체 수

```

## 13. 성능 최적화 기법 요약

| 기법 | 구현 | 효과 |
|------|------|------|
| **공유 정수** | 0~9999 사전 생성, refcount 불변 | 메모리 할당 0, 비교 O(1) |
| **EMBSTR** | 64바이트 캐시라인 단일 할당 | 캐시 미스 절반으로 감소 |
| **kvobj 인라인 키** | 키+값 연속 메모리 | 별도 키 할당/해제 없음 |
| **점진적 리해시** | 1버킷/연산 + beforeSleep 1ms | O(N) 블로킹 없음 |
| **SipHash-1-3** | Hash DoS 방어 + 빠른 해시 | 안전성 + 속도 균형 |
| **근사 LRU** | 5개 샘플 Eviction Pool | 정확한 LRU 대비 10% 오차, O(1) |
| **IO 스레드** | 네트워크 I/O 멀티스레드 | 멀티코어 네트워크 처리량 |
| **파이프라인 lookahead** | 커맨드 미리 디코드+프리페치 | IO 대기 중 CPU 활용 |
| **빅 인자 임시 버퍼** | 32KB 초과 인자 별도 버퍼 | 대용량 쓰기 메모리 복사 절감 |
| **비동기 해제** | BIO_LAZY_FREE 스레드 | 대용량 DEL 레이턴시 스파이크 방지 |
| **COW 스냅샷** | fork() 기반 | 스냅샷 중 서비스 지속 |
| **Active Defrag** | jemalloc hint + 객체 이동 | 단편화 누적 방지 |

## 14. 성능 관련 주요 설정 한눈에
