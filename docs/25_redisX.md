# Redis → redisX(Rust) 이관 로드맵

> 목적: `redis_src`(바닐라 Redis + 이번 세션에서 추가한 커스텀 기능)를 신규 프로젝트 `redisX`로 **Rust 전면 재구현**하기 위한 단계별 로드맵.
> 전체를 한 번에 이관하는 것은 비현실적이라고 판단, 서브시스템 단위 점진 이관으로 설계한다.
> 참고: `redis_document/00`~`24` (소스 분석 문서), `redis_src/CHANGE.md` (이번 세션 커스텀 변경 내역)

---

## 0. 배경 및 전제

- `redis_document`의 원래 목적 2가지 중 두 번째가 "C/C++ 소스를 Rust로 전환"이었다. 이 문서는 그 작업을 실행 가능한 로드맵으로 구체화한 것이다.
- 이관 대상은 **바닐라 Redis가 아니라 `redis_src` 현재 상태**다. 즉 다음 커스텀 기능이 이미 반영된 버전을 기준으로 한다 (`CHANGE.md` 참고):
  1. SLOWLOG — 메모리 저장 제거, 파일 기반 로깅/tail 읽기 (`slowlog.c/h`)
  2. AOF — MONITOR 스타일 텍스트 포맷으로 전면 교체, 복구 기능 포기 (`aof.c`)
  3. Python 스크립팅 엔진 — Lua와 공존하는 `FUNCTION/FCALL` 엔진 (`function_python.c/h`)
  4. Make 빌드 환경 — `BUILD_PYTHON` 자동 감지/설치 지원 (`Makefile`, `utils/install-python-dev.sh`)
- `redisX/` 디렉토리는 현재 빈 상태 — Cargo 워크스페이스로 새로 시작한다.
- 직전 대화에서 추산한 전체 이관 비용은 **약 1,100만~1,900만 토큰** (읽기/분석/코드생성/컴파일-디버깅 반복/테스트 포함, 벤더 C 의존성 제외). 단일 세션/컨텍스트로 소화 불가능한 규모이므로, 본 로드맵은 이를 **9개 Phase + 빌드 전환 트랙**으로 분해한다.

## 1. 이관 원칙

1. **와이어 프로토콜(RESP2/RESP3) 호환 유지** — 기존 `redis-cli`, `tests/*.tcl` 하네스, 심지어 real Redis 클라이언트 라이브러리를 그대로 검증 도구로 재사용한다. 프로토콜을 먼저 깨뜨리면 모든 이후 단계의 검증 수단이 사라진다.
2. **온디스크/와이어 바이트 포맷은 우선 1:1 포팅** — `listpack`, `ziplist`, `intset`, RDB 파일 포맷 등은 Rust에서도 동일 바이트 레이아웃을 생성/파싱하도록 포팅한다. 포맷을 새로 설계하는 것은 범위 밖.
3. **단일 스레드 커맨드 실행 불변식 유지 여부는 Phase 1에서 결정** — 이 프로젝트 전체에서 가장 중요한 아키텍처 분기점(§4 참고). 결정 전에는 Phase 2 이후로 진행하지 않는다.
4. **벤더링 C 의존성은 동등 기능의 성숙한 Rust crate 치환을 기본값으로** (예: `lzf`→`lz4_flex`/`flate2`, `siphash`→`siphasher`, `xxhash`→`xxhash-rust`). 직접 포팅은 포맷 호환이 필수인 경우(listpack 등)에만.
5. **각 Phase의 종료 조건은 "독립적으로 컴파일되는 모듈 + 최소 통합 테스트 통과"** — 빅뱅 이관 금지. Phase 중간에 전체가 안 돌아가도 되지만, Phase가 끝나면 그 서브시스템은 검증 가능해야 한다.
6. **커스텀 기능은 별도 트랙이 아니라 해당 서브시스템 Phase에 자연 편입** — SLOWLOG는 Phase 7, AOF는 Phase 4, Python 엔진은 Phase 6에서 함께 포팅한다.

## 3. Phase 상세

### Phase 0 — 코어 자료구조/유틸
- **포함**: `sds`, `dict`, `adlist`, `kvstore`, `mstr`, `intset`, `listpack`, `ziplist`, `zipmap`, `rax`, `ebuckets`, `estore`, `entry`, `fwtree`, `keymeta`, `zmalloc`, `util`, `rand`, `siphash`, `crc16/64`, `endianconv`, `monotonic`, `mt19937-64`, `pqsort`, `lzf_c/d`, `sha1`, `sha256`
- **Rust 설계 메모**: `sds`는 `Vec<u8>`/`bytes::Bytes`로 대체 가능하지만, RDB/프로토콜 레이어가 "binary-safe C string" 가정을 많이 깔고 있어 당분간은 동일 API 표면의 `RSds` 래퍼 타입으로 시작 → 이후 점진적으로 표준 타입으로 치환 권장. `listpack`/`ziplist`/`intset`은 바이트 포맷 호환이 필수이므로 **직접 포팅**(바이트 단위 인코딩 재현). `siphash`/`crc16`/`crc64`/`lzf`는 기존 crate(`siphasher`, `crc`, `lz4_flex` 등)로 치환.
- **완료 기준**: 각 자료구조별 단위 테스트(기존 `dict`/`sds`의 C 테스트 로직을 Rust `#[test]`로 이식) 통과, listpack/ziplist는 실제 Redis가 생성한 바이너리를 파싱해 라운드트립 검증.
- **리스크**: listpack/ziplist의 미묘한 인코딩 경계 조건(소수점, 길이 접두사 가변 길이 등)을 놓치면 Phase 4(RDB) 전까지 발견 안 될 수 있음 → Phase 0 자체에 바이너리 fixture 기반 테스트를 반드시 포함.

#### Phase 0 진행 상황 (완료)

워크스페이스: `redisX/Cargo.toml` (members = `crates/redisx-core`). 크레이트 이름 `redisx-core` (lib명 `redisx_core`).

**실제 Redis 바이너리 교차검증**:
1. `redis_src/src/redis-server`(포트 7799, `rdbcompression no`)를 띄워 `RPUSH`로 문자열(`"a" "b" "c"`), 양의 16비트 정수(`12345`), 음의 13비트 정수(`-200`), 100바이트 문자열을 넣고 `DUMP`으로 꺼낸 실제 바이트를 수작업으로 디코딩해 `listpack.rs`가 만든 바이트와 1바이트 단위로 대조 — 헤더(`total_bytes`/`numele`), 각 인코딩 바이트, backlen까지 전부 일치.
2. 같은 서버에서 `rdbcompression yes`로 200바이트 문자열을 담은 리스트를 `DUMP`해 실제 LZF 압축 바이트를 추출, `lzf.rs`의 `decompress()`로 풀어서 → 그 결과를 다시 `listpack.rs`로 파싱 → 원본 200바이트 문자열이 정확히 복원되는 end-to-end 체인을 확인(검증용 임시 example은 확인 후 삭제, 테스트 인스턴스는 `SHUTDOWN NOSAVE`로 정리).

**Phase 0 종료 요약**: 바이트/동작 호환이 필요한 항목(sds 핵심 서브셋, crc16/64, intset, dict, listpack, kvstore, lzf 압축해제)은 전부 포팅 및 실제 바이너리 교차검증 완료. 나머지는 ① 특정 데이터 타입 전용이라 해당 Phase로 재분류했고 그 Phase에서 실제로 처리됨(rax → Phase 9에서 `BTreeMap`으로 대체, ziplist/zipmap → Phase 12에서 포팅) ② 설계 선결 조건이 있어 해당 Phase로 이관했고 그 결정이 실제로 내려짐(zmalloc → §4-2 "Rust 기본 allocator" 결정) ③ Rust 표준/크레이트로 1:1 대체가 더 합리적이라 포팅 자체가 불필요(mstr/siphash/mt19937-64/monotonic/pqsort/sha1/sha256/endianconv/rand/adlist) — "건너뛰었다"가 아니라 "왜 Phase 0에 속하지 않는지"를 확인하고 내린 결정이며, 위 표의 "처리여부" 칼럼대로 전부 완료 상태다. **유일한 예외는 `ebuckets`/`estore`/`entry`/`keymeta`(해시 필드 TTL 전용 구조)** — Hash 타입을 구현하는 Phase 3로 재분류됐지만, Phase 3을 포함해 이 문서의 어느 Phase에서도 `HEXPIRE`류 해시 필드 TTL 커맨드 자체가 구현되지 않아 이 표에서 유일하게 미완료로 남아 있다.

### Phase 1 — 이벤트 루프 & 네트워크 (완료)
- **포함**: `ae.c`+`ae_epoll/evport/kqueue/select.c`, `anet`, `connection`, `networking`, `socket`, `unix`, `tls`, `resp_parser`, `call_reply`, `eventnotifier`
- **핵심 설계 결정 (§4-1, 확정됨)**: **`mio` 채택.** `tokio`는 소켓 I/O 자체는 더 "현대적"이지만, 그 대가로 `async`/`.await`가 연결을 다루는 모든 계층에 퍼지게 되고, Redis의 핵심 불변식("명령 실행은 절대 끼어들지 않는다")을 코드 전체에서 수동으로 재증명해야 하는 부담이 생긴다. 특히 이 포크에 이미 구현된 `function_lua.c`/`function_python.c`의 `scriptCall()` 기반 동기·재진입-안전 실행 모델은 비동기 전환과 상성이 나쁘다. 반면 `mio`는 순수 epoll/kqueue 래퍼로만 쓰고, 이벤트 루프 자체는 `ae.c`와 동일하게 "reactor가 평범한 콜백을 하나씩 순서대로 호출"하는 모양을 그대로 유지했다 — task/waker/future 없음.
- **포팅 결과**: `redisX/crates/redisx-net`에 `ae.rs`(이벤트 루프)와 `resp.rs`(RESP2/RESP3 프로토콜) 구현.
  - `ae.rs`: `ae.c`의 파일 이벤트(readable/writable, fd로 바로 인덱싱) + 타임 이벤트(생성/삭제/재스케줄, `AE_NOMORE` 계약, "이번 패스에서 새로 만든 타이머는 이번 패스에 실행 안 됨" maxId 가드까지)를 그대로 포팅. `AE_BARRIER`(writable을 readable보다 먼저 실행)도 순서 반전 테스트로 검증. C API와의 유일한 의도적 차이: `aeCreateFileEvent`가 같은 함수 포인터를 r/w 양쪽에 한 번에 꽂을 수 있던 부분은, Rust의 `Box<dyn FnMut>`이 `Copy`가 아니라 `set_readable`/`set_writable`로 분리(실제 호출부인 `connSetReadHandler`/`connSetWriteHandler`도 원래 따로 호출함).
  - `resp.rs`: `networking.c`의 `addReply*` 계열을 그대로 포팅한 인코더(Null/Bool/Double/BigNumber/Map/Set/Push 전부 RESP2 폴백 규칙 포함) + `processInlineBuffer`/`processMultibulkBuffer`를 포팅한 요청 파서. 단, 원본은 클라이언트별 상태(`qb_pos`/`multibulklen`/`bulklen`)를 이벤트 루프 반복에 걸쳐 들고 있는 상태머신인 반면, 이 포팅은 "버퍼를 받아 명령 하나를 시도 파싱, 모자라면 NeedMore" 형태의 **무상태** 함수로 단순화 — 프로토콜과 에러 조건은 동일, 매번 처음부터 재스캔하는 성능 손실만 있음(정확성 우선 원칙).
- **완료 기준 검증**: `examples/ping_server.rs`(mio 이벤트 루프 + RESP 코덱으로 PING/ECHO/QUIT만 처리하는 최소 서버)를 실제로 띄워, 이번 세션에서 빌드해 둔 **진짜 `redis-cli`**로 `PING`/`PING hello`/`ECHO "hi there"`/존재하지 않는 커맨드(에러 응답)를 전부 검증했고, Python 소켓 스크립트로 인라인 프로토콜(`PING\r\n`)과 **한 번의 TCP read에 담긴 멀티벌크 커맨드 2개 파이프라이닝**(`PING`+`ECHO world`가 한 read 콜백에서 순서대로 올바르게 처리되는지)까지 확인함.
- **리스크**: TLS(`tls.c`)는 OpenSSL C API에 강하게 묶여 있어 `rustls`/`native-tls` 중 선택이 필요 — 인증서/ALPN 옵션 호환성 재검증 필요(이번 Phase에서는 미포함, TLS 없이 평문 TCP만 구현 — `rustls`로 Phase 18에서 완료).
- **Phase 2로 넘기는 것**: 전체 커맨드 디스패치, 클라이언트별 출력 버퍼/쓰기 준비 상태 처리(지금은 소켓에 즉시 `write_all`), RESP3 `HELLO` 협상, 상태 저장형(stateful) 증분 파서로의 전환(성능 최적화), TLS(Phase 18에서 완료).

### Phase 2 — 커맨드 디스패치 & 서버 코어 (완료 — 최소 범위)
- **포함**: `server`, `commands`, `config`, `db`, `object`, `multi`, `acl`, `blocked`, `module`(스텁 처리 또는 범위 제외), `iothread`
- **범위 조정**: `module.c`/`redismodule.h`(모듈 API)는 LOC가 크고(헤더만 수천 라인) 이번 이관의 핵심이 아니므로 **1차 범위에서 제외**하고 Phase 9 이후 별도 검토 권장.
- **포팅 결과**: `redisX/crates/redisx-server` 신설(`redisx-core`+`redisx-net` 의존). `config.rs`(glob 패턴 매칭 CONFIG GET/SET), `object.rs`(Phase 2 범위에 맞춰 `RObj::String` 한 종류만 — 나머지 타입은 Phase 3), `server.rs`(커맨드 테이블 기반 디스패치 + MULTI/QUEUED/EXEC/DISCARD/EXECABORT 상태머신), `src/bin/redisx-server.rs`(`redisx-net`의 `ae`+`resp`를 실제로 엮은 바이너리).
  - 커맨드 테이블: `PING/ECHO/QUIT/SELECT/DBSIZE/FLUSHALL/SET/GET/DEL/EXISTS/TYPE/INCR/CONFIG/MULTI/DISCARD/EXEC` — "진짜 커맨드 몇 개가 디스패치/트랜잭션/CONFIG를 정말로 동작시키는지"를 증명하는 최소 집합. 키 저장은 Phase 0의 `KvStore`(`num_dicts_bits=0`)를 그대로 재사용 — Phase 5(클러스터)에서 비트 수만 늘리면 되는 구조를 Phase 2부터 자연스럽게 따라감.
  - MULTI/EXEC는 `multi.c`의 핵심 계약(중첩 MULTI 금지, QUEUED 응답, 큐잉 중 에러 시 `CLIENT_DIRTY_EXEC` → EXEC는 `EXECABORT`, DISCARD로 큐 비우기, EXEC는 큐를 순서대로 즉시 실행)을 그대로 포팅. **WATCH의 낙관적 잠금(`CLIENT_DIRTY_CAS`)은 미포함** — 키 변경 추적(`touchWatchedKeysInDb` 등)은 Phase 3에서 실제 쓰기 커맨드들이 들어온 뒤에 붙이는 게 더 자연스러워 다음 과제로 이연.
- **Phase 0에서 이관됐던 선결 과제 처리**: `zmalloc` 메모리 집계는 §4-2(할당자 전략) 결정이 아직 안 내려져 **이번에도 보류**(실제 커맨드가 메모리 통계를 요구하기 전까지는 급하지 않다고 판단). ACL 비밀번호 해시용 `sha1`/`sha256`은 이번 범위에 ACL 자체를 포함하지 않아 **아직 불필요** — ACL을 실제로 구현하는 시점으로 재이연.
- **완료 기준 검증**: 유닛테스트 21개(디스패치/CONFIG/MULTI 전 시나리오) 통과에 더해, 실제로 빌드한 `redisx-server` 바이너리를 띄워 **진짜 `redis-cli`**로 PING/SET/GET/INCR/DEL/EXISTS/TYPE/CONFIG GET·SET(글롭 패턴 포함)/`-n`을 통한 SELECT·DBSIZE/unknown-command·arity 에러까지 전부 확인했고, Python 소켓으로 멀티벌크 MULTI/EXEC를 두 시나리오(큐잉 중 미지의 커맨드로 EXECABORT / 정상 트랜잭션이 순서대로 실행되는 것) 모두 검증함.
- **커스텀 반영 지점**: `slowlog-file-path`를 포함한 커스텀 config 항목이 이 Phase의 config 시스템에 자연 포함됨을 실제 `CONFIG GET slowlog*`/`CONFIG SET slowlog-file-path ...` 호출로 확인.
- **Phase 2 → Phase 3+로 넘기는 것**: 출력 버퍼/쓰기 준비 상태 관리(Phase 1에서 이미 명시), RESP3 HELLO 협상, `WATCH` 낙관적 잠금, ACL, blocking 커맨드, 클라이언트별 출력 버퍼 한도, `RObj`의 List/Hash/Set/ZSet/Stream 변형(Phase 3 본연의 범위).

### Phase 3 — 데이터 타입 (완료 — 최소 범위: List/Hash/Set/ZSet)
- **포함**: `t_string/list/hash/set/zset/stream`, `hyperloglog`, `geo*`, `bitops`, `sort`
- **범위 조정(완료 후 재확정)**: 이번 패스는 **List/Hash/Set/ZSet**까지만 다루고, **Stream/HyperLogLog/Geo/bitops/SORT는 명시적으로 범위 밖**으로 남겼다. 이유: Stream은 Phase 0에서 재분류해 둔 `rax`(2,117줄, 아직 미착수)가 선행돼야 의미 있게 구현 가능하고, HyperLogLog/Geo/SORT는 String/Set/ZSet 위에 얹는 "응용 계층"이라 핵심 디스패치/인코딩 전환 로직을 증명하는 이번 목적엔 필수가 아니라고 판단함.
- **Phase 0에서 재분류되어 아직 남아있는 항목**: `rax`(Stream 전용), `ebuckets`/`estore`/`entry`/`keymeta`/`mstr`(해시 필드 TTL 전용) — 이번 Hash 구현에는 필드 TTL이 없어 여전히 불필요.
- **포팅 결과**: `redisx-server`에 `list.rs`/`hash.rs`/`set.rs`/`zset.rs` 신설, `object.rs`의 `RObj`에 각 변형 추가.
  - **List**: 항상 `ListPack` 하나 — 실제 Redis의 quicklist(listpack 노드 여러 개로 분할)는 미포팅. 거대 리스트에서 메모리 비효율은 있지만 `LPUSH/RPUSH/LPOP/RPOP/LRANGE/LINDEX` 동작은 동일(정확성 우선 원칙). 이 작업 중 Phase 0 `listpack.rs`에 없던 **임의 위치 삽입/삭제**(`insert_str`/`insert_int`/`remove`)를 추가 포팅함 — LPUSH(prepend)/LPOP/RPOP에 필수였던 빠진 조각.
  - **Hash**: `ListPack`(작을 때) ↔ `RDict`(클 때) 전환, 기준은 `hash-max-listpack-entries`/`-value`(실제 Redis와 동일 이름·기본값). 다운그레이드 없음(실제 Redis와 동일). 이 작업 중 Phase 0 `dict.rs`에 없던 **전체 1회성 반복자**(`RDict::iter`, `SCAN`용 `dictScan`과는 다른 `dictNext`류)를 추가 포팅 — `HGETALL` 구현에 필요했던 조각.
  - **Set**: 실제 Redis는 intset→listpack→hashtable 3단계 인코딩인데, **listpack 단계는 생략**하고 intset↔`RDict`(값 없는 맵) 2단계로 단순화 — 작은 문자열 집합의 메모리 최적화 하나를 포기한 것일 뿐, 정확성에는 영향 없음(모든 연산이 두 인코딩 모두에서 동일하게 동작). 정수 판정은 Phase 0의 `listpack::parse_canonical_i64`를 그대로 재사용해 `"007"` 같은 비정규 숫자 문자열이 실제 Redis처럼 문자열 멤버로 취급되도록 함.
  - **ZSet**: `ListPack`(작을 때, `(score,member)` 정렬 유지) ↔ 정렬된 `Vec<(member,score)>`(클 때) — 실제 Redis의 skiplist+dict 대신 이진탐색 삽입(`O(n)` 삽입, `O(log n)` 조회)으로 대체. kvstore의 Fenwick 트리와 같은 종류의 트레이드오프(정확성 동일, 점근적 성능만 다름).
  - 모든 타입이 공통으로 "틀린 타입의 키에 연산하면 `WRONGTYPE Operation against a key holding the wrong kind of value`"를 반환 — `server.c`의 모든 타입별 커맨드가 공유하는 핵심 불변식.
  - 신규 커맨드: `LPUSH/RPUSH/LPOP/RPOP/LRANGE/LLEN/LINDEX`, `HSET/HGET/HDEL/HGETALL/HLEN/HEXISTS`, `SADD/SREM/SISMEMBER/SMEMBERS/SCARD`, `ZADD/ZSCORE/ZREM/ZCARD/ZRANK/ZRANGE[WITHSCORES]`.
- **완료 기준 검증**: 유닛테스트 42개(타입별 인코딩 전환 경계값 포함) 전부 통과 + 실제 `redisx-server`를 띄워 **진짜 `redis-cli`**로 4개 타입의 전체 커맨드 세트를 호출해 리스트 순서, 해시 필드/값, 집합 멤버십, 정렬집합의 점수순 정렬(WITHSCORES 포함)과 WRONGTYPE 에러까지 전부 올바름을 확인함.
- **리스크(해결됨)**: 애초 우려했던 "zset의 skiplist+dict 이중 구조, quicklist의 plain/packed 노드 전환" 같은 세부 최적화는 위에 적은 대로 전부 의도적으로 단순화하고 그 이유를 문서화함으로써 리스크가 아니라 확정된 설계 결정이 됨.

### Phase 4 — 영속성 (완료 — RDB + AOF)
- **포함**: `rdb`, `rio`, `aof`(이미 MONITOR 포맷으로 교체된 버전), `redis-check-rdb`, `redis-check-aof`
- **범위 조정**: RDB와 AOF를 별도 패스로 나눠 진행했다 — AOF는 이미 MONITOR 포맷 전용 쓰기 로그로 단순화돼 있어 "RDB와 같은 바이트 포맷 호환성 리스크"가 없는 별개 작업이었기 때문.
- **Phase 0에서 재분류되어 사용된 항목**: `crates/redisx-core/src/lzf.rs`(압축해제)와 `intset.rs`/`listpack.rs`를 그대로 재사용 — Phase 0에서 미리 바이트 호환으로 포팅/검증해 둔 덕분에 Phase 4에서는 RDB 프레이밍(길이 인코딩, 타입 바이트, 오프코드)만 새로 작성하면 됐다. `ziplist`/`zipmap`(구버전 RDB 호환 로더)은 **이번 Phase에서는 범위 밖** — 아래 "미지원 포맷" 참고. (이후 Phase 12에서 마저 포팅됨.)
- **포팅 결과**: `redisx-server/src/rdb.rs` 신설.
  - **길이/문자열 인코딩**: `rdbSaveLen`(6/14/32/64비트 길이, **32/64비트는 빅엔디안** — Redis의 다른 대부분 바이너리 포맷과 반대라 주의 깊게 확인함)과 `rdbSaveRawString`(11바이트 이하 캐노니컬 정수는 int8/16/32 특수 인코딩, 그 외엔 길이+원문)을 그대로 포팅. 읽기 경로는 int8/16/32 인코딩에 더해 **LZF 압축 문자열**도 지원(Phase 0 `lzf.rs` 재사용) — 쓰기 경로는 압축을 전혀 하지 않음(Phase 0에서 이미 내린 결정: redisX는 압축 없이 쓰고, 압축 여부는 포맷 요구사항이 아니므로 실제 Redis도 비압축 RDB를 문제없이 읽음).
  - **객체 타입 매핑**: `RObj::List`→`RDB_TYPE_LIST_QUICKLIST_2`(노드 1개짜리 "가짜 quicklist"로, 바로 이전에 손으로 디코딩했던 바이트 구조 그대로), `Hash`→`RDB_TYPE_HASH_LISTPACK`/`RDB_TYPE_HASH`, `Set`→`RDB_TYPE_SET_INTSET`/`RDB_TYPE_SET`, `ZSet`→`RDB_TYPE_ZSET_LISTPACK`/`RDB_TYPE_ZSET_2`(스코어는 8바이트 바이너리 double, little-endian, "큰 점수부터" 저장하는 실제 Redis 순서까지 재현).
  - **파일 구조**: `REDIS0014` 헤더 + `SELECTDB` 오프코드 + 키마다 `[타입][키][값]` + `EOF`(0xFF) + **8바이트 CRC64 트레일러** — Phase 0에서 체이닝 가능하도록 고쳐둔 `crc64`를 그대로 사용. 읽기 경로는 `AUX`/`RESIZEDB`/`FREQ`/`IDLE`/`EXPIRETIME[_MS]` 오프코드를 인식하고 건너뜀(실제 Redis가 항상 쓰는 `redis-ver` 등 AUX 필드가 있어야 실제 덤프를 읽을 수 있어서 필수였음). `RDB_TYPE_SET_LISTPACK`(세 번째 Set 인코딩, `set.rs`엔 없는 것)도 읽을 때는 intset/dict 중 맞는 쪽으로 변환해 수용.
  - **미지원 포맷(이번 Phase 기준 명시적 범위 밖, 이후 전부 해소)**: 레거시 ziplist/zipmap 기반 타입(오프코드 9/10/12/13 — Phase 12에서 포팅됨)과 구형 plain list/zset(1/3), `FUNCTION2`/`MODULE_AUX`/`SLOT_INFO`/`KEY_META`(전부 Phase 20에서 포팅됨) — 당시엔 전부 명확한 에러를 반환(조용히 깨지지 않음)했음.
  - `SAVE` 커맨드와 서버 기동 시 RDB 자동 로드(`Server::load_rdb_if_present`)를 추가해 `dir`/`dbfilename` config로 실제 파일 입출력까지 연결.
- **완료 기준 검증 (유닛테스트를 넘어선 실제 교차검증)**:
  1. 유닛테스트 49개(빈 서버, 문자열 int 인코딩, 4개 타입의 소형/대형 인코딩 양쪽, SELECTDB 격리, 체크섬 손상 거부, DB 인덱스 범위 초과 거부) 전부 통과.
  2. **redisx-server → 실제 redis-server**: 문자열/리스트/해시/정수집합/문자열집합/정렬집합을 담아 `SAVE`한 뒤, 그 `dump.rdb`를 **실제 `redis-server`**가 그대로 읽게 함 — 로그에 `Done loading RDB, keys loaded: 7`가 찍히고 `redis-cli`로 전부 올바른 값(인코딩까지 `listpack`/`intset`으로 동일)을 확인.
  3. **실제 redis-server → redisx-server**: `rdbcompression yes` 상태의 실제 redis-server로 500바이트 문자열(LZF 압축 대상)·50개짜리 리스트·300개짜리 정수집합·해시·정렬집합을 저장한 뒤, 그 덤프를 redisx-server가 기동 시 그대로 로드 — `redis-cli`로 압축 해제된 문자열과 모든 컬렉션 값이 정확히 일치함을 확인.
  이 양방향 교차검증으로 "RDB SAVE/LOAD 라운드트립"과 "재시작 시 데이터 복구"라는 완료 기준을 둘 다 실제 바이너리로 충족했다.

#### AOF (완료)

- **포팅 결과**: `redisx-server/src/aof.rs` 신설. C 쪽에서 이미 내려진 "복구 포기, MONITOR 스타일 쓰기 전용 로그" 결정을 그대로 가져와 `catAppendOnlyGenericCommand`의 한 줄 포맷(`<ts>.<usec> [<dbid> <peer>] "ARG1" "ARG2" ...\r\n`)만 포팅했다 — AOF 로딩, `BGREWRITEAOF`, BASE/INCR manifest는 복구 자체가 범위 밖이라 전혀 필요 없음. 인자 이스케이프는 Phase 0의 `Sds::cat_repr`(C의 `sdscatrepr`과 동일 로직)을 그대로 재사용.
- **설계 결정 — `peer`를 `ClientState`에 저장**: AOF 줄의 `[dbid peer]`는 클라이언트의 `ip:port`가 필요한데, 이건 `Server`가 아니라 소켓을 들고 있는 바이너리 계층만 아는 정보다. `PSYNC`/`REPLICAOF`처럼 가로채는 대신, 연결을 수락할 때 바이너리가 `ClientState.peer`에 한 번 적어두고 이후로는 `Server`가 그 값을 그대로 쓰는 방식을 택했다 — PSYNC와 달리 AOF는 소켓 자체를 다루지 않고 문자열 하나만 필요하기 때문에 훨씬 가벼운 해법이 가능했다.
- **설계 결정 — 복제 전파와 AOF 기록을 하나의 훅으로 통합**: `dispatch`/`execute_single`/`apply_replicated_command` 세 지점 모두 쓰기 커맨드 성공 시 `after_write()` 하나를 호출해 전파(`propagate`)와 AOF 기록(`aof::append`)을 같이 처리한다. 레플리카로 복제돼 들어온 커맨드도 그 레플리카 자신의 AOF/하위 레플리카로 다시 흘러가도록 했다(체이닝 복제와 동일한 원리).
- **완료 기준 검증**: 유닛테스트 4개(포맷이 MONITOR 스타일과 일치, 바이너리-unsafe 인자 repr 이스케이프, 파일 생성/누적, `appendonly` 설정 반영) 포함 `redisx-server` 전체 57개 통과. 실제 `redisx-server`를 띄워 `CONFIG SET appendonly yes` 후 `redis-cli`로 SET/RPUSH/INCR을 실행해 생성된 `appendonly.aof` 파일을 직접 확인 — `1791924697.168912 [0 127.0.0.1:55134] "set" "foo" "bar baz"` 형태로 C 포크가 문서화해둔 예시 포맷과 정확히 일치했고, GET 같은 읽기 커맨드는 전혀 기록되지 않음을 확인.

### Phase 5 — 복제 (완료 — 기본 REPLICAOF만; 클러스터는 범위 밖)
- **포함**: `replication`, `cluster.c/h`, `cluster_legacy.c/h`, `cluster_slot_stats`, `cluster_asm`, `sentinel`, `gcra`
- **범위 조정**: 이번 패스는 **기본 마스터/레플리카 복제(`REPLICAOF`, 전체 재동기화만)** 까지만 다뤘다. 클러스터 가십 프로토콜(`cluster_legacy.c`)은 원래 계획대로 범위 밖으로 남겼다 — §4-5에서 결정이 필요하다고 플래그했던 "기존 클러스터와 바이트 호환 vs 신규 프로토콜" 질문은, 클러스터 자체를 아예 다음으로 미루기로 하면서 자연히 보류됨. Sentinel도 마찬가지로 범위 밖.
- **포팅 결과**: `server.rs`에 복제 상태(`Role`, `replid`, `master_repl_offset`)와 쓰기 커맨드 전파(`propagate`/`take_pending_propagation`/`apply_replicated_command`)를 추가하고, `src/bin/redisx-server.rs`에 `PSYNC`/`REPLICAOF`의 실제 네트워킹을 구현했다.
  - **설계 결정 — PSYNC/REPLICAOF는 일반 커맨드 핸들러가 아니라 바이너리 계층에서 가로챔**: 다른 모든 커맨드는 `fn(&mut Server, argv) -> Reply`로 표현되는데, `PSYNC`는 성공하면 RDB 바이트 스트림을 보내고 그 이후 연결의 의미를 "요청-응답"에서 "일방향으로 전파되는 커맨드 스트림"으로 바꿔야 하고, `REPLICAOF`는 아예 새 아웃바운드 연결을 열어야 한다 — 둘 다 `Server`가 들고 있지 않은 `mio::net::TcpStream`/`EventLoop` 접근이 필요해서, `Server`를 순수하게 유지하기 위해 일부러 바이너리 계층에서 커맨드 이름으로 먼저 가로챘다.
  - **설계 결정 — 레플리카가 `capa eof`를 일부러 광고하지 않음**: 실제 Redis는 레플리카가 `capa eof`를 보내야만 디스크리스(EOF 마커로 구분되는) RDB 전송을 쓰고, 그렇지 않으면 디스크 기반의 단순한 `$<len>\r\n<bytes>` 형식을 쓴다(`replication.c`의 `socket_target = ... && (mincapa & SLAVE_CAPA_EOF)`). EOF 마커 파싱(40바이트 랜덤 마커를 스트림에서 찾는 로직)을 아예 구현하지 않기 위해 `capa eof`를 생략해서, **진짜 `redis-server`를 마스터로 삼아도 항상 단순한 길이-프리픽스 형식**을 받도록 유도했다 — 이 덕분에 내 마스터 구현과 동일한 파싱 경로를 재사용할 수 있었다.
  - **설계 결정 — REPLICAOF의 초기 핸드셰이크는 동기/블로킹**: 연결+PING+REPLCONF 2회+PSYNC+RDB 수신까지 전부 블로킹으로 처리한 뒤에야 이벤트 루프에 스트리밍용으로 등록한다. 매 요청마다 발생하는 게 아니라 관리자가 가끔 호출하는 `REPLICAOF` 한 번에 국한된 일시적 비용이라 Phase 1의 단일 스레드 불변식을 어기지 않는다고 판단했다(실시간 커맨드 스트림 자체는 양방향 모두 완전히 이벤트 기반).
  - 부분 재동기화(`+CONTINUE`)·복제 백로그·`WAIT`·장애조치는 모두 범위 밖.
- **완료 기준 검증 (실제 바이너리 교차검증)**:
  1. 유닛테스트 4개 추가(쓰기만 전파/읽기는 전파 안 함, 실패한 쓰기는 전파 안 함, db 변경시에만 SELECT 주입, 복제된 커맨드 적용) 포함 `redisx-server` 전체 53개 테스트 통과.
  2. **redisx-server 마스터 + redisx-server 레플리카**: `REPLICAOF`로 전체 동기화(문자열/리스트/해시/셋) 후, 마스터에 새 쓰기(SET/INCR)를 하면 레플리카에 실시간으로 반영됨을 확인.
  3. **redisx-server 레플리카 → 실제 `redis_src/src/redis-server` 마스터**: 실제 마스터에 데이터를 넣고 redisx-server를 그 레플리카로 붙였더니 전체 동기화(109→297바이트 RDB)와 이후 실시간 스트리밍 모두 정상 동작(`redis-cli`로 전부 확인).
  4. **실제 `redis-server`를 redisx-server의 레플리카로 붙이는 반대 방향에서 무관한 기존 버그 발견**: 이 프로젝트의 `redis_src` 커스텀 빌드(Python 스크립팅 엔진 세션에서 작업한 그 포크)를 레플리카로 붙이자, 전체 동기화 직전 `emptyData()`가 `functionsLibCtxClearCurrent()`를 통해 **`pythonEngineInitEngine()`을 재호출**하면서 `PyEval_SaveThread`에서 세그폴트(이미 초기화된 Python 인터프리터를 또 초기화하려 함). **이건 오늘 작업한 redisX Rust 포팅과 무관한, 이전 세션에서 추가된 Python 엔진 통합 코드 자체의 버그**이며, `FLUSHALL`이나 다른 복제 레플리카를 붙일 때도 똑같이 재현될 것으로 보인다. Homebrew의 순정 Redis 8.6.0으로 바꿔서 재시도했더니 이번엔 `RDB_VERSION`(이 포크는 14, 순정 8.6.0은 그보다 낮은 값)이 달라 "Can't handle RDB format version 14" 에러로 막혀, 이 방향은 완전한 검증을 못 했다 — 다만 반대 방향(③)에서 이미 프로토콜 호환성은 충분히 입증됐다고 판단. **`redis_src`의 Python 엔진 재초기화 버그는 이 redisX 포팅과 별개로 fix가 필요한 이슈로 남겨둔다.**

### Phase 6 — 스크립팅 엔진 (완료 — FUNCTION/FCALL, Lua + Python)
- **포함**: `functions.c`의 엔진-추상화 설계를 포팅한 `FUNCTION LOAD/DELETE/LIST` + `FCALL/FCALL_RO`, Lua 엔진(`function_lua.c` 대응), Python 엔진(`function_python.c` 대응).
- **범위 조정**: 레거시 `EVAL`/`EVALSHA`(`eval.c`, C 버전에서 Lua 전용으로 하드코딩되어 있고 `functions.c`의 엔진 추상화와는 별개 경로)는 범위 밖으로 남겼다 — `FUNCTION`만으로 두 엔진을 전부 실제로 동작시킨다는 이번 Phase의 완료 기준은 이미 충족됨. 함수 플래그(`no-writes` 등), `FUNCTION DUMP`/`RESTORE`, 스크립트 kill/timeout도 범위 밖.
- **Rust 설계 메모**:
  - Lua는 `mlua` crate(`lua54` + `vendored` feature — Lua 5.4를 소스에서 그대로 빌드하므로 시스템에 Lua가 없어도 동작), Python은 `pyo3`(`auto-initialize` feature — 시스템에 이미 설치된 Python을 자동 감지/초기화)로 치환. C 포크의 `BUILD_PYTHON` 자동 감지 Makefile 로직에 비하면 두 엔진 모두 설정 작업 없이 그대로 빌드됨.
  - 원본의 `engine` vtable 추상화(`functions.c`)는 `script.rs`의 `EngineKind`(Lua/Python) + `CompiledFunction`(`Lua(mlua::RegistryKey)` / `Python(pyo3::Py<PyAny>)`) + `Library` 세 타입으로 대응시켰다. Python 엔진은 `python` Cargo feature로 분리(`--features python`로만 빌드에 포함) — Lua는 항상 켜져 있다.
  - **재진입 문제와 해법**: `redis.call()`은 스크립트 콜백 안에서 "또 하나의 평범한 Redis 커맨드"를 실행해야 하므로 `&mut Server`가 다시 필요한데, `FCALL` 핸들러가 이미 `&mut Server`를 스택에 들고 있는 상태라 평범한 대여로는 불가능하다(C 포크가 `current_run_ctx`류의 static 전역으로 풀던 것과 동일한 문제). Rust에서는 스레드-로컬에 담은 raw pointer(`CURRENT_SERVER: Cell<*mut Server>`)로 재현했다 — `push_context`/`pop_context`로 각 `FCALL` 호출 전후에 설치/복원하고, `redis_call_impl`에서 그 포인터를 역참조해 동일한 `Server::dispatch`를 다시 태운다. 이 덕분에 스크립트 안의 쓰기는 타입체크/WRONGTYPE/복제 전파/AOF 로깅까지 평범한 클라이언트 커맨드와 완전히 동일한 경로를 탄다. `unsafe`를 쓰지만 `dispatch`의 커맨드 핸들러들이 `lua`/`compiled`/`libraries`/`functions` 필드를 건드리지 않으므로 실제 데이터 레이스는 없다는 점을 모듈 문서에 명시해둠(Phase 1의 `ae.rs` take-and-restore 패턴과 같은 정신).
  - **RESP↔스크립트 값 변환**은 각 언어의 자연스러운 관용구를 따르되 모두 문서화된 단순화를 거쳤다: Lua는 테이블이 하나뿐이라 RESP map도 "키,값,키,값..." 식으로 평탄화한 테이블로 단순화했지만, Python은 진짜 `dict`가 있어서 RESP map을 그대로 `dict`로 옮긴다(손실 없음). 양쪽 다 RESP bulk string은 임의 바이너리가 아니라 UTF-8 `str`/Lua 문자열로 다루는 단순화를 뒀다(바이너리는 손실 변환). `keys`/`args`는 Lua는 1-indexed 테이블, Python은 0-indexed 리스트로 각 언어 관용에 맞췄다.
  - **엔진을 가로지르는 버그를 하나 발견/수정**: Lua/Python 에러(특히 Lua의 멀티라인 스택 트레이스백)를 `Reply::Error`로 그대로 감쌌더니 RESP 단순-에러 라인에 리터럴 CR/LF가 섞여 프로토콜 프레이밍이 깨지는 버그를 **진짜 `redis-cli`로 테스트하다가** 발견(`Error: Bad simple string value`로 나타남) — `sanitize_error()`로 `\r`/`\n`을 공백으로 치환해 모든 스크립팅발 에러 경로에 일괄 적용해 수정.
  - **`FCALL` 자체는 `is_write`로 표시하지 않음**: 스크립트 내부의 각 `redis.call()` 쓰기가 `dispatch` 재진입을 통해 이미 각자 전파되므로(실제 Redis의 "effects replication"과 동일), `FCALL`까지 전파로 표시하면 모든 쓰기가 중복 전파된다.
- **macOS 빌드 환경 메모(이번 세션에서 실제로 겪은 문제, Phase B에서 해결됨)**: pyo3 `auto-initialize`가 찾아낸 시스템 Python이 Anaconda/Miniconda처럼 비-framework 빌드인 경우, 바이너리가 `@rpath/libpython3.1x.dylib`를 찾지 못해 런타임에 `dyld: Library not loaded`로 죽는다. 이번 Phase 6 시점에는 `DYLD_LIBRARY_PATH=<python의 lib 디렉터리>`를 실행 시 수동으로 지정해야 했다 — **Phase B에서 `redisx-server/build.rs`가 동일한 경로를 링커 rpath로 바이너리에 직접 박아 넣도록 고쳐서, 이 수동 설정은 더 이상 필요 없다.** (빌드 자체는 이 문제와 무관하게 항상 성공했음.)
- **완료 기준 검증**:
  1. 유닛테스트: 기본 빌드(`cargo test -p redisx-server`) 66개 통과(Lua 경로만), `--features python` 빌드 71개 통과(Lua 9개 + Python 5개, 동일한 시나리오를 양쪽 엔진에 대해 일대일로 반복 — 재진입이 실제 키스페이스에 닿는지, 에러가 `pcall`에서는 안 터지는지, 쓰기가 복제 스트림에 전파되는지, 두 엔진이 서로 다른 라이브러리명으로 동시에 공존하는지까지 모두 확인). `cargo clippy -p redisx-server --all-targets`는 기본/`--features python` 양쪽 모두 경고 0개.
  2. **실제 `redisx-server` 바이너리 + 진짜 `redis-cli`로 Lua 교차검증**: `FUNCTION LOAD`로 3개 함수(set/get/echo)를 등록한 라이브러리를 올리고 `FCALL`로 전부 호출, `FUNCTION LIST`의 구조까지 확인. String 키에 `LPUSH`를 호출하는 함수로 WRONGTYPE 에러가 `sanitize_error` 수정 전/후 어떻게 다른지 직접 비교(수정 전: `redis-cli`가 `Error: Bad simple string value`로 프로토콜 깨짐 / 수정 후: 깔끔한 한 줄 `(error) ERR ...`).
  3. **실제 `redisx-server`(`--features python`) + 진짜 `redis-cli`로 Python 교차검증**: Python 라이브러리(`pyecho`/`pyset`/`pyget`)를 `FUNCTION LOAD`하고 `FCALL`로 호출해 Lua와 동일한 결과를 얻었고, 같은 서버에 Lua 라이브러리를 추가로 로드해 **두 엔진이 한 프로세스 안에서 동시에 공존**함을 확인(`luaecho`와 `pyecho`를 번갈아 호출). Python 쪽 WRONGTYPE 에러도 `sanitize_error`를 거쳐 한 줄로 나오는 것까지 확인.

### Phase 7 — 운영/보조 기능 (완료 — SLOWLOG + EXPIRE + PUBSUB + CLIENT TRACKING 기본)
- **포함/범위 조정**: `slowlog`(파일 기반, 커스텀 설계 그대로 포팅), `expire`(TTL 전체 명령군 + 활성 만료), `pubsub`(샤드 pub/sub 제외), `tracking`(기본 모드만). `latency`/`defrag`/`evict`/`lazyfree`/`hotkeys`/`bio`/`debug`/`childinfo`/`syscheck`는 전부 범위 밖으로 남겼다 — jemalloc 아레나 통계·fork 기반 백그라운드 저장·멀티스레드 I/O처럼 "C 메모리 할당자/프로세스 모델에 결합된 운영 진단" 기능들이라, 이 포트의 단일 스레드 리액터 + Rust 기본 allocator 모델에는 적용 대상 자체가 없거나(`defrag`/`lazyfree`/`bio`) Rust 쪽에서 의미를 다시 정의해야 하는(`debug`/`latency`) 영역이라고 판단했다. `notify`(keyspace notification)도 PUBSUB 인프라가 이번에 막 생겼으니 다음 세션의 자연스러운 후속으로 남겨둔다.
- **SLOWLOG**: `CHANGE.md` §1 설계(메모리 저장 완전 제거, 파일 append + 매 호출마다 파일 tail 재파싱) 그대로 포팅. 라인 포맷(`[수행된 yyyy-mm-dd hh:mm:ss] ip "cmd" "arg" ... <dur>us`)과 그 라벨 문자열까지 바이트 그대로 재현했다. **의도적으로 벗어난 지점 하나**: C 버전은 `localtime_r`/`strftime`로 시스템 로컬 타임존을 쓰지만, 이 포트는 TZ 데이터베이스 의존성을 새로 끌어오고 싶지 않아 항상 UTC로 쓰고 읽는다 — `SLOWLOG GET`이 돌려주는 `time` 필드(실제 유닉스 타임스탬프)는 쓰기/파싱이 같은 기준을 쓰므로 정확히 왕복하고, 사람이 파일을 직접 읽을 때 보이는 날짜/시각 칸만 로컬 타임존이 아닌 UTC로 보인다는 점만 다르다.
- **EXPIRE 계열**: `EXPIRE`/`PEXPIRE`/`EXPIREAT`/`PEXPIREAT`/`PERSIST`/`TTL`/`PTTL`/`EXPIRETIME`/`PEXPIRETIME` + `SET`의 `EX`/`PX`/`EXAT`/`PXAT`/`KEEPTTL` 옵션까지 포팅. `NX`/`XX`/`GT`/`LT` 플래그는 범위 밖. **설계 결정 — 활성 만료를 "매 커맨드 실행 직전 해당 db 전체 스윕"으로 단순화**: 실제 Redis의 `activeExpireCycle`(주기적 크론 + 무작위 샘플링)을 재현하는 대신, `run_command`(모든 커맨드 실행 경로가 공유하는 단일 지점) 진입 시점에 그 커맨드가 쓸 db의 `expires` 맵 전체를 훑어 만료된 키를 즉시 삭제한다 — `expires` 맵은 보통 비어 있거나 작으므로 비용이 거의 없고, Phase 0의 Fenwick 트리 생략 결정과 같은 "정확성 우선, 성능은 나중" 기조. 마스터만 삭제된 키에 대해 합성 `DEL`을 전파/AOF 기록하고, 레플리카도 자신의 만료된 키를 로컬에서 즉시 지우되 전파는 하지 않는다(실제 Redis의 "읽기에서만 숨기고 마스터의 DEL을 기다린다"는 더 정교한 split-brain 방지 로직은 생략 — 나중에 도착하는 마스터의 DEL이 이미 지워진 키에 멱등하게 적용되므로 무해함).
- **PUBSUB**: `SUBSCRIBE`/`UNSUBSCRIBE`/`PSUBSCRIBE`/`PUNSUBSCRIBE`/`PUBLISH`/`PUBSUB CHANNELS·NUMSUB·NUMPAT`. 샤드 pub/sub(`SSUBSCRIBE` 등)는 클러스터 전용이라 범위 밖(클러스터 자체가 범위 밖인 것과 동일 사유). **설계 결정 — `Reply::Multi` 신규 변형 추가**: `dispatch()`는 커맨드당 `Reply` 하나만 반환하는데, `SUBSCRIBE ch1 ch2`는 채널마다 별도의 최상위 RESP 프레임을 보내야 한다(`pubsub.c`가 채널당 한 번씩 `addReplyPubsubSubscribed`를 호출하는 것과 동일). `Reply::Multi(Vec<Reply>)`를 추가해 "감싸는 프레임 없이 여러 독립 프레임을 이어 붙여 인코딩"하는 것으로 해결 — 원소가 하나뿐이면 평범한 단일 프레임과 바이트 단위로 동일해서 기존 커맨드에는 영향이 없다. **설계 결정 — `PUBLISH`는 특정 다른 클라이언트에게 비동기로 메시지를 밀어넣어야 하는 최초의 기능**(복제는 항상 "모든 레플리카에게 동일한 바이트" 브로드캐스트였던 것과 다름): `ClientState`에 `id`(바이너리 계층이 `RawFd`를 그대로 부여)를 추가하고, `Server`에 `(client_id, Reply)` 큐(`pending_pushes`)를 둬서 바이너리 계층이 `take_pending_pushes()`로 꺼내 그 fd가 아직 연결돼 있으면 그 커넥션 고유의 RESP 버전으로 인코딩해 써준다 — `take_pending_propagation()`과 동일한 "Server는 소켓이 없다" 패턴의 재사용.
- **CLIENT TRACKING**: 기본(비-`BCAST`) 모드만 — `CLIENT TRACKING ON|OFF`, 같은 커넥션으로의 무효화 푸시, `argv[1]`을 "이 커맨드가 건드린 키"로 보는 휴리스틱(이 포트가 구현한 모든 단일키 커맨드에 대해 정확함; `CONFIG GET`처럼 `argv[1]`이 진짜 키가 아닌 비-write 커맨드는 추적 테이블에 무해한 더미 항목이 하나 생길 뿐 — 해당 클라이언트가 끊기거나 트래킹을 끄면 자동으로 청소됨). `REDIRECT`/`BCAST`/`PREFIX`/`OPTIN`/`OPTOUT`/`NOLOOP`는 범위 밖.
- **선행 요건으로 추가된 `HELLO`**: `CLIENT TRACKING`은 RESP3 전용인데, 이 포트는 Phase 2 완료 노트에서부터 "RESP3 HELLO 협상은 Phase 3+로 이연"이라고 미뤄둔 채 Phase 3~6 어디서도 집어가지 않았다 — `HELLO`가 없으면 실제 클라이언트가 RESP3로 전환할 방법 자체가 없어 이번 Phase의 완료 기준(CLIENT TRACKING 기본 동작)을 실제 클라이언트로 증명할 수 없는 구조였다. 그래서 `HELLO [protover]`(버전 negotiation만, `AUTH`/`SETNAME`은 받아들이되 무시 — ACL이 없어 인증할 대상 자체가 없음)를 최소 구현으로 추가했다. 스코프 확장이 아니라 이번 Phase의 완료 기준이 요구하는 막힌 전제조건이라 판단.
- **완료 기준 검증**:
  1. 유닛테스트: 기본 빌드 92개(`SLOWLOG` 6 + `EXPIRE` 계열 6 + `PUBSUB` 8 + `CLIENT TRACKING` 4 + `HELLO` 1, 기존 66개 포함) 통과, `--features python` 빌드 97개 통과. `cargo clippy --workspace --all-targets`(및 `--features python`) 경고 0개.
  2. **SLOWLOG**: 실제 `redisx-server` + `redis-cli`로 `slowlog-log-slower-than 0`으로 모든 커맨드를 강제 기록시키고 `SLOWLOG GET`/`LEN` 결과와 파일 raw 바이트를 직접 대조 — 타임스탬프/시간/인자/피어 IP 전부 정확히 round-trip함을 확인.
  3. **EXPIRE**: 실제 `redis-cli`로 `EXPIRE`/`TTL`/`PERSIST`, `SET ... EX`/`KEEPTTL`가 TTL을 설정·보존·해제하는 것, `PX 50`으로 설정한 키가 짧은 sleep 후 `GET`/`EXISTS`에서 실제로 사라지는 것(능동 만료 스윕 확인)까지 확인.
  4. **PUBSUB**: `redis-cli SUBSCRIBE`를 백그라운드로 띄워두고 **별도의 `redis-cli` 프로세스**에서 `PUBLISH`했을 때 구독 중인 프로세스가 실시간으로 `message`를 받는 것(진짜 크로스-프로세스 전달)과, `PSUBSCRIBE "news.*"`가 `news.tech` 발행을 `pmessage`로 받는 것, `PUBSUB CHANNELS`/`NUMPAT`이 살아있는 구독 상태를 정확히 반영하는 것까지 확인.
  5. **CLIENT TRACKING**: `redis-cli -3`로 `HELLO 3` 협상이 실제로 되는 것을 먼저 확인한 뒤, `redis-cli`의 비대화형 I/O 모델이 비동기 푸시 수신 테스트에 맞지 않아 — 이전 phase들의 "로우레벨 프로토콜 검증은 raw 소켓 스크립트로" 관행을 따라 — Python 소켓 스크립트로 커넥션 A가 `HELLO 3` + `CLIENT TRACKING ON` + `GET k` 후, **완전히 별도인 커넥션 B**가 `SET k v3`을 실행하자 커넥션 A가 비동기로 `>2\r\n$10\r\ninvalidate\r\n*1\r\n$1\r\nk\r\n` RESP3 푸시 프레임을 정확히 받는 것을 바이트 단위로 확인.

### Phase 8 — 클라이언트 도구 (완료 — `redisx-cli`; `redis-benchmark`/`lolwut`는 범위 밖으로 이연했다가 Phase 9에서 마저 포팅)
- **포함/범위 조정**: `redis-cli.c`(11,144줄)에서 완료 기준이 실제로 요구하는 부분만 — 연결, 대화형 REPL(라인 편집 + 영속 히스토리), 원샷 모드, RESP3(`HELLO`) 협상, raw/formatted 출력 전환, `SUBSCRIBE`/`PSUBSCRIBE` 스트리밍 모드 — 가져왔다. `cli_commands`/`cli_common`의 커맨드별 탭 자동완성·인라인 도움말 테이블, 클러스터 리다이렉션, `--bigkeys`/`--hotkeys`/`--memkeys`, `--latency*`, `--pipe`, RDB/레플리카 모드, Lua 디버거(`--ldb`)는 전부 범위 밖으로 명시. `redis-benchmark`와 `lolwut`는 각각 별도 도구(전자는 그 자체로 상당한 작업, 후자는 순수 이스터에그)라 이번 Phase에서 다루지 않고 다음으로 이연 — 완료 기준 문장(`redisX-cli`가 REPL 경험을 제공)이 이 둘을 요구하지 않는다고 판단.
- **새 크레이트 `redisx-cli`**: `redisx-core`(인자 토큰화용 `split_args`, 이스케이프 출력용 `Sds::cat_repr` 재사용)와 `redisx-net`에만 의존, `rustyline`(라인 편집/히스토리) 하나만 신규 의존성으로 추가.
- **선행 요건 — `redisx-net`에 RESP 응답 디코더 신규 추가**: 지금까지 `resp.rs`는 "요청(멀티벌크) 파싱 + 응답 인코딩"만 있었고 "응답 디코딩"은 아무도 필요로 한 적이 없었다(서버는 응답을 만들기만 하지 읽지 않음). CLI는 서버가 보낸 바이트를 읽어 사람이 읽을 수 있게 그려야 하므로 그 반대 방향이 처음으로 필요해졌다 — `parse_reply`/`ReplyParseOutcome`을 `parse_request`와 동일한 "증분 재시도" 패턴으로 추가(RESP2/3 전 타입 재귀 지원), `Reply::encode`로 만든 바이트를 다시 `parse_reply`로 읽으면 원래 값으로 정확히 왕복하는지 전수 테스트.
- **설계 결정 — raw/formatted 출력 전환은 표준 라이브러리 `IsTerminal`만으로**: 실제 `redis-cli`와 동일하게 "stdout이 진짜 터미널이면 formatted, 파이프/리다이렉트면 raw"를 기본값으로 삼고 `--raw`/`--no-raw`로 강제 전환 가능하게 했다. `std::io::IsTerminal`(표준 라이브러리, 외부 크레이트 불필요)로 tty 여부를 판별 — 이번 세션 테스트에서도 Bash 도구를 통한 비-tty 호출은 자동으로 raw, `--no-raw`를 줄 때만 포맷된 출력이 나오는 것으로 실제로 확인된 바로 그 동작.
- **설계 결정 — nested 배열의 번호 매김/들여쓰기 로직**: 실제 `redis-cli`의 `cliFormatReplyTTY`가 만드는 `4) 1) "SLOWLOG"` / `      2) "LEN"` 같은 "중첩 배열의 첫 항목은 부모 라벨과 같은 줄에 이어 쓰고, 그 다음 항목부터 누적된 들여쓰기로 새 줄" 스타일을 정확히 재현 — Phase 7에서 실제로 캡처해 둔 `SLOWLOG GET` 출력 샘플을 테스트 픽스처로 그대로 사용해 바이트 단위로 일치하는지 검증했다.
- **`SUBSCRIBE`/`PSUBSCRIBE` 스트리밍 모드**: 보내고 나면 들어오는 모든 reply를 무한히 출력 — Phase 7에서 만든 PUBSUB을 실제 두 프로세스 간 전달까지 다시 한번 교차검증하는 효과. Ctrl-C로 멈추는 것은 실제 `redis-cli`처럼 "프롬프트로 복귀"가 아니라 그냥 프로세스가 종료되는 단순화된 동작(블로킹 소켓 읽기를 깔끔히 취소하려면 시그널 핸들링 의존성이 추가로 필요해, 이번 완료 기준에는 과한 비용이라고 판단).
- **완료 기준 검증**:
  1. 유닛테스트: `redisx-net`에 RESP 응답 디코더 왕복 테스트 다수 추가(33개로 증가), `redisx-cli` 자체 6개(라벨 포맷팅 샘플 포함) 신규. `cargo test --workspace` 전체 통과(core 59 + net 33 + server 92 + cli 6, `--features python` 빌드는 server 97), `cargo clippy --workspace --all-targets`(및 `--features python`) 경고 0개.
  2. **실제 `redisx-server` + 빌드한 `redisx-cli` 바이너리로 교차검증**: 원샷 모드로 SET/GET/LPUSH/LRANGE/INCR(WRONGTYPE 에러 포함)을 raw(기본, 비-tty)와 `--no-raw`(formatted) 양쪽 모드로 실행해 포맷 차이를 직접 확인(`GET foo` → raw `bar` / `--no-raw` `"bar"`). `-3`으로 RESP3 협상 + `CLIENT ID` 호출 확인. `-x`로 표준입력에서 마지막 인자를 읽어 `SET viastdin <stdin값>`이 정확히 적용됨을 확인. `SLOWLOG GET`의 중첩 배열 formatted 출력이 Phase 7에서 확보해 둔 실제 샘플과 정확히 일치함을 재확인.
  3. **SUBSCRIBE 크로스-프로세스 검증**: `redisx-cli SUBSCRIBE news`를 백그라운드로 띄우고 별도의 `redisx-cli PUBLISH news ...` 프로세스로 발행했을 때, 구독 중인 프로세스가 `subscribe`/`message` 두 프레임을 실시간으로 정확히 출력함을 확인.
  4. **REPL 모드**: 표준입력으로 `SET`/`GET`/`SELECT`/`QUIT` 시퀀스를 흘려보내 대화형 루프가 각 커맨드를 순서대로 올바르게 실행하고 `QUIT`에서 깨끗이 종료함을 확인, `~/.redisx-cli_history` 파일이 실제로 생성/누적되는 것도 확인.

### Phase B — 빌드/배포 전환 (완료 — `--features python`의 런타임 rpath 격차 해소)
- **"자동 감지를 Cargo build.rs + feature flag로 재구현"은 이미 Phase 6에서 사실상 완료돼 있었음을 확인**: `pyo3`의 `auto-initialize` feature가 `pyo3-build-config` crate를 통해 시스템의 Python 설치(버전, `lib_name`, `lib_dir`, 헤더 경로 등)를 셸 스크립트 하나 없이 빌드 시점에 전부 자동 탐지한다 — `BUILD_PYTHON=yes`의 `python3-config` 후보 탐색 로직(`CHANGE.md` §4)을 직접 재구현할 필요 자체가 없었다. `make python-setup`(OS 패키지 매니저로 Python dev 헤더를 자동 설치하는 신규 타겟)에 대응하는 기능은 **의도적으로 제공하지 않음** — Cargo 생태계 관례상 빌드 도구가 시스템 패키지를 임의로 설치하는 동작은 기대되지 않고, `pyo3-build-config`가 Python을 못 찾았을 때 내는 에러 메시지 자체가 이미 충분히 친절해서 별도 스크립트가 필요 없다고 판단.
- **진짜 남아 있던 격차 — 런타임 rpath 임베딩**: Phase 6 검증 중 실제로 겪은 문제(Anaconda/Miniconda 같은 비-framework Python에서 `dyld: Library not loaded: @rpath/libpython3.13.dylib`)가 이 Phase의 진짜 작업거리였다. C 포크는 `CHANGE.md` §4에서 `-Wl,-rpath,<python-prefix>/lib`를 링크 플래그에 추가해 해결했는데, 이번 포트는 `redisx-server/build.rs`(신규)에서 `pyo3_build_config::get()`로 **pyo3가 이미 빌드 시점에 확정해 둔 바로 그 interpreter config**(별도의 재탐지 로직 없이, pyo3와 절대 어긋날 수 없는 단일 소스)를 읽어 `lib_dir`를 얻고 `cargo:rustc-link-arg=-Wl,-rpath,{lib_dir}`로 동일한 플래그를 내보낸다. `-Wl,-rpath`는 macOS(ld64 → `LC_RPATH`)와 Linux(GNU ld/lld → `DT_RUNPATH`) 양쪽에서 똑같이 동작해 플랫폼 분기가 필요 없었다. `python` feature가 꺼져 있으면 `build.rs`는 완전히 아무 일도 하지 않아 기본 빌드는 전과 동일하게 의존성 0개를 유지한다.
- **`-bins`가 아니라 범용 `rustc-link-arg` 사용**: 처음엔 `cargo:rustc-link-arg-bins`로 바이너리에만 좁혀 적용했는데, `cargo test --features python`이 만드는 테스트 하네스 바이너리(`script_python.rs`의 `#[cfg(test)]` 모듈이 그 안에서 호출됨)에는 적용되지 않아 `DYLD_LIBRARY_PATH` 없이 테스트가 실패하는 것을 실제로 겪었다 — 접미사 없는 범용 `rustc-link-arg`로 바꿔 테스트 하네스도 동일하게 커버하도록 수정.
- **완료 기준 검증**:
  1. `otool -l`로 빌드된 `redisx-server` 바이너리에 `LC_RPATH /opt/anaconda3/lib`가 실제로 박혀 있음을 직접 확인.
  2. **`DYLD_LIBRARY_PATH`를 완전히 `unset`한 셸에서** `redisx-server --features python` 빌드가 (a) 정상적으로 기동하고, (b) 실제로 `FUNCTION LOAD`(Python 엔진)+`FCALL`을 실행해 올바른 결과를 돌려주는 것까지 확인 — Phase 6 때는 반드시 필요했던 환경변수 설정이 이제는 전혀 필요 없어졌음을 end-to-end로 증명.
  3. 같은 `unset` 상태에서 `cargo test -p redisx-server --features python`(97개) 전부 통과, `cargo clippy --all-targets --features python` 경고 0개 — 테스트 하네스도 수동 환경변수 설정 없이 동작함을 확인.
  4. `otool -L`로 **기본 빌드**(`--features python` 없이)의 `redisx-server`와 `redisx-cli`에 libpython 링크가 전혀 없음을 재확인 — C 포크가 지켰던 "Python 미사용 시 완전히 기존과 동일" 불변식이 이번 변경으로도 깨지지 않았음을 확인.

### Phase 9 — "남은 부분" 정리 패스 (완료 — 클러스터 제외 전부)

사용자가 "남은 부분이 있으면 전부 마무리"를 요청했을 때, 클러스터(가십 프로토콜 설계 결정이 선행돼야 하는 별도 서브시스템 규모 — §4-5)만 명시적으로 제외하기로 합의하고, 그 외에 이 문서가 그동안 "범위 밖"으로 미뤄뒀던 거의 모든 항목을 한 번에 처리한 패스. Phase 0~8 각각의 잔여 항목이 뒤섞여 있어 번호를 하나 더 붙였다. 아래는 다룬 순서 그대로.

- **Bitops + SORT** (`server.rs`): `SETBIT`/`GETBIT`/`BITCOUNT`/`BITPOS`/`BITOP`을 `RObj::String` 위에 직접 구현(`BITFIELD`는 범위 밖 — 부호/비부호 다중폭 서브 언어가 그 자체로 별도 프로젝트 규모). `SORT`는 `BY`/`GET` 외부 키 패턴 없이 숫자/`ALPHA`/`LIMIT`/`STORE`까지 지원. `SORT`는 `STORE` 없이는 읽기 전용이라는 점을 놓치지 않고 `CommandSpec.is_write: false`로 두되, `STORE` 분기에서만 수동으로 `after_write`/tracking 무효화를 호출하도록 설계 — 그렇지 않으면 `SORT` 그 자체가 항상 write로 취급돼 `CLIENT TRACKING`이 "읽기만 한" 소스 키를 잘못 무효화하는 버그가 생길 뻔했다.
- **`SET NX/XX/GET` + `EXPIRE` 계열 `NX/XX/GT/LT`**: `SET`은 네 옵션(`NX`/`XX`/`GET`/`KEEPTTL`+TTL 옵션들) 조합을 전부 지원. `EXPIRE`/`PEXPIRE`/`EXPIREAT`/`PEXPIREAT`에 선택적 트레일링 플래그 추가 — `GT`/`LT`는 "TTL이 아예 없는 키는 무한 TTL로 간주"하는 실제 Redis 규칙(`GT`는 TTL 없는 키에 대해 항상 실패, `LT`는 항상 성공)까지 정확히 반영.
- **키스페이스 알림(`notify.c`)**: `notify-keyspace-events` 플래그 문자열 파싱 + `__keyspace@<db>__:`/`__keyevent@<db>__:` 채널 발행을 Phase 7의 PUBSUB 인프라(`publish_to_channel`) 위에 그대로 얹었다. `SET`/`DEL`/`EXPIRE`/`PERSIST`/능동 만료(`expired` 이벤트, `x` 클래스)/`INCR`/`LPUSH`/`RPUSH`/`LPOP`/`RPOP`/`HSET`/`HDEL`/`SADD`/`SREM`/`ZADD`/`ZREM`/`SETBIT`/`BITOP`/`SORT ... STORE`/`XADD`/`XDEL`/`XTRIM`/`GEOADD`/`PFADD`/`PFMERGE` 호출부에 전부 연결. `t`(stream)/`d`(module)/`m`(key-miss)/`e`(evicted) 클래스는 플래그 문자열 자체는 받아주되 실제로 발화시키는 호출부가 없음(컨슈머 그룹/모듈/키미스 추적/축출이 이 포크에 없으므로) — 명시적으로 문서화.
- **ACL-lite (`AUTH`/`requirepass`)**: 전체 ACL 사용자 테이블 대신 전역 비밀번호 하나(`requirepass`)만 지원(→ 전체 ACL 사용자 테이블은 Phase 22에서 완료). `dispatch()` 최상단에 인증 게이트를 추가해 `requirepass`가 설정돼 있고 아직 인증 안 된 커넥션은 `AUTH`/`HELLO`/`QUIT`/`RESET` 외 모든 커맨드를 `NOAUTH`로 거부. `HELLO ver AUTH user pass`로 프로토콜 협상과 인증을 한 번에 하는 것도 지원.
- **`WAIT`/`FAILOVER`**: `WAIT`는 실제 ack-오프셋 대기가 아니라 "지금 연결된 레플리카 수"를 즉시 반환하는 근사치(이 포크 레플리카가 `REPLCONF ACK`를 아예 안 보내므로 대기할 오프셋 자체가 없음 — 정직하게 문서화). `FAILOVER`는 결과를 흉내내지 않고 "이 포크의 단방향 복제 스트림에는 특정 레플리카에게 원격으로 승격 신호를 보낼 제어 역채널이 없어 지원 불가"라는 명확한 에러로 답하도록 구현 — `REPLICAOF NO ONE`이 여전히 수동 승격의 올바른 도구임을 에러 메시지에 명시.
- **부분 재동기화(`PSYNC`의 `+CONTINUE`) + 복제 백로그**: `Server`에 1MiB 고정 크기 `repl_backlog`(+ `repl_backlog_start_offset`)를 추가하고, `propagate()`가 `pending_propagation`에 쓰는 바이트를 그대로 백로그에도 먹인다. 이 과정에서 기존 버그를 하나 고쳤다 — 기존 `propagate()`는 db 전환 시 주입하는 `SELECT` 프리픽스 바이트를 `master_repl_offset` 계산에서 빼먹고 있었는데(Phase 5부터 있던 과소 계산), 부분 재동기화가 오프셋과 백로그 내용이 바이트 단위로 정확히 일치해야만 성립하므로 이번에 같이 수정. 바이너리 계층(`handle_psync`)은 `PSYNC <replid> <offset>`의 인자를 이제 실제로 파싱해 `Server::try_partial_resync`로 먼저 시도하고, `replid` 불일치나 오프셋이 백로그 보존 구간을 벗어난 경우에만 기존 전체 재동기화로 폴백한다. **Raw 소켓 스크립트로 end-to-end 실제 검증**: 커넥션 A가 `PSYNC ? -1`로 전체 동기화 후 `+FULLRESYNC`의 replid/offset을 포착 → 별도 커넥션이 쓰기 1건 수행 → 커넥션 B가 포착해 둔 replid/offset으로 재접속했을 때 전체 RDB가 아니라 `+CONTINUE` + 놓친 그 쓰기 바이트만 정확히 돌아오는 것을 바이트 단위로 확인.
- **레거시 `EVAL`/`EVALSHA`/`SCRIPT`**: Lua 전용(실제 Redis도 `EVAL`을 Lua로만 하드코딩 — `FUNCTION`만 멀티 엔진). `FUNCTION`의 등록형 콜백과 달리 스크립트 바디를 매번 새로 컴파일하고 `KEYS`/`ARGV`를 전역으로 노출하는 `eval.c`의 관례를 그대로 따름. `EVAL`/`SCRIPT LOAD`가 스크립트를 `SHA1(body)`로 캐싱해 이후 `EVALSHA`가 찾을 수 있도록 함 — 이 SHA1 때문에 `redisx-core`에 `sha1.rs`(교과서적 FIPS 180-1 구현, 알려진 테스트 벡터로 검증)를 신규 추가, Phase 0에서 "EVAL/SCRIPT 전용, 아직 필요 없음"으로 미뤄뒀던 항목을 드디어 사용.
- **HyperLogLog**: `hyperloglog.c`의 dense/sparse 이중 인코딩과 MurmurHash64A 대신, 레지스터당 1바이트(6비트 패킹 생략) + SHA-1 64비트 절삭 해시를 쓰는 단순화된 자체 구현(`hll.rs`). 알고리즘 자체(표준 HyperLogLog 카디널리티 추정 + 소규모 보정)는 그대로 — 실제 10,000개 고유 원소에 991 추정치(0.9% 오차, 이론적 표준오차 범위 내)로 검증.
- **Geo**: `GEOADD`/`GEOPOS`/`GEODIST`/`GEOSEARCH`(`FROMLONLAT`+`BYRADIUS`/`BYBOX`+`ASC`/`DESC`+`COUNT`+`WITHCOORD`/`WITHDIST`)를 `RObj::ZSet` 위에 구현 — 52비트 인터리브 지오해시를 점수로 저장하는 설계까지 실제 Redis와 동일. 팔레르모-카타니아 거리 예제로 실제 Redis 문서가 공개한 수치(≈166.27km)와 일치 확인. `GEOSEARCHSTORE`/`FROMMEMBER`/레거시 `GEORADIUS` 계열은 범위 밖.
- **Stream**: 새 `RObj::Stream` 변형 추가. 실제 Redis의 `rax` 리스트팩 트리 대신 `BTreeMap<StreamId, Fields>`(Phase 0의 Fenwick 트리 생략과 같은 결의 단순화) — 정렬된 범위 질의가 공짜로 따라옴. `XADD`/`XLEN`/`XRANGE`/`XREVRANGE`/`XDEL`/`XTRIM`/`XREAD`(논블로킹) 구현, 이 시점엔 컨슈머 그룹·블로킹 `XREAD`·`XINFO`/`XSETID`는 범위 밖이었다(컨슈머 그룹·`XINFO`/`XSETID`는 각각 Phase 16/13에서 완료 — 블로킹 `XREAD`만 아직 미착수, §7 "다음 액션" 참고). RDB에는 실제 Redis의 `RDB_TYPE_STREAM_LISTPACKS*` 포맷이 아니라 이 포크 전용의 단순 포맷(타입 바이트 200, 실제 Redis와 상호운용 안 됨 — 명시)으로 저장, 마지막 ID 워터마크가 항목 삭제 후에도 살아남아 ID 재사용을 막는 것까지 RDB 왕복 테스트로 확인.
- **`CLIENT TRACKING`의 `BCAST`/`REDIRECT`/`NOLOOP`**: Phase 7에서 기본 모드만 구현했던 것의 나머지. `BCAST`는 읽은 키가 아니라 프리픽스 일치로 무효화(서버에 `client_id -> prefix 목록` 맵 추가), `REDIRECT`는 무효화 푸시를 다른 커넥션으로 돌리고, `NOLOOP`는 자기 자신의 쓰기에 대한 무효화를 건너뜀.
- **`LOLWUT`**: 실제 `lolwut.c`의 "미출시/개발 버전은 한 줄짜리 verbatim 문자열만 반환"하는 `lolwutUnstableCommand` 분기만 포팅 — 회전 사각형 ASCII 아트를 그리는 `lolwut5/6/8Command`는 순수 이스터에그라 포팅 가치가 없다고 판단.
- **`MEMORY USAGE`/`MEMORY DOCTOR`**: §4-2 결정(Rust 기본 allocator 유지)에 따라 jemalloc 통계 없이, 값의 내용 크기를 직접 순회해 근사치를 내는 방식으로 구현. `MEMORY STATS`/`MALLOC-STATS` 등은 범위 밖.
- **`redisx-benchmark`**: `redisx-cli` 크레이트에 두 번째 바이너리로 추가. `-c`/`-n`으로 동시 커넥션·총 요청 수를 받아 스레드별 블로킹 요청-응답 왕복을 수행하고 처리량만 보고 — 실제 `redis-benchmark`의 지연시간 백분위수 히스토그램은 범위 밖. 커맨드를 안 주면 `PING`/`SET`/`GET`/`INCR` 기본 스위트를 돌림.
- **`README.md`/`LICENSE.md`**: 루트에 신규 추가. README는 워크스페이스 구조/빌드(Python feature 포함)/실행/데몬화(nohup, systemd, launchd)/테스트/구현 현황 요약, 이 문서(`25_redisX.md`)를 "설계 근거의 권위 있는 출처"로 명시적으로 가리킴. LICENSE.md는 `Cargo.toml`이 이미 선언한 tri-license(RSALv2/SSPLv1/AGPLv3)를 원본 Redis 프로젝트의 `LICENSE.txt`에서 바이트 단위로 그대로 가져옴(diff로 재확인) — 새 라이선스 조건을 임의로 만든 것이 아니라 이미 선언된 라이선스를 실제로 구현한 것.
- **완료 기준 검증 (종합)**:
  1. 유닛테스트: `redisx-core` 61(+SHA1 2개) + `redisx-net` 33 + `redisx-server` 151(기본)/156(`--features python`) + `redisx-cli` 6, 전부 통과. `cargo clippy --workspace --all-targets`(및 `--features python`) 경고 0개 — 이 패스 전체를 통틀어 단 하나의 clippy 경고도 남기지 않음.
  2. 실제 `redisx-server` 바이너리로 거의 모든 신규 커맨드를 `redis-cli`로 교차검증: `SET NX/XX/GET`, bitops, `SORT`, `EXPIRE` 플래그, `AUTH`/`CONFIG SET requirepass`, `WAIT`, `EVAL`/`SCRIPT LOAD`/`EVALSHA`(SHA1 해시가 실제로 일치), `PFADD`/`PFCOUNT`(1000개 중 991 추정), `GEOADD`/`GEOPOS`/`GEODIST`/`GEOSEARCH`, `XADD`/`XLEN`/`XRANGE`, `LOLWUT`, `MEMORY USAGE`, `FAILOVER`(의도된 에러 메시지).
  3. Python 소켓 스크립트로 부분 재동기화(`+CONTINUE`)를 프로토콜 바이트 레벨에서 검증(위 설명 참고).
  4. `redisx-benchmark`를 실제 `redisx-server`에 돌려 기본 스위트 처리량 출력 확인 + `LPUSH` 단일 커맨드 모드로 1000개 요청이 전부 실제로 반영됐는지(`LLEN` 비교) 확인.
  5. `--features python` 빌드·테스트가 이번 패스의 모든 변경 이후에도 여전히 `DYLD_LIBRARY_PATH` 없이 통과함을 재확인(Phase B의 rpath 수정이 이번 패스 전체에 걸쳐 깨지지 않았음을 보증).

### Phase 10 — "Phase 3 갭 채우기" 패스 (완료)

"아직 안된 부분이 있는지 체크해줘"라는 감사 요청에서, Phase 9가 "거의 전부"를 처리했다고 자평했음에도 여전히 남아 있던 버그 2건과 Phase 3(데이터 타입) 범위에 해당하는 표준 커맨드 다수의 누락을 발견했다. 사용자가 "phase3에서 개발 또는 convert되지 않은 상황이라면 정리해서 다 채워넣어줘"로 범위를 **Phase 3 데이터 타입(제네릭 키 커맨드 포함)으로 명시적으로 한정**해 승인한 패스. `WATCH`/`UNWATCH`/`INFO`/`TIME`/`LASTSAVE`/`BGSAVE`/`SHUTDOWN`/`DUMP`/`RESTORE`/`COMMAND`는 같은 감사에서 함께 발견됐지만 Phase 2/4/운영 영역이라 **이번 패스에서 의도적으로 제외**했다(조용히 누락시킨 게 아니라 범위 판단으로 기록).

- **버그 수정 — `FCALL_RO`가 쓰기를 막지 못함**: `FCALL_RO`로 호출한 함수 안에서 `redis.call()`로 쓰기 커맨드를 실행해도 그냥 통과되고 있었다(이름만 `_RO`였지 실제로는 아무 것도 강제하지 않음). `script.rs`에 `CURRENT_READONLY: Cell<bool>` 스레드 로컬을 추가하고 `push_context`/`pop_context`(및 `call_function`/`call_lua_function`/`call_python_function`)의 시그니처에 `read_only: bool`을 끼워 넣어, `redis_call_impl`이 호출 직전에 `is_write_command(name)`을 검사해 거부하도록 고쳤다. `EVAL`/`EVALSHA`에는 `_RO` 대응이 없는 실제 Redis와 동일하게 항상 `false`로 고정.
- **버그 수정 — `RESET`이 `bypasses_queueing` 목록에만 있고 실제 핸들러가 없었음**: `cmd_reset`을 신규 구현 — MULTI 큐/구독/CLIENT TRACKING/인증 상태/선택된 DB 인덱스를 전부 초기화하고 `+RESET`을 반환.
- **제네릭 키 커맨드 일괄 추가** (`server.rs`): `TOUCH`/`UNLINK`/`KEYS`/`RANDOMKEY`/`RENAME`/`RENAMENX`/`COPY`/`MOVE`/`SCAN`/`HSCAN`/`SSCAN`/`ZSCAN`/`OBJECT ENCODING|REFCOUNT|IDLETIME|FREQ`.
  - `COPY`는 `RObj`가 `Clone`을 derive하지 않으므로, `rdb.rs`의 기존 private `save_value`/`Reader`/`load_value`를 그대로 재사용하는 `clone_value()`(RDB 인코딩을 통한 왕복 딥카피)로 구현 — `redisx-core`의 `ListPack`/`RDict`/`IntSet`에 손대지 않고 끝남.
  - `OBJECT ENCODING`은 `object.rs`에 신규 `RObj::encoding_name()`을 추가해 실제 Redis가 보고하는 문자열(`int`/`embstr`/`raw`, `listpack`/`hashtable`, `intset`/`hashtable`, `listpack`/`skiplist`, `stream`)을 그대로 재현. `REFCOUNT`는 `1` 고정, `IDLETIME`은 `0` 고정(LRU 미구현), `FREQ`는 LFU 미구현 에러로 응답.
  - `RANDOMKEY`/추후 `SRANDMEMBER`/`SPOP`/`HRANDFIELD`/`ZRANDMEMBER`가 공유하는 `object::pseudo_random_index()`를 신규 추가(`std::collections::hash_map::RandomState` 기반 경량 비암호화 난수 — `generate_replid()`와 동일한 전례).
  - **`SCAN`은 Phase 0의 `KvStore::scan`(역이진 커서)을 그대로 재사용**해 진짜 증분 스캔으로 구현(한 번의 호출이 버킷 하나만 방문, `COUNT`는 실제 Redis와 동일하게 어드바이저리일 뿐 강제 상한이 아님). 반면 `HSCAN`/`SSCAN`/`ZSCAN`은 `HashObj`/`SetObj`/`ZSetObj`에 커서 재개 가능한 내부 스캔이 없어서, **한 번의 호출로 일치하는 전부를 반환하고 커서는 항상 `0`**으로 단순화했다 — 프로토콜 계약(완전성 보장) 자체는 어기지 않는 합법적인 단순화이나 "진짜 증분"은 아님을 코드 주석에 명시.
- **String 커맨드 보강**: `INCRBY`/`DECR`/`DECRBY`/`INCRBYFLOAT`(기존 `cmd_incr`를 공용 `incr_by_i64` 헬퍼로 리팩터링해 재사용), `APPEND`/`STRLEN`/`GETRANGE`/`SETRANGE`, `MGET`/`MSET`/`MSETNX`, `GETDEL`/`GETEX`. 새 `object.rs`/`*.rs` 타입 메서드는 불필요 — 전부 `RObj::String(Vec<u8>)` 위에서 직접 동작.
- **List 커맨드 보강**: `LSET`/`LINSERT`/`LREM`/`LTRIM`/`LPOS`/`LMOVE`/`RPOPLPUSH`. `list.rs`에 `set_at`/`insert_pivot`/`remove_value`/`trim`/`positions` 신규 메서드 추가(전부 `ListPack`의 기존 `remove`/`insert_str` 원자 연산을 조합). `LPOS`는 `RANK`/`COUNT`/`MAXLEN` 전부 지원. `LMOVE`/`RPOPLPUSH`는 source==destination(회전) 케이스까지 공용 `do_lmove` 헬퍼로 올바르게 처리.
- **Hash 커맨드 보강**: `HSETNX`/`HMGET`/`HKEYS`/`HVALS`/`HINCRBY`/`HINCRBYFLOAT`/`HRANDFIELD`. `hash.rs`에 `incr_by`/`incr_by_float` 신규 메서드 추가(`incr_by_float`는 포맷터 클로저를 인자로 받아 `hash.rs`가 `server.rs`의 `fmt_score`에 의존하지 않도록 역전).
- **Set 커맨드 보강**: `SMISMEMBER`/`SPOP`/`SRANDMEMBER`/`SMOVE`/`SINTER`/`SUNION`/`SDIFF`(+`STORE` 변형). `set.rs`에 `pop_random`/`random_members` 신규 메서드 추가(둘 다 호출자가 넘기는 난수 클로저를 받는 형태 — `set.rs`가 `server.rs`의 `object::pseudo_random_index`를 직접 참조하지 않도록 분리). `SINTER`/`SUNION`/`SDIFF`는 `members()`를 `HashSet`으로 모아 집합 연산 — 별도 타입 메서드 불필요.
- **ZSet 커맨드 보강**: `ZREVRANGE`/`ZREVRANK`/`ZCOUNT`/`ZRANGEBYSCORE`/`ZREVRANGEBYSCORE`(`LIMIT` 포함)/`ZINCRBY`/`ZPOPMIN`/`ZPOPMAX`/`ZMSCORE`/`ZRANDMEMBER`/`ZUNIONSTORE`/`ZINTERSTORE`/`ZDIFFSTORE`. `zset.rs`에 `range_by_score`/`incr_by`/`pop`/`random_members` 신규 메서드 추가. **`ZUNIONSTORE`/`ZINTERSTORE`/`ZDIFFSTORE`는 `WEIGHTS`/`AGGREGATE` 옵션 없이 기본형(합산/첫 세트 점수 유지)만 지원**(명시적 단순화 — 옵션이 오면 명확한 에러로 거부). `ZRANGEBYLEX`는 활용도가 낮다고 판단해 이번에도 범위 밖으로 남김(→ Phase 19에서 완료).
- **완료 기준 검증**:
  1. 유닛테스트: `redisx-server` 기본 빌드 197개(`--features python` 202개), 신규 타입 메서드(`list.rs`/`hash.rs`/`set.rs`/`zset.rs`)와 신규 커맨드(`server.rs`) 양쪽에 전부 전용 테스트 추가. `cargo clippy --all-targets`(및 `--features python`) 경고 0개.
  2. 실제 `redisx-server` 바이너리(`redis-cli`)로 제네릭 키(`KEYS`/`RENAME`/`COPY`/`SCAN`의 커서 증분 동작)/String(`APPEND`/`GETRANGE`/`SETRANGE`/`GETEX` TTL 설정·해제)/List(`LINSERT`/`LPOS`/`LMOVE`)/Hash(`HINCRBY`/`HRANDFIELD`/`HMGET`)/Set(`SINTER`/`SUNIONSTORE`/`SPOP`)/ZSet(`ZRANGEBYSCORE`/`ZREVRANGE`/`ZINCRBY`/`ZUNIONSTORE`, 자기 자신과의 합집합이 점수를 두 배로 합산하는 것까지)를 전부 교차검증.

### Phase 11 — `sha256` 이관 + ACL 비밀번호 비교를 실제 해시 비교로 교정 (완료)

Phase 0에서 "사용 시점(Phase 2/6)으로 이관"이라고 미뤄뒀던 `sha1`/`sha256` 중, `sha1`은 Phase 9에서 `EVALSHA`/`SCRIPT` 캐싱에 이미 포팅됐지만 `sha256`은 그때까지도 미착수 상태였다(Phase 9 ACL-lite가 `requirepass`를 평문 비교 한 줄로 구현하고 넘어갔기 때문). "sha1, sha256을 이관해줘"라는 명시적 요청으로 이 마지막 한 조각을 마저 포팅했다.

- **`redisx-core::sha256`** (신규): `redis_src/src/sha256.c`를 포팅한 교과서적 FIPS 180-4 구현 — Phase 0이 원래 적어뒀던 "검증된 `sha2` 크레이트로 추가"(§3 Phase 0 표) 대신, Phase 9에서 `sha1`을 포팅할 때 이미 깨진 그 원칙(외부 크레이트 대신 자체 구현 + 알려진 테스트 벡터로 검증)을 그대로 따랐다 — `sha1.rs`와 동일한 모양의 모듈(스트리밍 `SHA256_CTX` 없이 한 번에 한 버퍼를 해싱, `sha256`/`sha256_hex` 두 함수)로 일관성을 유지하는 편이, 같은 일을 하는 암호화 해시 하나는 자체 구현·하나는 외부 크레이트로 쪼개는 것보다 낫다고 판단. NIST 표준 테스트 벡터 3종(`""`, `"abc"`, 56바이트 다중 블록 메시지)으로 검증.
- **버그 교정 — `requirepass`가 평문 비교였던 것을 실제 Redis와 동일한 해시 비교로 교정**: Phase 9 ACL-lite 구현 당시엔 `sha256`이 없어 `password.as_slice() == configured.as_bytes()`로 평문째 비교하고 있었다. 실제 Redis는 Redis 6+부터 `requirepass`를 설정하면 내부적으로 `ACLUpdateDefaultUserPassword` → `ACLHashPassword`를 거쳐 SHA-256 해시로 저장하고, `AUTH`는 시도한 비밀번호를 똑같이 해싱한 뒤 `time_independent_strcmp`로 비교한다(`acl.c`) — 평문 비교가 아니다. `cmd_auth`를 고쳐 `configured`/시도한 비밀번호 양쪽을 `sha256_hex`로 해싱한 뒤 비교하도록 했다. 이 비교에 쓰는 `time_independent_strcmp`(diff를 OR로 누적, 조기 종료 없음)도 `acl.c`의 것을 그대로 `server.rs`에 포팅 — 두 인자가 항상 64자 고정 길이 해시 문자열이라는 전제까지 동일(가변 길이 평문을 이 방식으로 비교하는 것은 애초에 의미가 없어, 실제 Redis도 해시로 바꾼 뒤에만 이 비교를 쓴다).
- **완료 기준 검증**:
  1. 유닛테스트: `redisx-core`에 `sha256` 테스트 2개(기존 61 → 63), `redisx-server`에 `time_independent_strcmp` 전용 테스트 + "비밀번호의 SHA-256 해시 자체로는 인증되지 않는다"(평문 비교로 되돌아가지 않았음을 증명하는 회귀 테스트) 2개 추가(기본 빌드 197 → 199, `--features python` 202 → 204). `cargo clippy --workspace --all-targets`(및 `--features python`) 경고 0개.
  2. 실제 `redisx-server` + `redis-cli`로 `CONFIG SET requirepass secret` 후: 인증 전 `NOAUTH`, 틀린 비밀번호 `WRONGPASS`, **`secret`의 SHA-256 16진 다이제스트 자체를 비밀번호로 시도해도 `WRONGPASS`**(평문 비교였다면 이 케이스가 통과했을 것 — 해시 비교로 바뀌었음을 실제 바이너리로 증명), 올바른 비밀번호로는 `AUTH`/`-a` 양쪽 다 정상 인증됨을 확인.

### Phase 12 — `ziplist`/`zipmap` 이관 (완료 — 디코드 전용 레거시 RDB 로더)

Phase 0에서 "Phase 4로 이관"이라고 분류해뒀지만 Phase 4가 끝날 때(§3 Phase 4 섹션)까지도 "여전히 범위 밖"으로 명시적으로 미뤄져 있던 마지막 항목. "ziplist, zipmap 포팅해줘"라는 명시적 요청으로 마저 포팅했다 — 이로써 Phase 0 표에 적힌 모든 이관/재분류 대상이 완료 또는 명시적 불필요 판정으로 닫혔다.

- **`redisx-core::ziplist`/`redisx-core::zipmap`** (신규, 둘 다 **디코드 전용**): `ziplist.c`/`zipmap.c`를 포팅 — 이 포크는 둘 다 절대 쓰지 않고(실제 Redis도 Redis 7부터는 listpack만 쓴다), 오래된 RDB 덤프를 읽을 때만 필요하기 때문에 쓰기 경로 자체를 만들지 않았다. 둘 다 `entries()` 하나만 공개해 블롭을 순서대로 디코딩한 값들을 반환한다.
  - `ziplist::entries`: `<zlbytes><zltail><zllen>` 10바이트 헤더 이후를 순회하며 `<prevlen><encoding+rawlen><data>` 엔트리를 하나씩 디코딩. 문자열 3종 인코딩(6/14비트 리틀→빅엔디안 혼재 주의, 32비트)과 정수 5종(8/16/24/32/64비트, 24비트는 `zipLoadInteger`의 "상위 3바이트에 넣고 8비트 산술 시프트로 부호 확장" 트릭까지 그대로 포팅) + 4비트 즉시값(1~13 인코딩 → 0~12 값)을 전부 포팅. `prevlen` 자체의 값은 역방향 순회에만 쓰이므로, 정방향 전용 리더는 1바이트/5바이트 중 어느 쪽인지만 보고 건너뛴다.
  - `zipmap::entries`: `<zmlen:u8><key><value>...<0xFF>` — `zmlen`은 254 이상이면 신뢰할 수 없어(`zipmapLen`의 자체 한계와 동일) 항상 `0xFF` 종료 마커까지 순회. 값 뒤의 `free` 패딩 바이트(제자리 업데이트를 위해 남겨둔 여유 공간)까지 정확히 건너뛴다. 4바이트 "빅렌" 인코딩은 C 소스 주석이 명시한 대로 **호스트 바이트 오더**로 저장되는 레거시 포맷 자체의 이식성 결함인데, 현실의 zipmap 시대 RDB는 전부 리틀엔디안 호스트에서 생성됐으므로 리틀엔디안으로 읽는다(이 포트가 만든 결함이 아니라 원본 포맷 자체의 특성이라는 점을 모듈 문서에 명시).
  - 둘 다 "잘려나간/손상된 바이트"에 패닉 대신 `None`을 반환 — `ListPack::from_bytes`/`IntSet::from_bytes`와 같은, 신뢰할 수 없는 온디스크 바이트에 대한 이 포트의 일관된 태도.
- **`rdb.rs` 연동**: `RDB_TYPE_LIST_ZIPLIST`/`HASH_ZIPLIST`/`ZSET_ZIPLIST`/`HASH_ZIPMAP`(오프코드 10/13/12/9) 네 개의 로드 분기를 추가. ziplist/zipmap은 이 포크의 네이티브 `ListPack`과 완전히 다른 바이트 포맷이라(`HASH_LISTPACK`/`ZSET_LISTPACK`처럼 디코딩한 바이트를 그대로 `ListPack::from_bytes`로 감쌀 수 없음), 디코딩한 필드/값(또는 멤버/점수) 쌍을 새 `ListPack`에 다시 `push_str`해 네이티브 리스트팩으로 재인코딩한 뒤 `HashObj::Listpack`/`ZSetObj::Listpack`으로 감싼다. `ZSET_ZIPLIST`는 `ZSET_LISTPACK`과 동일하게 "디스크의 ziplist가 이미 멤버/점수 정렬 순서로 저장돼 있다"(실제 Redis가 항상 그렇게 쓴다)는 전제에 의존한다.
- **완료 기준 검증**:
  1. 유닛테스트: `redisx-core`에 `ziplist`(문자열 3종+정수 5종+즉시값 전부, 손상된 버퍼 거부 포함) 6개 + `zipmap`(`zipmap.c` 주석의 실제 예제 바이트 포함) 5개 신규(기존 63 → 74). `redisx-server`의 `rdb.rs`에 `load_value` 레벨 테스트 5개(리스트/해시/zset ziplist, 홀수 개수 거부, 해시 zipmap) + 손수 조립한 완전한 `REDIS0014` 파일(헤더+`SELECTDB`+레거시 오프코드+`EOF`+진짜 CRC64 트레일러)을 `load_value`가 아니라 **실제 `load()` 오프코드 디스패치 루프**로 통과시키는 통합 테스트 1개, 총 6개 신규(기본 빌드 199 → 205, `--features python` 204 → 210). `cargo clippy --workspace --all-targets`(및 `--features python`) 경고 0개.
  2. **실제 바이너리 교차검증**: 실제 레거시 RDB를 생성해줄 구버전 Redis 바이너리가 설치돼 있지 않아(현재 환경의 실제 `redis-server`는 8.6.0과 이 포크의 개발판, 둘 다 Redis 7+라 ziplist/zipmap을 더 이상 쓰지 않음), `zipmap.c`/`ziplist.c` 원본 소스 주석에 박혀 있는 실제 바이트 예제를 그대로 쓴 손수 조립 `REDIS0014` 파일(오프코드 9의 해시 + 오프코드 10의 리스트 + 오프코드 12의 zset, 전부 진짜 CRC64 포함)을 실제 `redisx-server` 바이너리가 가리키는 디렉터리에 놓고 기동 → `redis-cli`로 `HGETALL`/`LRANGE`/`ZRANGE WITHSCORES`가 정확한 값을 반환하고 `OBJECT ENCODING`이 셋 다 `listpack`(재인코딩 완료)으로 보고되는 것까지 확인. 검증용 스크래치 바이너리(`examples/make_legacy_rdb.rs`)는 확인 후 삭제.

### Phase 13 — "Phase 상세 전수 감사" 패스 (완료 — 자잘한 누락 커맨드 일괄 보강)

"3. Phase 상세를 보니 아직 안된 부분들이 있는데, 불필요하다고 판단한 거 말고 남아 있는 것들은 구현이 되었으면 해"라는 요청으로 이 문서 §3 전체를 다시 감사해, "불필요/대체 결정"이 아니라 "그냥 아직 안 만든 것"으로 분류되는 항목을 전부 골라낸 패스. 규모가 작지 않은 항목(블로킹 커맨드, Stream 컨슈머 그룹, TLS)은 사용자가 "전부 다"로 확정해 Phase 14 이후로 계속 이어간다 — 이 Phase는 그보다 먼저 끝난, 기존 코드 재사용만으로 끝나는 작은 항목들의 모음이다.

- **`WATCH`/`UNWATCH`**: Phase 2에서 "다음 과제로 이연"해둔 뒤 한 번도 집어가지 않았던 낙관적 잠금. **설계 결정 — 서버가 다른 클라이언트의 상태를 직접 건드릴 수 없는 이 포트의 구조적 제약**(`pending_pushes`/`tracking_table`과 같은 이유)을 그대로 따라, 실제 Redis처럼 "쓰기가 들어오는 즉시 다른 클라이언트를 더티 처리"하는 대신 `Server::watched_key_versions: HashMap<(db,key), u64>`(쓰기마다 증가하는 전역 카운터)과 `ClientState::watching: Vec<(db,key,그때버전)>`(WATCH 시점의 스냅샷)을 두고 **EXEC 시점에 지연 비교**하는 방식을 택했다 — 결과는 동일(워치한 키가 그 사이 바뀌었으면 EXEC는 `EXECABORT`가 아니라 `*-1`/nil 배열을 반환)하면서 아키텍처를 깨지 않는다. 버전 카운터는 일반 쓰기 커맨드(`tracked_key` 휴리스틱 재사용 — `CLIENT TRACKING`과 같은 한계: 다중 키 커맨드는 `argv[1]`만 더티 처리됨), 능동 만료 스윕, `FLUSHALL`/`FLUSHDB`(신규 커맨드, 아래 참고) 세 경로 모두에서 올바르게 증가한다. `EXEC`/`DISCARD`/`RESET`은 전부 `watching`을 비운다(실제 Redis의 `unwatchAllKeys` 호출 지점과 동일).
- **`FLUSHDB`**: `FLUSHALL`은 있었지만 `FLUSHDB`가 없었다 — 단순 누락. 현재 선택된 db만 비우고, `WATCH` 버전 카운터도 그 db에 속한 키만 증가시킨다.
- **`DUMP`/`RESTORE`**: `rdb.rs`의 기존 `[type byte][value]` 내부 인코딩을 그대로 재사용(`dump_value`/`verify_dump_payload`/`restore_value` 신규) — `DUMP`는 그 인코딩에 2바이트 RDB 버전 + 8바이트 CRC64 트레일러만 덧붙이고, `RESTORE`는 역순으로 검증 후 디코드. 새 포맷을 설계한 게 아니라 이미 있던 포맷을 그대로 노출한 것이라 구현 자체는 작았다.
- **`TIME`/`LASTSAVE`/`BGSAVE`/`SHUTDOWN`**: 전부 Phase 10 감사에서 "Phase 3이 아니라서 이번엔 제외"로 명시적으로 미뤄뒀던 항목. `BGSAVE`는 이 포크에 `fork()` 대응물이 없어(그리고 단일 스레드 리액터를 막고 싶지 않아) `SAVE`와 동일하게 동기 저장 후 `Background saving started`를 응답하는 문서화된 근사치(`WAIT`와 같은 정신). `SHUTDOWN [NOSAVE]`는 핸들러 안에서 바로 `std::process::exit(0)`을 호출 — 응답을 아예 안 보내는 것까지 실제 Redis와 동일한 동작(이벤트 루프 계층의 개입이 필요 없는, `PSYNC`/`REPLICAOF`와는 다른 종류의 "일반 커맨드 함수 시그니처를 벗어나는" 케이스).
- **`COMMAND [COUNT|LIST|INFO|DOCS|GETKEYS]`**: 커맨드 디스패치가 이미 쓰는 `COMMANDS` 테이블을 그대로 내부고(introspect)해 절대 어긋날 일이 없게 했다. `first_key`/`last_key`/`step`은 전용 key-spec 테이블이 없어 `tracked_key`와 같은 "`argv[1]`이 있으면 1/1/1" 휴리스틱으로 근사. `DOCS`는 설명 텍스트 테이블이 없어 빈 맵만 반환(존재 여부 확인 용도로는 충분).
- **`INFO`**: 실제로 추적하는 상태만으로 server/clients/memory/persistence/stats/replication/keyspace 7개 섹션을 구성 — `cpu`/`commandstats`/`latencystats`/`cluster`처럼 이 포크에 근거 데이터가 아예 없는 섹션은 지어내지 않고 생략. `connected_clients`(신규: 바이너리 계층이 `connected_replicas`와 같은 패턴으로 채움), `total_commands_processed`/`rdb_changes_since_last_save`(신규 카운터, `run_command`/`save_rdb_to_disk`에서 증감)까지 전부 실제로 갱신되는 값.
- **`ZUNIONSTORE`/`ZINTERSTORE`의 `WEIGHTS`/`AGGREGATE`**: Phase 10에서 "옵션이 오면 에러로 거부"했던 단순화를 실제로 채워 넣었다(`ZDIFFSTORE`는 실제 Redis 문법 자체에 이 옵션이 없어 여전히 거부). 겸사겸사 `STORE`-less 형제들(`ZUNION`/`ZINTER`/`ZDIFF`/`ZINTERCARD`)도 같은 연산 로직(`compute_zset_op` 공용화)을 재사용해 신규 추가 — 이들은 Phase 10에서 언급조차 되지 않았던 순수 누락.
- **`GEOSEARCH`의 `FROMMEMBER` + `GEOSEARCHSTORE`**: `geo.rs` Phase 9 당시 "추가 후속 작업, 블로커 아님"으로 명시해뒀던 둘을 채움. `GEOSEARCHSTORE`는 `STOREDIST` 없이는 원본 geohash 점수를, 있으면 계산된 거리를 점수로 저장 — `georadiusGeneric`의 `storedist` 분기와 동일.
- **`XSETID`/`XINFO STREAM`/`XINFO GROUPS`**: `StreamObj::set_last_id` 신규 메서드로 워터마크를 강제 이동(기본값 기준 뒤로 가는 건 거부, `FORCE` 없음). `XINFO STREAM`은 `entries-added`/`max-deleted-entry-id`를 누적 카운터 없이 "현재 길이"/"`0-0`"으로 근사하는 걸 명시하고, `XINFO GROUPS`는 이 시점엔 컨슈머 그룹 자체가 없어 항상 빈 배열이었다(Phase 16에서 실제 그룹 상태 보고로 교체).
- **완료 기준 검증**:
  1. 유닛테스트: 이 패스 전체에서 `redisx-server`에 약 30개 신규 추가(`WATCH`/`FLUSHDB` 7, `TIME`/`LASTSAVE`/`BGSAVE`/`COMMAND` 6, `DUMP`/`RESTORE` 5, `INFO` 4, `ZUNION`류 3, `GEOSEARCH`류 2, `XSETID`/`XINFO` 2 등). `cargo clippy --workspace --all-targets`(및 `--features python`) 경고 0개를 매 체크포인트마다 재확인.
  2. 실제 `redisx-server` + `redis-cli`로 전 항목 교차검증: `WATCH`는 Python 소켓 스크립트로 **완전히 별도인 두 번째 커넥션**이 끼어드는 실제 경합 시나리오까지(`EXEC`가 nil을 반환하는 것을 바이트 단위로 확인), `DUMP`/`RESTORE`는 리스트를 실제로 덤프·복원해 `LRANGE`로 재확인, `SHUTDOWN`은 실행 후 프로세스가 실제로 종료되고 재기동 시 저장된 데이터가 복구되는 것까지, `GEOSEARCHSTORE`/`ZUNIONSTORE WEIGHTS` 등은 계산값을 직접 대조.

### Phase 14 — 블로킹 커맨드 (완료 — `BLPOP`/`BRPOP`/`BLMOVE`/`BRPOPLPUSH`/`BZPOPMIN`/`BZPOPMAX`)

Phase 13 감사가 "서브시스템 규모 설계가 필요하다"며 미뤄뒀던 세 항목 중 첫 번째. 핵심 질문은 "이 포트의 단일 스레드 리액터(`ae.rs`, Phase 1의 `mio` 채택 결정)에서 '한 커맨드가 응답을 받지 못한 채 다른 클라이언트의 처리를 막지 않고 대기한다'를 어떻게 구현하는가"였다.

- **핵심 설계 — `Server`는 여전히 소켓을 모른다, 이번에도**: `pending_pushes`/`watched_key_versions`와 같은 제약(서버가 *다른* 커넥션의 상태를 직접 건드릴 수 없음)이 그대로 적용된다. 그래서 블로킹 커맨드는 `fn(&mut Server, &mut ClientState, argv) -> Reply`로 표현하지 않고, `PSYNC`/`REPLICAOF`처럼 바이너리 계층이 커맨드 이름으로 먼저 가로채 `Server::try_blocking_command`를 호출하는 세 번째 사례로 추가했다. 즉시 처리 가능하면 평범한 `Reply`를, 아니면 `BlockingOutcome::Blocked`를 반환해 "이 클라이언트에게는 지금 응답을 쓰지 말라"는 신호를 바이너리 계층에 전달한다.
- **설계 결정 — 블로킹 커맨드는 전부 "합성된 비블로킹 커맨드를 `run_command`로 재실행"하는 식으로 구현**: `BLPOP key1 key2 0`이 즉시 처리 가능하면 내부적으로 `LPOP key1`(또는 `key2`)을 `run_command`로 직접 실행하고 그 결과를 `[key, value]` 모양으로 포장한다. `BLMOVE`/`BRPOPLPUSH`도 각각 `LMOVE`/`RPOPLPUSH`를 재사용. 이 덕분에 전파/AOF/`WATCH` 버전 증가/`CLIENT TRACKING` 무효화가 전부 그 내부 커맨드의 `run_command` 경로에서 공짜로 따라온다 — `FCALL`이 `is_write`로 표시되지 않는 것과 동일한 "effects replication" 원리이며, `COMMANDS` 테이블에 등록된 블로킹 커맨드 자신의 핸들러(`cmd_blpop_or_brpop_non_blocking` 등, 아래 참고)도 같은 이유로 `is_write: false`다.
- **설계 결정 — FIFO 공정성은 서버 쪽 역색인으로**: `Server::blocking_keys: HashMap<(db,key), Vec<client_id>>`에 도착 순서대로 쌓아두고, 어떤 키에 쓰기가 일어나면(`run_command`의 `tracked_key` 훅에서 `maybe_unblock_waiters` 호출) 가장 오래 기다린 클라이언트부터 순서대로 깨운다 — 나중에 등록된 클라이언트가 먼저 원하는 데이터가 생겼다고 새치기하지 않는다(실제 Redis의 `ready_keys` FIFO 보장과 동일). **버그 발견/수정**: 처음 구현에서는 "재시도 성공 → 등록 해제"의 순서였는데, `BRPOPLPUSH`의 재시도 자체가 내부적으로 `RPOPLPUSH` 쓰기를 실행하면서 같은 `maybe_unblock_waiters`를 재귀적으로 다시 태우고, 그 재귀 호출이 아직 등록 해제되지 않은 같은 클라이언트를 또 찾아내 **이중으로 깨우는** 버그를 유닛테스트로 잡았다 — "재시도 *전에* 먼저 등록 해제"로 순서를 뒤집어 고쳤다(재귀 호출이 더 이상 이 클라이언트를 찾지 못하게). **버그 발견/수정 2건째**: 각 `attempt_blocking_*` 함수가 처음엔 "데이터 없음"과 "키가 있지만 타입이 다름(WRONGTYPE)"을 구분하지 않고 둘 다 "계속 대기"로 처리하고 있었다 — 유닛테스트로 발견, 타입이 다르면 즉시 에러를 반환하도록 수정.
- **`MULTI`/`EXEC`·스크립트 안에서는 절대 블로킹하지 않음**: 실제 Redis의 규칙을 그대로 따라, `COMMANDS` 테이블에 각 블로킹 커맨드의 "비블로킹 버전" 핸들러(`cmd_blpop_or_brpop_non_blocking` 등)를 등록했다 — `MULTI`/`EXEC`로 큐잉된 커맨드와 `redis.call()`로 스크립트가 호출하는 커맨드는 전부 `dispatch`/`execute_single` → `run_command` 경로를 타므로 이 등록된 핸들러로 가고, 바이너리 계층의 가로채기(`try_blocking_command`)는 최상위 클라이언트가 직접 보낸 커맨드에서만 일어난다 — 같은 로직을 공유하되 "즉시 안 되면 포기하고 타임아웃 응답 반환" 한 줄만 다르다.
- **바이너리 계층(`src/bin/redisx-server.rs`) 구현**: `Conn`에 `pending_commands: VecDeque<Vec<Vec<u8>>>` 추가 — 한 번의 읽기에서 여러 커맨드가 파싱됐는데 그중 하나가 블로킹되면, 그 뒤에 이미 파싱된 커맨드를 잃어버리지 않고 큐에 남겨뒀다가 깨어난 뒤 이어서 처리한다(파이프라이닝 드물게 겹치는 경우의 정확성). 블로킹되는 순간 `ev.delete_readable(fd)`로 그 fd의 읽기 관심을 해제해(실제로 뭔가를 더 보낸 클라이언트가 있어도 커널 소켓 버퍼에 쌓일 뿐 바쁜 루프를 돌지 않음) 깨어날 때 `register_readable`로 복구한다. `Server::take_unblocked()`(기존 `take_pending_pushes`와 동일한 드레인 패턴)를 매 커맨드 처리 직후와, 100ms 주기 타임 이벤트(`ae.rs`의 `create_time_event`, 실제 Redis의 `handleBlockedClientsTimeouts`와 같은 크론 방식 — 블로킹 클라이언트 하나당 타이머를 만들지 않음)에서 호출해 깨어난/타임아웃된 클라이언트에게 응답을 전달한다.
- **AOF/복제 로그에 찍히는 것은 합성된 비블로킹 커맨드**: `BLPOP`이 만족되면 복제 스트림/AOF에는 `LPOP`이 찍힌다(블로킹 의미론은 레플리카에게 무의미하므로) — 실제 Redis도 동일.
- **문서화된 단순화**: (1) 합성 커맨드의 `ClientState::peer`는 `"internal"`로 찍혀 AOF 줄의 피어 주소가 실제 블로킹 클라이언트의 것이 아님. (2) 블로킹 중인 키가 다른 타입으로 바뀌는 어떤 쓰기든 그 즉시 WRONGTYPE로 깨운다 — 실제 Redis는 그런 경우에도 계속 대기시킨다(타입에 맞는 push 연산만 깨우는 신호를 보냄). 둘 다 희귀한 엣지 케이스이고, 전자는 영향이 미미하며 후자는 오히려 더 정직한 동작이라고 판단해 그대로 뒀다.
- **완료 기준 검증**:
  1. 유닛테스트 16개 신규(서버 상태만으로 직접 `try_blocking_command`/`take_unblocked`/`check_blocking_timeouts` 호출 — FIFO 순서, WRONGTYPE 즉시 에러, 타임아웃 응답 모양(`BLMOVE`/`BRPOPLPUSH`는 null bulk, 나머지는 null array), 연결 종료 시 등록 해제, `MULTI`/`EXEC` 안에서 안 블로킹하는 것까지). `cargo clippy --workspace --all-targets`(및 `--features python`) 경고 0개.
  2. **실제 바이너리 + raw 소켓 스크립트로 5가지 시나리오 전부 교차검증**: (a) 커넥션 A가 `BLPOP`으로 블로킹 → 별도 커넥션 B가 `RPUSH` → A가 정확한 값으로 깨어남, (b) 응답 후 B가 평범하게 계속 쓸 수 있음, (c) 타임아웃이 정확히 지정한 시간만큼(±허용오차) 뒤에 null로 응답, (d) **파이프라이닝**: 같은 TCP 쓰기에 `BLPOP`과 `PING`을 연달아 보내고, `BLPOP`이 깨어난 뒤 `PING`의 `PONG` 응답이 그제서야 순서대로 도착하는 것, (e) `BZPOPMIN`도 동일하게 동작.

### Phase 15 — 설정 파일 + 독립 설치 스크립트 (완료)

Phase 14 작업 도중 사용자가 끼어들어 요청한 운영 편의 기능. "compile 후 cargo 없이 독립적으로 실행", "config가 default로 생성", "가능하면 `/usr/bin/redisX`에 설치", "설정 파일 경로 안내 메시지", "`.zshrc`/`.shrc`에 경로 추가 안내 메시지" 다섯 가지를 그대로 구현했다.

- **`ConfigStore::load_conf_file`/`write_conf_file`** (`config.rs` 신규): `key value` 한 줄씩, `#` 주석과 빈 줄 무시하는 단순 포맷. `load_conf_file`은 `ConfigStore::new()`의 기본값 위에 파일 내용을 덮어써서(파일에 없는 키는 컴파일된 기본값 유지), 실제 Redis의 "config 파일은 바꾸고 싶은 키만 적으면 된다" 관례를 그대로 따른다. `write_conf_file`은 내부 전용 `port`의 `"0"` 센티넬(바이너리가 실제로 바인딩한 뒤에야 채워지는 값)을 사람이 보는 파일에는 실제 기본값 `6379`로 바꿔 쓴다.
- **바이너리 쪽 디스패치**: `redisx-server [config-file]`(기본 경로는 `default_config_path()` — 실행 파일 자신의 디렉터리에 있는 `redisx.conf`, CWD가 아님: `/usr/bin/redisX/redisx-server`로 설치하면 어디서 실행하든 `/usr/bin/redisX/redisx.conf`를 기본으로 찾는다는 뜻) 또는 기존 스크립트/테스트/문서가 쓰던 레거시 `redisx-server <port> [num-databases]` 직접 호출 형태(설정 파일 없음) 둘 다 지원 — 첫 번째 인자가 포트 번호로 파싱되면 레거시로 간주. **버그 발견/수정**: 처음엔 "두 인자 모두 숫자여야 레거시"로 판정해서 `redisx-server 7897`(포트 하나만 준, 원래부터 되던 호출)을 설정 파일 경로로 오인해 `7897`이라는 이름의 파일을 만들고 기본 포트 6379로 떠버리는 회귀를 실제 바이너리 테스트로 발견 — "첫 번째 인자만 포트로 파싱되면 레거시"로 조건을 완화해 고쳤다.
- **설정 파일이 없을 때**: 기본값으로 새로 만들고, 어디에 만들었는지와 "수정 후 재시작하라"는 안내를 표준에러에 출력(`load_or_create_config`) — 매 요청마다 반복되는 게 아니라 기동 시 한 번뿐.
- **`install.sh` 신규** (레포 루트): `cargo build --release --workspace` 후 `redisx-server`/`redisx-cli`/`redisx-benchmark`를 `INSTALL_DIR`(기본 `/usr/bin/redisX`, 보통 `sudo` 필요 — 쓰기 불가할 때만 자동으로 요청)에 복사. 서버를 실행하거나 쉘 설정 파일을 직접 건드리지 않고, 끝에 설정 파일 경로 수정 안내와 `~/.zshrc`/`~/.shrc`에 추가할 `export PATH=...` 줄을 출력만 한다 — 시스템 전역 경로(`/usr/bin`) 쓰기와 쉘 시작 파일 수정은 사용자 승인 없이 자동으로 실행하지 않는다는 원칙에 따라, 실제로 무엇을 할지 보여주고 사용자가 직접 실행하게 함.
- **완료 기준 검증**:
  1. 유닛테스트 4개 신규(`write_conf_file`→`load_conf_file` 왕복, 내부 포트 센티넬이 사람이 보는 파일에선 `6379`로 나오는 것, 주석/빈 줄 무시, 없는 파일은 `NotFound`). `cargo clippy --workspace --all-targets` 경고 0개.
  2. 실제 바이너리로: 인자 없이 실행 → `target/debug/redisx.conf`(실행 파일 옆)에 기본값 파일 생성 + 안내 메시지 확인, 생성된 파일의 `port`를 수정해 재시작하면 그 포트로 뜨는 것 확인, 레거시 `redisx-server <port>`/`redisx-server <port> <num_dbs>` 둘 다 설정 파일 없이 정상 동작(위 회귀 수정 포함) 확인.
  3. `INSTALL_DIR`을 스크래치 디렉터리로 지정해 `install.sh`를 실제로 실행 — 세 바이너리가 전부 설치되고, `cargo` 없이 그 디렉터리의 `./redisx-server`만으로 기동·`PING` 응답까지 확인(`/usr/bin/redisX` 자체에는 `sudo` 없이 쓸 수 없어 실제로 설치하지는 않음 — 스크립트가 맞는 동작을 한다는 것만 별도 디렉터리로 검증).

### Phase 16 — Stream 컨슈머 그룹 (완료 — `XGROUP`/`XREADGROUP`/`XACK`/`XCLAIM`/`XAUTOCLAIM`/`XPENDING`)

Phase 13 감사가 미뤄뒀던 세 항목 중 두 번째("전부 다" 중 남은 항목). 핵심 설계는 `stream.rs`의 기존 "`rax` 대신 `BTreeMap`" 결정을 그대로 확장한 것 — 그룹별 PEL(pending entries list)도 real Redis의 `rax` 기반 구조 대신 `BTreeMap<StreamId, PelEntry>`로 구현했다.

- **`stream.rs`에 `StreamGroup`/`PelEntry`/`Consumer` 신규**: `StreamGroup`은 `last_delivered_id` 워터마크, PEL(`BTreeMap<StreamId, PelEntry>`), 컨슈머별 `seen_time_ms`/`active_time_ms`를 들고 있다. `entries_read`는 `-1`이면 "알 수 없음"(이 포크의 `entries-added` 근사치가 믿을 수 없어지는 `XSETID` 이후 등)이라는 real Redis의 관례를 그대로 따라, `XINFO GROUPS`의 `lag` 필드가 이 경우 정수 대신 `nil`을 보고한다.
- **`XGROUP CREATE/SETID/DESTROY/CREATECONSUMER/DELCONSUMER`**: `CREATE ... MKSTREAM`만 키를 새로 만들 수 있고, 나머지 서브커맨드는 real Redis처럼 키/그룹이 없으면 `NOGROUP` 에러. `DELCONSUMER`는 삭제되는 컨슈머가 들고 있던 PEL 엔트리 수를 반환.
- **`XREADGROUP GROUP g consumer [COUNT n] [NOACK] STREAMS key... id...`**: `>`(새 항목만)와 명시적 id(이미 이 컨슈머에게 전달된 PEL 항목 재조회) 둘 다 지원. `BLOCK`은 미구현 — 아래 "다음 액션" 참고.
- **`XACK`**: PEL에서 제거, 존재 여부를 반환값(ack된 개수)으로 구분.
- **`XPENDING key group`**(요약: 총 개수/최소id/최대id/컨슈머별 개수)와 **`XPENDING key group [IDLE ms] start end count [consumer]`**(확장: id/consumer/idle시간/배달횟수 배열) 둘 다 구현.
- **`XCLAIM`**: `min-idle-time` 미달이면 무시, `FORCE`로 PEL에 없어도(스트림엔 아직 있는) 항목을 새로 PEL에 올림, `JUSTID`면 배달횟수를 올리지 않음. 클레임 대상 id가 이미 `XDEL`로 지워졌으면 — real Redis 최신 동작과 동일하게 — PEL에서도 조용히 제거하고 결과에서 제외한다(`XCLAIM`/`XAUTOCLAIM` 둘 다).
- **`XAUTOCLAIM`**: `start` 커서부터 PEL을 스캔해 `min-idle-time` 조건을 만족하는 것부터 최대 `COUNT`개(기본 100) 클레임, `[다음-커서, 클레임된-엔트리들, 삭제된-id들]` 3-튜플 반환.
- **`XINFO GROUPS`/`XINFO CONSUMERS`**: 더 이상 빈 배열 고정 응답이 아니라 실제 그룹/컨슈머 상태(`name`/`consumers`/`pending`/`last-delivered-id`/`entries-read`/`lag`, `name`/`pending`/`idle`/`inactive`)를 보고.
- **RDB 영속화**: 이 포크 전용 `TYPE_STREAM_CUSTOM` 옵코드(real Redis 포맷이 아님 — `rdb.rs` 모듈 문서 참고)를 포맷 확장해, 엔트리 목록 뒤에 그룹 수 → 그룹별(이름/워터마크/`entries_read`/PEL/컨슈머 목록)을 추가로 직렬화. real Redis와 호환해야 할 포맷이 아니므로 하위 호환 없이 바로 확장.
- **완료 기준 검증**:
  1. 유닛테스트 — `stream.rs`에 `StreamGroup`/PEL 단위 동작(생성 중복 거부, delete_consumer의 PEL 정리, deliver/ack) 4개, `server.rs`에 커맨드별 동작(`XGROUP` 생성/중복/삭제, `XREADGROUP` 신규전달·재전달없음·NOACK·NOGROUP, `XCLAIM`의 idle 문턱/JUSTID/삭제된 엔트리 처리, `XAUTOCLAIM`의 커서·삭제목록, `XGROUP CREATECONSUMER`/`DELCONSUMER`, `XINFO GROUPS`/`CONSUMERS`) 11개, `rdb.rs`에 그룹+PEL 왕복 1개 — 총 16개 신규. `cargo clippy --all-targets`(및 `--features python`) 경고 0개(논민멀불리언 경고 1건 발견 즉시 수정). `redisx-server` 유닛테스트 250 → 264(`--features python`: 255 → 269).
  2. **실제 바이너리 + `redis-cli` 교차검증**: `XADD` 3건 → `XGROUP CREATE` → `XREADGROUP`(COUNT 2)로 2건 전달 → `XPENDING` 요약이 정확히 2건·두 극단 id 보고 → `XACK` 1건 → 확장 `XPENDING`이 나머지 1건만 보고 → 두 번째 컨슈머가 `XREADGROUP ... >`로 세 번째 항목만 새로 받는 것(이미 전달된 건 다시 안 옴) → `XINFO GROUPS`/`CONSUMERS`가 실제 숫자 반영 → `XCLAIM`이 `min-idle-time` 미달이면 빈 배열, 0이면 소유권 이전 → `XAUTOCLAIM`이 남은 전부를 한 번에 클레임하고 커서 `0-0` 반환 → `XGROUP DELCONSUMER`가 정확한 보류 개수 반환. 전부 기대대로 동작.
  3. **real RDB 영속화 교차검증**: 그룹 2개(하나는 일부 ack, 하나는 전부 미ack) 상태에서 `SAVE` → `SHUTDOWN NOSAVE` → 바이너리 재기동 → `XINFO GROUPS`/`CONSUMERS`/`XPENDING`이 정확히 재기동 전 상태(그룹 2개, 컨슈머 수, 보류 개수, ack된 항목은 보류 목록에서 빠진 것)를 그대로 복원.

### Phase 17 — `XREAD BLOCK`/`XREADGROUP ... BLOCK` (완료 — Phase 14 블로킹 인프라 재사용)

Phase 13 감사가 미뤄뒀던 세 항목 중 마지막에서 두 번째("전부 다" 중 남은 항목). Phase 16 "다음 액션"이 예상한 그대로, Phase 14가 만든 `Server::blocked`/`blocking_keys`/`try_blocking_command`/`maybe_unblock_waiters`/`check_blocking_timeouts` 인프라를 그대로 재사용해서 끝났다 — 새 자료구조는 하나도 필요 없었다.

- **바이너리 계층의 라우팅 조건이 `BLPOP` 계열과 다르다**: `BLPOP`/`BRPOP`/... 는 커맨드 *이름*만으로 블로킹 여부가 정해지지만, `XREAD`/`XREADGROUP`은 같은 이름이 `BLOCK` 옵션의 유무에 따라 블로킹/논블로킹 둘 다로 쓰인다. `redisx-server.rs`에 `wants_block_option(argv)`(`STREAMS` 키워드 전까지 스캔해 `BLOCK` 토큰이 있는지만 확인)을 추가해, 이 조건이 참일 때만 `BLPOP`과 동일한 경로(`try_blocking_and_respond` — 기존 `BLPOP` 처리 블록을 그대로 함수로 뽑아 재사용)로 보낸다. `BLOCK` 없는 평범한 `XREAD`/`XREADGROUP`은 지금까지처럼 `dispatch()`로 직행.
- **`$`는 블로킹 시작 시점에 한 번만 해석**: `try_blocking_xread`가 `STREAMS` 절의 각 `$`를 "지금 이 순간의 `last_id`"로 즉시 치환해 그 값을 `BlockedClient.argv`에 그대로 저장한다 — 재시도 때마다 다시 해석하면 "방금 그 쓰기 자체가 새 `last_id`"가 되어 매번 "아직 아무것도 없음"으로 보이는 버그가 생긴다(논블로킹 `XREAD`의 기존 doc 주석이 "지금 이 순간엔 `$`가 항상 '아직 없음'으로 읽히는 게 정확하다"고 적어둔 바로 그 이유가, 반대로 블로킹에서는 한 번만 풀어야 하는 이유이기도 하다). `XREADGROUP`의 `>`는 그룹의 `last_delivered_id` 워터마크를 기준으로 항상 "아직 전달 안 된 것"을 가리키므로 매번 다시 평가해도 안전 — 별도 치환이 필요 없다.
- **`attempt_blocking_xread`는 `cmd_xread`를 직접 호출**(`run_command`를 거치지 않음 — `XREAD`는 `is_write: false`라 전파/AOF를 얻을 게 없음), **`attempt_blocking_xreadgroup`은 `run_command`를 거침**(`XREADGROUP`은 `is_write: true`라 PEL 변경을 전파/AOF에 반영해야 하므로, 블로킹 전용 경로라고 이 보장을 잃으면 안 됨 — 목록/정렬집합 블로킹 커맨드가 `run_command`를 거치는 것과 같은 이유). `check_blocking_timeouts`의 타임아웃 응답 모양 분기는 수정 불필요 — `XREAD`/`XREADGROUP`의 "아무것도 없음" 응답은 원래도 null *array*라 이미 "그 외 전부" 분기에 해당.
- **정직하게 남겨둔 근사**: 여러 스트림에 `>`/명시적 id가 섞인 `XREADGROUP` 호출에서, 일부 키가 이미 값을 내놓는데 다른 키는 "역사적 id라 영원히 데이터가 안 생길 것"인 경우라도 전체 응답이 비어 있으면 블로킹에 들어간다 — real Redis는 "`>`가 아닌 키는 항상 즉시 응답"을 보장하지만 이 포크는 "전체가 비어 있으면 블로킹"으로 단순화했다. 틀린 결과를 내는 게 아니라 드문 혼합 케이스에서 더 오래 기다릴 뿐이라 허용 가능한 근사로 문서화.
- **완료 기준 검증**:
  1. 유닛테스트 8개 신규 — `try_blocking_command`를 직접 호출해 `XREAD BLOCK`/`XREADGROUP ... BLOCK`의 즉시 응답(이미 데이터 있음/WRONGTYPE), 블로킹 후 깨어남(`$`가 한 번만 해석되는 것 — 블로킹 이후에 추가된 항목만 오는 것까지 확인), `NOGROUP` 즉시 에러, 타임아웃 null array 모양을 전부 확인. `cargo clippy --all-targets`(및 `--features python`) 경고 0개(인자 7개 초과 경고 1건을 `XReadGroupAttempt` 구조체로 묶어 즉시 수정). `redisx-server` 유닛테스트 264 → 271(`--features python`: 269 → 276).
  2. **실제 바이너리 + raw 소켓 스크립트로 5가지 시나리오 교차검증**(Phase 14와 같은 방식): (a) 커넥션 A가 `XREAD BLOCK 0 STREAMS st $`로 블로킹 → 커넥션 B가 `XADD` → A가 정확한 새 항목으로 깨어남, (b) 푸셔 커넥션이 그 후에도 정상 동작, (c) 타임아웃이 지정 시간(±허용오차) 뒤에 null array로 응답, (d) **파이프라이닝**: `XREAD BLOCK`과 `PING`을 한 번에 보내고 `XREAD`가 깨어난 뒤에야 `PING`의 `PONG`이 도착, (e) `XREADGROUP GROUP g c BLOCK 0 STREAMS st >`도 동일하게 깨어나고, 깨어난 뒤 `XPENDING`이 그 전달을 정확히 반영. 전부 통과.
- **다음 액션**: §3 감사가 "전부 다"로 확정했던 세 대형 항목(블로킹 커맨드, Stream 컨슈머 그룹, `XREAD BLOCK`/`XREADGROUP BLOCK`) 전부 완료 — 남은 것은 TLS(인증서 로딩 + `rustls` 등 신규 의존성 + 평문/TLS 듀얼 리스너 설계) 하나뿐.

### Phase 18 — TLS (완료 — `rustls` 기반 서버 사이드, 평문/TLS 듀얼 리스너)

"전부 다"로 확정했던 B그룹 세 대형 항목 중 마지막. §4-1(리스크 노트: "TLS는 OpenSSL C API에 강하게 묶여 있어 `rustls`/`native-tls` 중 선택 필요")에서 예견했던 그대로 `rustls`를 선택 — 순수 Rust라 이 포트가 지금까지 지켜온 "OpenSSL FFI 같은 외부 C 의존성 없음" 기조와 맞고, non-blocking 소켓을 전제로 암호화 레코드를 직접 펌핑하는 sans-I/O 설계라 이 포크의 `mio` 기반 단일 스레드 리액터와도 잘 맞는다.

- **범위를 의도적으로 좁혔다**: 서버 사이드 전용(클라이언트 인증서 검증·SNI 멀티서트·`tls-protocols`/`tls-ciphers` 튜닝 없음 — rustls의 안전한 기본값 그대로), 인증서/키 각각 하나씩 기동 시 1회 로드(런타임 리로드 없음 — 이 포크의 평문 설정도 `SIGHUP` 리로드가 없으니 동일 원칙), 그리고 **이 포크 자신의 아웃바운드 `REPLICAOF` 핸드셰이크는 TLS를 타지 않음**(real Redis의 별도 `tls-replication` 토글에 해당 — 클라이언트 쪽 `rustls::ClientConnection` 배선이 추가로 필요해 범위 밖으로 뺌). 반대로 **인바운드 연결은 전부 공짜로 TLS를 탄다** — `PSYNC`로 복제본이 되는 연결이든 평범한 클라이언트든, `tls-port`로 들어오기만 하면 동일하게 암호화된다(아래 `ConnStream` 설계 덕분에 바이너리 계층의 나머지 코드가 전혀 달라질 필요가 없었던 결과).
- **`tls.rs` 신규**: `install_default_crypto_provider()`(`ring` 크립토 프로바이더를 프로세스 전역 기본값으로 설치 — rustls 0.23부터 명시적으로 필요), `load_server_config(cert_path, key_path) -> Arc<rustls::ServerConfig>`(`rustls-pemfile`로 PEM 인증서 체인 + 키를 읽고 `with_no_client_auth().with_single_cert(...)`로 구성), 그리고 **`TlsStream`** — non-blocking 소켓 위에서 돌아가는 `rustls`의 표준 "펌프 루프"를 `Read`/`Write`로 감싼 타입. `rustls::Stream`은 blocking 소켓을 전제하므로 쓸 수 없어 직접 구현: `read()`는 평문 버퍼를 먼저 확인하고, 없으면 `read_tls`로 소켓에서 암호문을 더 끌어와 `process_new_packets`(핸드셰이크 진행까지 겸함)에 넘긴 뒤 다시 평문을 확인하는 루프이고, `write()`/`flush()`는 `writer().write()` 후 `wants_write()`가 참인 동안 `write_tls`로 반드시 플러시한다. `WouldBlock`은 그대로 전파되므로, 이미 `ErrorKind::WouldBlock`을 기준으로 쓰여 있는 나머지 코드(`service_connection` 등)는 손댈 필요가 없었다.
- **`redisx-server.rs`에 `ConnStream` enum 신규**: `Plain(mio::net::TcpStream)` / `Tls(Box<TlsStream>)` 두 variant에 `Read`/`Write`를 위임 구현만 해두고, `Conn::stream` 필드 타입을 이걸로 바꿨을 뿐 — `service_connection`/`handle_psync`/`drain_pending_commands` 등 소켓을 읽고 쓰는 다른 모든 코드는 `conn.stream.read(...)`/`write_all(...)`을 그대로 호출하므로 **단 한 줄도 TLS 여부를 알 필요가 없다**. 이게 이번 Phase의 핵심 설계 결정 — "TLS는 전송 계층 하나를 바꾸는 일이지, 커맨드 처리 로직을 바꾸는 일이 아니다"를 타입 시스템으로 강제한 것.
- **듀얼 리스너**: 기존 평문 accept 루프를 `setup_accept_loop(ev, server, conns, listener, tls_config: Option<Arc<ServerConfig>>)`로 뽑아내 평문/TLS 양쪽이 공유하게 했다 — `tls_config`가 `Some`이면 accept마다 `rustls::ServerConnection::new`로 새 TLS 세션을 열어 `ConnStream::Tls`로 감싸고, `None`이면 지금까지처럼 `ConnStream::Plain`. `tls-port`가 0이 아니면서 `tls-cert-file`/`tls-key-file`이 둘 다 유효하게 로드될 때만 두 번째 `TcpListener`를 바인드 — 하나라도 비었거나 로드에 실패하면 (real Redis와 동일하게) **기동 자체를 거부**하고 종료한다. 평문 `port`를 0으로 둬서 "TLS 전용" 모드로 만드는 것은 지원하지 않음(이 포크의 `port`용 `"0"` 센티넬 의미를 건드리게 되어 더 큰 변경이 필요 — 명시적으로 범위 밖) — 둘 다 켜는 "평문+TLS 동시 운영"만 지원.
- **`ConfigStore`에 `tls-port`(기본 `"0"`)/`tls-cert-file`/`tls-key-file`(기본 `""`) 추가** — real Redis와 이름은 같지만 `tls-ca-cert-file`/`tls-auth-clients` 등 나머지 TLS 설정 키는 없음.
- **완료 기준 검증**:
  1. 유닛테스트 4개 신규(`tls.rs`) — 10년 자체 서명 테스트 픽스처(`openssl req -x509 -newkey rsa:2048 -nodes -days 3650 -subj '/CN=localhost'`로 생성, 실제 서버가 쓰는 파일이 아니라 테스트 전용 상수로 소스에 내장)로 `load_server_config`의 성공 경로, 파일 없음, 빈 인증서 파일, 인증서-키 불일치 네 경우를 확인. `cargo clippy --all-targets`(및 `--features python`) 경고 0개(`ConnStream` enum의 variant 크기 차이 경고 1건을 `Box<TlsStream>`으로 즉시 수정). `redisx-server` 유닛테스트 271 → 275(`--features python`: 276 → 280).
  2. **실제 바이너리 + 실제 `redis-cli --tls`로 교차검증**(자체 서명 인증서라 `--insecure`로 검증 생략): `port`/`tls-port`를 둘 다 연 상태에서 `PING`/`SET`/`GET`을 평문 쪽에서, 같은 키를 TLS 쪽에서 조회해 **같은 데이터셋을 공유**하는 것 확인, 50KB 페이로드 왕복, 연속으로 새 TLS 연결 3개를 맺어도(핸드셰이크 반복) 매번 정상 응답, `MULTI`/`EVAL`, `PUBLISH`/`SUBSCRIBE`(백그라운드 TLS 구독자가 실제로 메시지 수신) 전부 TLS 위에서 정상 동작. `tls-port`만 설정하고 인증서/키를 비워두면 기동 직후 에러 메시지와 함께 종료 코드 1로 즉시 종료하는 것도 확인.
- **다음 액션**: §3 감사가 "전부 다"로 확정했던 B그룹 항목 전부 완료(블로킹 커맨드, Stream 컨슈머 그룹, `XREAD BLOCK`/`XREADGROUP BLOCK`, TLS). 남은 것은 애초부터 명시적 범위 밖으로 분류했던 것들뿐이었으나, 이후 별도 요청으로 그중 네 가지(`ZRANGEBYLEX`, 구형 RDB 옵코드, 전체 ACL, `tls-replication`)가 추가로 완료됨 — Phase 19~22 참고. 클러스터만 여전히 범위 밖.

### Phase 19 — `ZRANGEBYLEX`/`ZREVRANGEBYLEX`/`ZLEXCOUNT` (완료)

Phase 9에서 "활용도가 낮다고 판단해 범위 밖으로 남김"이라고 명시했던 항목. 사용자가 "전부 다 작업해줘"로 명시 요청해 마저 포팅.

### Phase 20 — 레거시 RDB 옵코드: `TYPE_LIST`/`TYPE_ZSET`/`FUNCTION2`/`SLOT_INFO`/`MODULE_AUX`/`KEY_META` (완료)

Phase 0/4가 "범위 밖"으로 명시했던 마지막 RDB 옵코드 묶음.

- **`TYPE_LIST`(오프코드 1)/`TYPE_ZSET`(오프코드 3)**: `ziplist`보다도 오래된, 서브컨테이너 없이 그냥 "개수 + 그만큼의 `rdbGenericLoadStringObject` 인코딩 문자열"(리스트)과 "멤버 문자열 + `rdbSaveDoubleValue`의 1바이트-길이-접두 ASCII 인코딩 점수"(zset, 253/254/255가 각각 NaN/+inf/-inf) 포맷 — 디코드 전용으로 `load_value`에 추가(`ziplist`/`zipmap`과 같은 수준의 스코프: 이 포크는 절대 쓰지 않지만 읽을 줄은 앎). `Reader::read_double_legacy` 신규.
- **`FUNCTION2`(옵코드 245)는 진짜 왕복 지원**: 이 포크엔 실제로 대응하는 기능(`FUNCTION LOAD`/`FCALL`)이 있으므로 "읽기만" 이 아니라 저장도 추가 — `script::Library`에 원본 소스(`source: String`) 필드를 새로 두고, `rdb::save`가 각 라이브러리를 `FUNCTION2` 옵코드 + 원본 소스 문자열로 기록, `rdb::load`가 그 문자열을 그대로 `Server::function_load(code, replace=true)`에 넘겨 재등록 — `FUNCTION LOAD` 자신이 쓰는 경로와 완전히 동일. `SAVE`/재시작을 거쳐도 라이브러리가 살아남는 진짜 기능 추가.
- **`SLOT_INFO`(244)/`MODULE_AUX`(247)/`KEY_META`(243)는 "에러 없이 건너뛰기"**: 이 포크엔 클러스터도 모듈 시스템도 없어 의미를 해석할 수 없지만, real Redis의 모듈 값 포맷 자체가 `RDB_MODULE_OPCODE_{SINT,UINT,FLOAT,DOUBLE,STRING}` + EOF로 끝나는 **자기서술적(self-describing) 스트림**이라는 점(`rdbLoadCheckModuleValue`)을 이용해 `Reader::skip_module_value`로 내용을 모른 채로도 정확히 건너뛸 수 있음 — `MODULE_AUX`와 `KEY_META`의 클래스별 메타데이터 둘 다 이 함수를 공유. `SLOT_INFO`는 슬롯 id/크기/만료-크기 세 길이값뿐이라 더 단순. 전부 "클러스터 모드가 아니면 무시"(real Redis 자신의 `SLOT_INFO` 처리와 동일 원칙)로 통일. 이전엔 이 세 옵코드가 전체 RDB 로드를 즉시 에러로 중단시켰지만, 이제는 real Redis(클러스터 모드였거나 모듈이 로드된 상태)가 만든 덤프도 나머지 키스페이스는 정상적으로 불러올 수 있음.
- **완료 기준 검증**: `rdb.rs`에 유닛테스트 6개 신규 — 레거시 plain list/zset 디코드, NaN 점수 거부, `SLOT_INFO`/`MODULE_AUX`/`KEY_META`를 뒤섞은 완전한 RDB 파일이 나머지 키를 정상 로드하는지, `FUNCTION2` 저장→재적재 라운드트립(`redisx-server`: 271→282, 이 중 `zset`/`acl` 등 다른 Phase 테스트도 섞여 있어 정확한 순증은 roadmap 각 Phase 절 참고). `cargo clippy --all-targets`(및 `--features python`) 경고 0개. 실제 `redisx-server` + `redis-cli`로 Lua 라이브러리 `FUNCTION LOAD` → `SAVE` → `SHUTDOWN NOSAVE` → 재시작 → `FCALL`이 재시작 후에도 그대로 동작하는 것까지 확인.

### Phase 21 — `tls-replication` (완료 — 아웃바운드 `REPLICAOF`의 TLS화)

Phase 18이 "클라이언트 쪽 `rustls::ClientConnection` 배선이 추가로 필요해 범위 밖"이라고 명시했던 마지막 조각.

- **`tls.rs`를 서버/클라이언트 공용으로 일반화**: `TlsStream`(비차단 소켓 펌프 `Read`/`Write` 구현체)을 `ServerConnection`/`ClientConnection` 어느 쪽이든 받는 제네릭 `TlsStream<C: RustlsConnection>`으로 바꾸고, 기존 이름 `TlsStream`은 `ServerConnection`용 기본 타입 인자로 그대로 유지(기존 호출부 전부 무변경), `TlsClientStream = TlsStream<ClientConnection>` 신규 — `RustlsConnection` trait은 `reader`/`writer`/`read_tls`/`write_tls`/`process_new_packets`/`wants_write`/`is_handshaking`을 양쪽에 위임만 한다. **까다로웠던 점**: 이 메서드들은 `ServerConnection`/`ClientConnection`의 진짜 inherent 메서드가 아니라 `Deref`로 상속된 `ConnectionCommon`의 메서드라서, 같은 이름의 trait 메서드를 그 타입에 직접 구현하면 메서드 탐색이 (inherent가 trait보다 항상 우선이라는 통념과 달리) **trait 쪽을 먼저 찾아 무한 재귀**가 남 — `std::ops::DerefMut::deref_mut(self).read_tls(...)`처럼 명시적으로 `Deref`를 거쳐 `ConnectionCommon`의 진짜 메서드에 도달하도록 고쳐 해결.
- **`load_client_config()` 신규** — `NoServerCertVerification`(모든 인증서를 수락하되 서명 검증 자체는 `rustls::crypto::verify_tls{12,13}_signature`로 진짜 수행)을 꽂은 `ClientConfig`. 이 포크엔 `tls-ca-cert-file` 설정 자체가 없어 마스터 인증서 체인을 검증할 CA 저장소가 없기 때문 — Phase 18이 인바운드 쪽에서 클라이언트 인증서 검증을 생략한 것과 같은 결의 범위 축소를 반대쪽 연결에도 적용한 것.
- **`redisx-server.rs`**: `send_command`/`read_line`을 `StdTcpStream` 전용에서 `impl Read`/`impl Write` 제네릭으로 바꿔 `replicaof_handshake_io`가 평문 소켓과 `rustls::Stream`(이 라이브러리 자신의 blocking 래퍼 — 이 핸드셰이크 자체가 이미 "이벤트 루프를 짧게 블로킹하는 동기 코드"로 설계돼 있어 Phase 18의 non-blocking 펌프가 필요 없음) 양쪽에서 동일하게 동작. 핸드셰이크가 끝나면 `std::net::TcpStream`을 non-blocking으로 전환해 `mio::net::TcpStream`으로 감싸고, 이미 협상이 끝난 `ClientConnection`(TLS 세션 상태는 소켓 타입과 무관하게 그대로 재사용 가능)과 묶어 `ConnStream::TlsClient`로 이벤트 루프에 등록 — `ConnStream`이 `Plain`/`Tls`/`TlsClient` 세 variant가 됨.
- **`tls-replication`(기본 `no`) 설정 추가**. `REPLICAOF`가 이 값을 보고 `tls_config: Option<Arc<ClientConfig>>`를 만들어 `replicaof_handshake`에 넘기는 것만으로 평문/TLS 분기가 끝 — 핸드셰이크 로직 자체는 완전히 공유.
- **완료 기준 검증**: `tls.rs`에 유닛테스트 1개 신규 — 실제 루프백 TCP로 `ServerConnection`(서버 쪽, `load_server_config`)과 `ClientConnection`(클라이언트 쪽, `load_client_config`)이 자체서명 테스트 인증서로 실제 핸드셰이크를 완주하고 평문 데이터를 주고받는 것까지 확인. `redisx-server` 275→283(실제로는 Phase 19/22 테스트도 섞임, 정확한 수는 전체 합계 참고). `cargo clippy --all-targets`(및 `--features python`) 경고 0개(`RustlsConnection`을 `pub trait`로, `read_tls`류를 `Deref`로 우회하는 수정 2건). 실제 바이너리 2대(평문+TLS 듀얼 리스너 마스터, `tls-replication yes` 레플리카)로 `REPLICAOF`를 실행해 마스터 로그에 `accepted ... (TLS)`/`is now a replica`가 찍히는 것, 초기 전체 동기화로 받은 키와 이후 실시간으로 전파된 쓰기 양쪽이 모두 레플리카에 정확히 반영되는 것을 확인.

### Phase 22 — 전체 ACL 사용자 테이블 (완료)

Phase 9의 "ACL-lite" 노트가 처음부터 범위 밖이라고 못박았던, 이 "전부 다" 추가 요청의 마지막이자 가장 큰 항목.

- **`acl.rs` 신규**: `AclUser { enabled, nopass, passwords: BTreeSet<SHA-256 hex>, all_keys, key_patterns, all_channels, channel_patterns, default_allow, command_rules: Vec<(bool, Selector)> }`. 권한 판정은 세 축 — `can_run(cmd)`(기준값에서 시작해 규칙을 순서대로 재생, 나중 규칙이 이김 — `acl.c`의 규칙 평가와 동일), `can_access_key(key)`, `can_access_channel(channel)`(둘 다 `config.rs`의 기존 `glob_match_bytes` 재사용 — `KEYS`/`PSUBSCRIBE`와 같은 글롭 문법).
- **의도적으로 좁힌 범위**(전부 모듈 doc에 명시):
  1. **`default` 사용자의 인증은 여전히 `requirepass` 하나로** — real Redis의 `requirepass`는 사실 ACL 기본 사용자 비밀번호를 고치는 설탕 문법인데, 이를 양방향 동기화하면 이미 충분히 검증된 기존 `requirepass` 경로 전체를 ACL 테이블과 매번 맞춰야 하는 부담이 생김. 대신 `requirepass`는 그대로 두고, `ACL SETUSER default >pw`로 추가 비밀번호나 명령/키/채널 제한을 **얹을 수만** 있게 함 — 둘 다 체크되고 어느 쪽도 다른 쪽을 덮어쓰지 않음. `default` 외의 모든 사용자는 전적으로 이 테이블에만 존재.
  2. **권한 검사는 `Server::dispatch` 한 곳에서만** — `NOAUTH`가 이미 쓰던 바로 그 지점이자 바로 그 우회 경로. `PSYNC`/`REPLICAOF`와 `BLPOP` 계열/`XREAD`/`XREADGROUP`의 `BLOCK`은 `dispatch` 도달 전에 바이너리 계층에서 가로채지므로(Phase 5/14/17 모듈 doc 참고) `NOAUTH`를 우회했던 것과 똑같이 ACL도 우회함 — 새로 생긴 구멍이 아니라 상속받은 구멍.
  3. **키/채널 검사는 `CLIENT TRACKING`이 이미 썼던 `tracked_key`(= `argv[1]`) 근사**를 그대로 재사용 — `SORT`/`GEORADIUS`/`EVAL`류의 완전한 키-스펙 테이블 대신, 커맨드마다 첫 번째 키만 검사(다중 키 커맨드의 두 번째 키부터는 검사 안 함). 기존 근사와 같은 수준.
  4. **selector 없음, 서브커맨드 단위 규칙(`+config|get`) 없음** — 둘 다 명확한 에러로 거부.
  5. **카테고리는 작은 큐레이션 집합**(`all`/`read`/`write`/`keyspace`/`admin`/`dangerous`/`connection`/`transaction`/`scripting`/`pubsub`) — real Redis의 `@string`/`@list`/`@fast`/`@slow` 등 커맨드별 세분화 태그는 없음. 목록에 없는 카테고리는 조용히 매치 없음이 아니라 명확한 에러.
  6. **`ACL SAVE`/`LOAD`는 항상 에러** — 이 포크엔 `aclfile` 설정 자체가 없어, real Redis가 `aclfile` 미설정 시 내놓는 바로 그 에러를 조건 없이 반환(축소가 아니라 real Redis도 타는 코드 경로 그대로).
- **`ACL` 커맨드**: `WHOAMI`/`LIST`/`USERS`/`CAT [category]`/`GETUSER`/`SETUSER`(토큰을 클론에 전부 적용해 하나라도 실패하면 전체 거부 — real Redis와 같은 all-or-nothing)/`DELUSER`(`default` 삭제는 거부)/`DRYRUN`/`SAVE`/`LOAD`.
- **`cmd_auth` 재작성**: `username == "default"`면 `requirepass`와 ACL 테이블의 명시적 비밀번호(오직 `nopass=false`이고 `passwords`가 비어있지 않을 때만 — 갓 초기화된 `nopass:true` 상태를 "비밀번호 있음"으로 착각하지 않도록 구분) 양쪽을 OR로 검사, 그 외 사용자명은 ACL 테이블만. `requires_auth_fn`도 `ACL SETUSER default off`/`resetpass`가 `requirepass` 없이도 실제로 접속을 막도록 확장(안 그러면 ACL로 기본 사용자를 잠가도 아무 효과가 없는 조용한 버그가 됨).
- **완료 기준 검증**: `acl.rs`에 유닛테스트 8개(기본/빈 사용자 상태, 규칙 순서/전체-아니면-무효 커밋, 카테고리, 알 수 없는 카테고리/커맨드 거부, `allkeys` 이후 패턴 거부, 해시 비밀번호 형식, `describe` 렌더링), `server.rs`에 18개(ACL 서브커맨드 전부, 제한된 사용자로 `AUTH` 전환 후 명령/키/채널 권한이 실제로 걸리는지, `ACL SETUSER default off`가 `requirepass` 없이도 잠그는지, 기존 `requirepass`/`AUTH` 테스트 전부 무회귀). `redisx-server` 275(Phase 18 기준) → 301(base)/306(`--features python`) — Phase 19~22 전체 순증. `cargo clippy --all-targets`(및 `--features python`) 경고 0개. 실제 `redisx-server` + 실제 `redis-cli`로: 기본 사용자 전부 허용 확인 → `ACL SETUSER bob on >pw ~foo:* +@read +set` → `redis-cli -u redis://bob:pw@...`로 접속해 허용된 `GET`/`SET foo:*`는 성공, 금지된 `DEL`과 범위 밖 키 `bar:1`은 각각 `NOPERM ...command`/`NOPERM ...key`로 거부, `ACL DRYRUN`이 실제 실행 없이 같은 판정을 미리 보여주는 것, `ACL DELUSER default` 거부, `ACL SAVE`의 에러 메시지까지 전부 확인.
- **다음 액션**: 이번 추가 요청(`ZRANGEBYLEX`, 레거시 RDB 옵코드, `tls-replication`, 전체 ACL)이 모두 끝남. 남은 것은 애초부터 범위 밖이었던 것 중 단 하나 — Redis Cluster(§4-5, 가십 프로토콜 설계가 선행돼야 하는, Phase 0~12를 합친 것과 맞먹는 규모의 별도 프로젝트).

### Phase 23 — Redis Cluster (완료 — §4-5의 "가십 프로토콜 신규 설계" 결정)

애초부터 범위 밖이었던 마지막 한 항목. §4-5가 미결정으로 남겨뒀던 질문("`cluster_legacy.c`와 바이트 호환 vs 신규 프로토콜")에 대한 답은 **신규 프로토콜** — 근거와 전체 스코프 축소 목록은 신규 `cluster.rs`의 모듈 doc에 전부 명시(아래는 요약).

- **`cluster.rs` 신규**: `crc16`(real Redis의 XMODEM 변형 테이블을 그대로 포팅, `crc16("123456789") == 0x31C3` 알려진 테스트 벡터로 고정)과 `key_hash_slot`(`{hashtag}` 지원), `ClusterNode`/`ClusterState`(16384 슬롯 소유권, 노드 테이블, 자기 자신의 id/epoch), 그리고 가십 와이어 포맷(`encode_gossip`/`parse_gossip` — 길이-프리픽스 텍스트 프레임, 바이너리 `cluster_legacy.c` 프로토콜과 호환 안 함, redisX끼리만 통신) + `merge_remote`(설정 epoch가 높은 쪽이 통째로 이김 — 슬롯 단위가 아니라 노드 레코드 단위로 적용한 것만 다름).
- **의도적으로 좁힌 범위**(전부 `cluster.rs` 모듈 doc에 명시):
  1. **가십은 새로 설계한 프로토콜** — 바이너리 체크섬/버전 협상이 있는 `cluster_legacy.c`를 재현할 실익이 redisX끼리만 통신하는 이 포크엔 없음.
  2. **리샤딩 댄스 없음** — `CLUSTER SETSLOT`은 `NODE`(즉시 강제 재할당) 변형만 지원, `IMPORTING`/`MIGRATING`/`STABLE`/`ASK`/`MIGRATE`는 없음. 슬롯 재할당은 이미 들어있는 키를 옮기지 않는다(이전 소유자가 로컬에 그대로 들고 있음) — `redis-cli --cluster reshard`가 `MIGRATE`+`ASK`로 하던 일은 의도적으로 클라이언트 쪽 관리 도구의 몫으로 남겨둠.
  3. **자동/투표 기반 장애조치 없음** — `CLUSTER FAILOVER`는 기존 비-클러스터 `FAILOVER` 커맨드와 똑같은 이유(복제 링크에 레플리카를 원격으로 승격시킬 제어 채널이 없음)로 동일한 형태의 명확한 에러를 반환. 수동 승격(`CLUSTER RESET` + `ADDSLOTS`/`SETSLOT`)이 유일한 경로.
  4. **`nodes.conf` 영속화 없음** — 클러스터 토폴로지는 메모리에만 존재(`CLUSTER SAVECONFIG`는 받아들이되 실제로는 아무것도 저장하지 않는 no-op). 재시작한 노드는 슬롯 없는 단독 마스터로 돌아오며 `CLUSTER MEET`을 다시 해야 한다.
  5. **장애 감지는 오직 로컬 측정만** — 가십으로 받은 제3자의 `fail` 상태는 절대 신뢰하지 않고(`merge_remote`가 `fail`/`misses`를 건드리지 않음), 모든 노드가 자신이 아는 모든 피어를 매 틱 직접 측정만 한다 — real Redis의 `PFAIL`→`FAIL` 승격에 필요한 다른 마스터들의 쿼럼 투표가 전혀 없음.
  6. **`CROSSSLOT` 검사는 커맨드별 명시적 키-위치 테이블**(`server.rs`의 `cluster_command_keys`) — ACL/`CLIENT TRACKING`이 쓰는 `argv[1]` 근사와 달리, 여기서 오탐은 `CONFIG GET maxmemory` 같은 평범한 비-키 커맨드를 잘못 리다이렉트시키는 가시적 버그가 되므로 화이트리스트 밖은 전부 "키 없음"으로 처리(미탐은 그 커맨드 하나가 아직 리다이렉트 인식이 안 되는 것뿐 — 더 안전한 쪽으로 기움).
- **가십 네트워킹 설계 반복**: 첫 구현은 틱마다 모든 피어와 "쓰고 나서 응답을 기다리는" 동기 왕복이었는데, 두 redisX 노드가 거의 동시에 기동되면 양쪽의 1초 cron 틱이 영원히 같은 위상으로 맞물려 **서로가 서로의 응답을 기다리며 매 틱 100% 재현되는 라이브락**이 됐다(단일 스레드 이벤트 루프라 "내 응답을 기다리는 동안 상대의 접속을 받아줄 수 없다"가 쌍방에 동시에 성립). 해결: 요청/응답을 **일방향 푸시**로 바꿔 틱마다 아는 피어 전원에게 현재 테이블을 쓰고 응답을 기다리지 않도록 재설계 — 그 덕에 실제로는 real Redis의 `CLUSTER MEET`과 동일한 "즉시 `+OK`, 핸드셰이크는 비동기"의미에 더 가까워졌다(기존 설계는 즉시 확인을 시도했었음). 도달성(`fail`/`misses`)도 왕복 성공이 아니라 "연결+쓰기 자체의 성공"만으로 판단하도록 바꿈 — 이 교정은 `redisx-server.rs`의 "Cluster bus" 섹션 모듈 doc에 원인/해결 전체를 기록해둠(실제 실행으로 재현 후 발견한 버그).
- **커맨드**: `CLUSTER MYID`/`INFO`/`NODES`/`SLOTS`/`SHARDS`/`KEYSLOT`/`COUNTKEYSINSLOT`/`GETKEYSINSLOT`/`ADDSLOTS(RANGE)`/`DELSLOTS(RANGE)`/`SETSLOT ... NODE`/`BUMPEPOCH`/`SET-CONFIG-EPOCH`/`FORGET`/`RESET`/`FLUSHSLOTS`/`SAVECONFIG`/`COUNT-FAILURE-REPORTS`/`LINKS`/`MEET`/`REPLICATE`/`FAILOVER`(거부) + `ASKING`/`READONLY`/`READWRITE`(마지막 둘은 `ClientState::cluster_readonly`로 실제 레플리카 stale-read 서빙까지 동작, `ASKING`은 받아들이되 참조 안 함 — 리샤딩 댄스가 없어서). `CLUSTER MEET`/`REPLICATE`는 `PSYNC`/`REPLICAOF`와 똑같이 실제 네트워크 I/O가 필요해 `redisx-server.rs`가 `dispatch` 도달 전에 가로챈다 — `REPLICATE`는 노드 id를 ip/port로 풀어서 기존 `handle_replicaof`에 그대로 위임(복제 로직 자체는 중복 구현 없음).
- **`Server::dispatch`에 `check_cluster_redirect` 신규 배선**(ACL 검사 바로 다음, `NOAUTH`/ACL과 같은 단일 지점 — 따라서 같은 우회 지점을 상속: `PSYNC`/`REPLICAOF`/블로킹 커맨드는 여기도 역시 우회). `cluster.enabled`가 꺼져 있으면 완전 no-op이라 기존 비-클러스터 동작은 바이트 단위로 무변경.
- **완료 기준 검증**: `cluster.rs` 유닛테스트 10개(crc16 벡터, hashtag, 슬롯 범위 병합/분할, 가십 인코드/파싱 왕복, `merge_remote`의 자기-보호/epoch 우선순위, `CLUSTER SLOTS`/`SHARDS` 그룹핑) + `server.rs` 11개(`MOVED`/`CROSSSLOT`/`CLUSTERDOWN`/`cluster-require-full-coverage no`/`READONLY` 레플리카 stale-read/`SETSLOT NODE`/`FORGET`/`SELECT` 클러스터 모드 제한/`CLUSTER INFO`-`NODES`-`SLOTS` 내용 검증). `redisx-server` 322(base)/327(`--features python`) — Phase 22 기준 301/306에서 순증. `cargo clippy --all-targets`(및 `--features python`) 경고 0개. **실제 바이너리 3대**로: `CLUSTER MEET`으로 2노드 가십 수렴(그리고 3번째 노드를 그 중 하나에만 `MEET`해도 전이적으로 전체를 알게 되는 것), `ADDSLOTSRANGE`로 16384 슬롯 전체 분할 후 `cluster_state:ok` 수렴, 다른 노드가 소유한 슬롯 키에 대한 raw `MOVED` 에러와 `redis-cli -c`의 투명한 자동 추종, `CROSSSLOT`(해시태그로 우회 가능함도 확인), `CLUSTER REPLICATE`가 실제 `REPLICAOF`를 걸어 `role:slave`+`master_link_status:up`까지 만드는 것, `READONLY` 이후 레플리카가 자기 마스터 슬롯의 키를 로컬에서 서빙하는 것(같은 커넥션에서 `READONLY` 없이는 여전히 `MOVED`)까지 전부 확인.
- **후속 감사 패스에서 발견/수정한 것 2건**("남은 부분 체크해줘봐" 요청으로 진행): (1) `acl.rs`의 `ADMIN_COMMANDS`가 Phase 22 때 확정된 뒤 Phase 23이 추가한 `CLUSTER` 커맨드를 반영하지 못해, `CLUSTER`가 `@admin`/`@dangerous`가 아니라 `@read`로만 분류되고 있었다 — `+@read -@admin` 같은 제한된 사용자가 `CLUSTER ADDSLOTS`/`RESET`/`FORGET` 같은 admin급 서브커맨드까지 실행 가능했던 실제 보안 관련 구멍. `ADMIN_COMMANDS`에 `CLUSTER` 추가 + 회귀 테스트(수정 전 상태로 되돌려 실패하는 것까지 직접 확인한 뒤 복구)로 닫았다. (2) `config.rs`의 `cluster-node-timeout`/`cluster-announce-ip`가 `CONFIG GET`에는 보이지만 실제로는 아무 데도 읽히지 않는 죽은 설정이었음을 발견 — 특히 `cluster-announce-ip`는 이 바이너리의 모든 리스너(클러스터 버스 포함)가 `127.0.0.1`에 하드코딩돼 있어(클러스터와 무관한 기존 제약) 이 값만 따로 연결해봐야 피어들에게 아무도 듣고 있지 않은 주소를 알려주는 꼴이 되므로, 배선하는 대신 "받아들이되 아직 효과 없음"을 명시적으로 문서화하는 쪽을 택했다(기존 `cluster-config-file`과 같은 처리). `stream.rs`의 오래된 모듈 doc 주석("`XREAD BLOCK`은 아직 미구현")도 Phase 17이 이미 구현했음을 반영하도록 교정(기능 문제 아님, 순수 설명 오기). 재검증: `redisx-server` 여전히 322(base)/327(`--features python`), clippy 경고 0개.
- **다음 액션**: 이것으로 §3/§4-5가 범위 밖으로 남겨뒀던 전부가 닫혔다. 이 문서 기준으로 더 이상 "애초부터 범위 밖"으로 분류된 미착수 항목은 없다 — 새 요청이 있다면 그건 추가 스코프이지 이연된 숙제가 아니다.

## 4. 전사 교차 관심사 (Phase 시작 전 확정 필요한 설계 결정)

1. **이벤트 루프 모델 — 확정됨: `mio`** (Phase 1에서 결정 및 구현 완료, 상세 근거는 Phase 1 섹션 참고). `tokio`는 생태계 친화적이지만 "명령 실행 중 다른 명령이 끼어들지 않는다"는 Redis의 핵심 불변식을 async 코드 전반에서 수동으로 보장해야 하는 부담이 있어 기각.
2. **메모리 할당자 전략 — 확정됨: Rust 기본 allocator, `jemalloc` 도입 안 함** ("남은 부분" 정리 패스에서 결정). `tikv-jemallocator`로 맞추면 `MEMORY STATS`/`MALLOC-STATS`/`defrag.c` 등을 실제 아레나 통계 기반으로 재현할 수 있지만, 이 프로젝트가 Phase 0부터 일관되게 유지해 온 "C 전용 최적화 트릭을 Rust에 억지로 들여오지 않는다"는 기조(Fenwick 트리 생략과 동일한 결)에 어긋나고, 이 포트의 실제 사용처(단일 프로세스 개발/테스트용 서버) 규모에서 jemalloc 아레나 분석이 주는 실익이 크지 않다고 판단했다. `MEMORY USAGE`는 jemalloc 없이도 구현 가능한 형태(값 내용 기반 근사치 산정)로 포팅했고, `MEMORY STATS`/`MALLOC-STATS`/`DEBUG`/`defrag`/`evict`/`lazyfree`는 전부 "할당자 통계가 없으므로 보고할 것 자체가 없음"으로 명시적 범위 밖 처리.
3. **unsafe 경계 정책**: `sds`/`listpack`/`rdb` 등 바이트 단위 파싱·조작이 많은 모듈에서 unsafe를 어디까지 허용할지(성능) vs 안전한 추상화로 감쌀지(안정성) 기준을 Phase 0에서 먼저 정해 이후 Phase에 일관 적용.
4. **스크립팅 엔진 재진입성**: Lua(`mlua`)는 동기 가정이 자연스럽지만, Python(`pyo3`)은 GIL 모델이 있어 C 버전(`function_python.c`)에서 쓴 `PyGILState_Ensure/Release` 패턴을 Rust에서도 동일하게 재현해야 함 — Phase 6에서 그대로 승계.
5. **클러스터 가십 프로토콜 호환 범위 — 확정됨: 신규 프로토콜**(Phase 23에서 결정 및 구현 완료). `cluster_legacy.c`의 바이너리·체크섬·버전 협상 프로토콜을 바이트 호환으로 재현할 실익이 redisX끼리만 통신하는 클러스터엔 없다고 판단 — 길이-프리픽스 텍스트 프레임 기반의 자체 설계(`cluster.rs`의 `encode_gossip`/`parse_gossip`)로 대체. 상세 근거와 전체 스코프 축소 목록은 Phase 23 섹션과 `cluster.rs` 모듈 doc 참고.
6. **테스트 전략 — 확정됨: 기존 Tcl 스위트를 그대로 채택하지 않고, "유닛테스트 + 실제 바이너리 수동 교차검증"을 계속 유지** ("남은 부분" 정리 패스에서 결정). 돌아보니 이 방식은 Phase 0부터 한 번도 어긴 적 없이 실제로 잘 작동했다 — 이 문서의 모든 Phase 섹션이 "유닛테스트 N개 통과" 옆에 반드시 "실제 `redis-cli`/`redis-server`로 무엇을 확인했는지"를 나란히 적어 온 것 자체가 그 증거. 기존 `tests/*.tcl`(219개 파일, 8.5만 라인)을 그대로 가져다 쓰지 않기로 한 이유: (a) 이 포트는 SLOWLOG/AOF 포맷처럼 이미 알고 의도적으로 바꾼 동작이 많아 Tcl 스위트의 상당수가 "의도된 차이"를 실패로 오판할 것이고, (b) Stream 컨슈머 그룹·클러스터·블로킹 커맨드처럼 범위 밖으로 명시한 영역을 검증하는 테스트가 전체의 적지 않은 비중을 차지해 그대로 돌리면 실패의 대부분이 노이즈가 된다. 커맨드 표면이 계속 커지는 만큼 회귀 방지용 Rust 네이티브 통합 테스트 하네스(바이너리를 띄워 스크립트화된 커맨드 시퀀스를 돌리는 것)는 여전히 가치 있는 다음 투자로 남겨두지만, 이번 패스에서 직접 만들지는 않음 — 지금까지처럼 유닛테스트 + 세션별 수동 교차검증으로 계속 간다.

## 7. 진행 현황 및 다음 액션

- **Phase 0 (완료)**: `redisX/crates/redisx-core` — sds 핵심 서브셋, crc16/64, intset, dict, listpack, kvstore, lzf(압축해제) 포팅 및 실제 Redis 바이너리 교차검증 완료. 나머지 항목은 전부 후속 Phase로 재분류하거나 Rust 표준으로 대체 결정.
- **Phase 1 (완료)**: `redisX/crates/redisx-net` — mio 채택 결정, `ae`(이벤트 루프)와 `resp`(RESP2/3 프로토콜) 포팅, 실제 `redis-cli` 및 raw 소켓 테스트로 PING/ECHO/인라인/파이프라이닝 검증 완료.
- **Phase 2 (완료 — 최소 범위)**: `redisX/crates/redisx-server` — 커맨드 테이블 디스패치, CONFIG GET/SET(글롭 매칭), MULTI/QUEUED/EXEC/DISCARD/EXECABORT 상태머신 포팅. `redisx-server` 바이너리를 실제로 띄워 `redis-cli`와 raw 소켓으로 전 시나리오 검증 완료. ACL/WATCH/blocking/출력 버퍼 관리/RESP3 HELLO 협상은 명시적으로 Phase 3+로 이연.
- **Phase 3 (완료 — List/Hash/Set/ZSet)**: `object::RObj`에 4개 타입 추가(`list.rs`/`hash.rs`/`set.rs`/`zset.rs`), 전부 소형/대형 인코딩 전환(ListPack↔RDict/IntSet/정렬Vec) 포함. 이 과정에서 Phase 0에 빠져 있던 `listpack`의 임의 위치 삽입/삭제와 `dict`의 전체 반복자를 추가 포팅함. `redis-cli`로 4개 타입 전체 커맨드와 WRONGTYPE 검증 완료. Stream/HyperLogLog/Geo/bitops/SORT는 명시적으로 범위 밖(Stream은 `rax` 선행 필요).

- **`install.sh` 버그 2건 수정**: (1) 기본 설치 경로 `/usr/bin/redisX`가 실제로는 절대 못 쓰는 경로였음을 사용자가 실행 중 발견 — 최신 macOS에서 `/usr/bin`은 SIP(System Integrity Protection)로 보호되는 시스템 볼륨이라 `sudo`로도 `mkdir`이 `Operation not permitted`로 막힌다(권한 문제가 아니라 SIP 차단). 기본값을 SIP 보호 대상이 아닌 `/usr/local/bin/redisX`로 변경. (2) `sudo mkdir`로 디렉터리를 새로 만든 뒤 소유권을 넘겨주지 않아 `root:wheel` 상태로 남았고, 그 결과 일반 사용자 권한으로 처음 `redisx-server`를 실행했을 때 같은 디렉터리에 기본 `redisx.conf`를 새로 쓰려다 `Os { code: 13, kind: PermissionDenied }`로 죽는 2차 버그가 실제로 재현됨 — `maybe_sudo_mkdir`이 `sudo mkdir` 직후 `sudo chown "$(id -u):$(id -g)"`로 소유권을 호출자에게 되돌려주도록 수정(새 디렉터리든, 이전 버전 스크립트가 만들어 둔 root 소유 기존 디렉터리든 둘 다 커버). 복구용으로 `--force` 옵션 신규 추가 — `sudo -v`로 먼저 sudo 접근을 확인한 뒤(삭제부터 하고 비밀번호가 틀리는 사고 방지) `$INSTALL_DIR`를 통째로 `rm -rf`하고 처음부터 재설치. `install.sh`는 유닛테스트 대상이 아닌 쉘 스크립트라 `bash -n` 구문 검사 + `INSTALL_DIR`를 스크래치 디렉터리로 돌린 실제 설치(바이너리 생성 확인 + `redisx-cli PING`까지)로 검증, `--force` 자체는 실제 `sudo` 비밀번호 입력이 필요해 사용자 환경에서 직접 확인이 필요함.
- **사용자 요청으로 `install.sh`가 Python 스크립팅을 포함하도록 변경**: 기존엔 `cargo build --release --workspace`(기능 플래그 없음)로 빌드해 설치된 `redisx-server`에 `FUNCTION LOAD`/`FCALL`의 Python 엔진(`--features python`, pyo3)이 빠져 있었음. `cargo build --release --workspace --features redisx-server/python`로 변경(워크스페이스 빌드에서 특정 멤버 크레이트의 feature만 켜는 `pkg/feature` 문법) — `redisx-cli`/`redisx-benchmark`는 이 feature와 무관해 영향 없음. 설치 완료 메시지에도 Python 지원 포함 사실을 한 줄 추가. 검증: `env -i`로 `DYLD_LIBRARY_PATH`/`cargo` 없는 깨끗한 환경에서 스크래치 디렉터리에 설치한 사본을 직접 기동 → `FUNCTION LOAD`로 `#!python` 라이브러리 등록 → `FCALL`까지 실제로 동작 확인(Phase B의 rpath 임베딩이 이 설치 경로에서도 그대로 유효함을 재확인). Python 3 개발 환경이 없는 빌드 머신에서는 이제 `install.sh`가 바로 실패함 — 플레인 빌드로 조용히 폴백하지 않음(요청 취지 자체가 "항상 포함"이므로 의도된 동작).
- **사용자 요청으로 `scripts/lua`·`scripts/python` 예제 신규 작성**: `FUNCTION LOAD`/`FCALL`을 바로 체험할 수 있는 3쌍(`hello`/`incrby_limit`/`rate_limiter`)을 두 언어로 각각 작성 — 같은 동작을 동일한 라이브러리/함수 이름으로 양쪽 엔진에 구현해 두 언어 컨벤션(Lua 1-indexed `keys[1]`/`args[1]` + `{err=...}`/`{ok=...}` 테이블, Python 0-indexed `keys[0]`/`args[0]` + `{'err':...}`/`{'ok':...}` dict)을 나란히 비교할 수 있게 했다. `incrby_limit`(한도 초과 시 쓰기 자체를 거부하는 원자적 증가)과 `rate_limiter`(`INCR`+`EXPIRE ... NX`로 구현한 고정 윈도우 레이트 리미터)는 "클라이언트 쪽에서 GET-then-SET으로 하면 두 라운드트립 사이에 경쟁 조건이 생기지만 FCALL은 단일 스레드 이벤트 루프 안에서 끼어듦 없이 완주되므로 진짜 원자적"이라는, 서버사이드 스크립팅의 존재 이유 자체를 보여주는 예제로 설계. `scripts/README.md`에 로드/호출 방법, 커맨드별 표, 직접 라이브러리를 작성할 때 알아야 할 API 요약(`redis.call`/`redis.pcall`/`register_function`)을 정리 — 테스트 중 발견한 실사용 함정(라이브러리/함수 이름을 두 언어가 똑같이 쓰고 있어서 같은 이름을 양쪽 엔진에 동시에 로드하면 `FUNCTION LOAD`가 "Library already exists"로 거부됨, `FUNCTION DELETE`로 지우고 전환해야 함)도 README에 명시해뒀다. 실제 `--features python`로 빌드한 바이너리로 6개 예제 전부 로드 + `FCALL` 호출 결과(정상/한도초과 에러/레이트리밋 소진 에러 전부 포함) 실측 확인.
- **사용자 요청으로 `scripts/` 예제를 00~90 난이도 커리큘럼으로 확장**: 기존 3쌍을 `00_hello`/`10_incrby_limit`/`30_rate_limiter`로 번호만 재배치하고, 그 사이·너머에 7레벨을 신규 추가해 총 10레벨(언어당)로 확장 — `20_cache_aside`(GET+SET+EXPIRE 조합과 Lua 배열 vs Python dict→RESP map의 실제 차이를 보여줌), `40_distributed_lock`(SET NX PX + 토큰 비교 DEL, 단일 인스턴스 락의 교과서적 패턴), `50_leaderboard`(ZADD/ZINCRBY+ZREVRANK 원자적 조합), `60_sliding_window_rate_limiter`(ZSET 기반 정밀 슬라이딩 윈도우 — 구현 중 이 포크에 `ZREMRANGEBYSCORE`/`ZREMRANGEBYRANK`가 아예 없다는 것을 발견해 `ZRANGEBYSCORE`+`ZREM` 조합으로 대체), `70_task_queue`(Stream 컨슈머 그룹 기반 claim+ack 원자적 큐), `80_bloom_filter`(RedisBloom 같은 네이티브 타입이 없는 이 포크에서 `SETBIT`/`GETBIT` + 스크립트 내 자체 구현 FNV-1a 더블해싱으로 블룸 필터를 직접 구성), `90_atomic_transfer`(두 키 사이의 잔액 불변식을 `WATCH`/`MULTI`/재시도 없이 단일 FCALL로 강제하는 캡스톤). 번호를 00·10·20...90으로 띄워서(0~9 전부 채우지 않음) 나중에 05/45 같은 레벨을 끼워 넣을 여지를 남겨뒀다. 실제 바이너리로 20개 파일 전부(언어 10개씩) 순차 로드+`FCALL` 호출까지 실측하는 과정에서 버그 1건 발견/수정 — `70_task_queue`의 `claim_and_complete`가 `(group, consumer)` 두 인자를 받는데 파일 자체의 사용 예시 주석이 인자 하나만 보여주고 있어서 그대로 따라하면 "redis lib command arguments must be strings or integers"(Lua)/"IndexError"(Python) 에러가 남 — 두 언어 파일의 doc comment를 실제 호출 시그니처에 맞게 수정하고 재검증. `scripts/README.md`를 레벨 표 + 번호 간격 규칙 설명까지 전면 재작성.
- **Phase 24 (완료 — `polars` 네이티브 DataFrame 타입)**: 사용자가 "redis에 polars dataframe을 연동"을 요청 → Python 블롭(FCALL 경유) 방식과 Rust `polars` 크레이트 직접 링크 방식 두 갈래를 제시했고, 사용자가 후자(쿼리를 Redis 프로세스 안에서 직접 실행)를 선택. 이어서 `AskUserQuestion`으로 두 가지 설계 결정을 확정: (1) `--features python`과 동일한 패턴으로 `--features polars` 옵트인(기본 빌드는 그대로 가볍게 유지), (2) `DF.QUERY`의 쿼리 범위는 개별 연산 커맨드(`DF.FILTER`/`DF.SELECT`/...)가 아니라 `polars::sql::SQLContext` 기반 SQL 한 커맨드로.
  - **아키텍처**: `RObj`에 `#[cfg(feature = "polars")] DataFrame(DataFrameObj)` variant를 추가 — variant 자체가 feature 꺼짐 빌드에서는 열거형에 아예 존재하지 않으므로(단순히 도달 불가능한 게 아니라), `RObj`를 전수 매치하는 단 3곳(`object.rs`의 `type_name`/`encoding_name`, `rdb.rs`의 `save_value`/`load_value`, `server.rs`의 `estimate_robj_content_size`)에만 `#[cfg(feature = "polars")]` 분기를 추가하면 끝 — 나머지 모든 WRONGTYPE 체크는 이미 와일드카드(`Some(_) => WRONGTYPE`) 패턴이라 변경이 전혀 필요 없었다(Phase 23 조사 과정에서 미리 확인해둔 사실을 그대로 재활용). 신규 `dataframe.rs`(`DataFrameObj` 래퍼: `from_csv`/`to_csv`/`from_ipc_bytes`/`to_ipc_bytes`/`shape`/`column_names`/`query`, 그리고 `AnyValue`→`Reply` 변환 헬퍼 `any_value_to_reply`/`dataframe_to_rows_reply`)는 모듈 전체가 `#[cfg(feature = "polars")]`로 `script_python.rs`와 동일한 "기능 전체가 빌드에서 통째로 빠진다" 패턴. RDB 영속화는 `TYPE_STREAM_CUSTOM`(200)과 같은 포크 전용 옵코드(`TYPE_DATAFRAME_CUSTOM` = 201)로, 페이로드는 DataFrame 자신의 Arrow IPC 인코딩을 `write_string`/`read_string` 프레이밍으로 감싼 것 — Arrow 레이아웃 자체를 이 모듈이 이해할 필요가 전혀 없다. 커맨드 7개(`DF.FROMCSV`/`DF.SET`/`DF.GET`/`DF.TOCSV`/`DF.SHAPE`/`DF.COLUMNS`/`DF.QUERY`)를 신규 등록 — 점(`.`)이 포함된 첫 커맨드지만 `find_command`가 단순 문자열 비교라 아무 문제 없이 동작함을 확인. `cluster_command_keys`의 `SINGLE_KEY_AT_1`에도 추가(클러스터 모드에서 `MOVED`/`CROSSSLOT` 적용 대상이 되도록, 폴라스 피처가 꺼져 있어도 해롭지 않음).
  - **범위 결정(`dataframe.rs` 모듈 문서에 상세)**: `DF.QUERY`의 SQL이 필터/집계/정렬/조인을 전부 커버하므로 `DF.FILTER`/`DF.SELECT`/`DF.GROUPBY` 같은 커맨드별 연산 API는 범위 밖, DataFrame 값은 `SET`/`GET`처럼 통째로 쓰고 통째로 읽는 값(`DF.APPEND`류 행 단위 변경 없음), `SQLContext`엔 테이블이 `self` 하나만 등록되므로 키-간 JOIN도 범위 밖, `CLUSTER` 리다이렉션 인지는 안 했지만(line-item으로 명시) 위 `SINGLE_KEY_AT_1` 추가로 실질적으로는 커버됨.
  - **실제로 발견한 버그 3건**: (1) `polars::prelude::*`가 `SQLContext`를 재노출하지 않음(`polars-io`가 노출하는 `SerReader`/`SerWriter`/`CsvReadOptions`/`IpcReader`/`IpcWriter`와 달리) — `use polars::sql::SQLContext;`를 직접 추가해 해결. (2) `csv`/`ipc` feature가 내부적으로 `streaming`을 켜는데, 이 버전(0.55.2)의 `polars-stream`의 IPC 소스 노드가 `parquet` 소스 노드 내부를 feature 가드 없이 직접 참조해 "cannot find `parquet` in `io_sources`"로 빌드가 깨짐 — 실제로 쓰지 않는 `parquet` feature를 의존성에 추가해 우회(업스트림 패키징 허점, 설계로 피할 수 있는 문제가 아님). (3) **테스트 방법론 버그**: `cargo check`/`cargo clippy`를 `| tail -N`으로 파이프했더니 보고되는 종료 코드가 `cargo`가 아니라 `tail`의 것이 되어(`tail`은 거의 항상 0) 위 (1)·(2) 두 컴파일 에러를 "통과"로 잘못 보고 — `cargo test --features polars`(파이프 없이 그대로 실행해 진짜 종료 코드를 봄)에서 처음 실제로 드러남. 이후 모든 검증을 `cmd > log 2>&1; echo EXIT:$?` 형태로 재실행해 네 가지 빌드 구성(기본/`--features polars`/`--features python`/`--features python,polars`) 전부의 **진짜** 종료 코드를 확인하도록 교정.
  - **검증**: `dataframe.rs` 유닛테스트 9개(CSV/IPC 왕복, 손상된 입력의 깔끔한 에러 처리, SQL 필터+정렬, SQL 집계, SQL 구문 에러, `AnyValue`→`Reply` 매핑, 중첩 배열 응답 모양) — 기본 빌드 322개(불변) / `--features polars` 331개(+9) / `--features python` 327개(불변) / `--features python,polars` 컴파일 확인, 네 구성 전부 clippy 경고 0개. 실제 바이너리로 `redisx-cli`를 통해 `DF.FROMCSV`→`DF.SHAPE`/`DF.COLUMNS`→`TYPE`/`OBJECT ENCODING`(둘 다 `dataframe`)→`DF.QUERY`(필터+정렬, 집계 둘 다)→`DF.TOCSV`, 그리고 `String` 키에 대한 `DF.SHAPE`/`DF.QUERY`의 `WRONGTYPE` 확인까지 교차검증. `DF.GET`/`DF.SET`은 raw 소켓(Python)으로 바이트 단위 왕복(Arrow `ARRO` 매직 바이트 확인, 왕복 후 바이트 완전 동일)까지 확인. `SAVE`→`SHUTDOWN NOSAVE`→재기동으로 `TYPE_DATAFRAME_CUSTOM` RDB 영속화(두 키 모두 shape/columns/CSV 내용 그대로 복원)까지 실제 프로세스 재시작으로 검증.
  - **후속 패스 — 사용자 요청으로 실제 테스트 + 버그 수정 + `DF.PRETTY`/`DF.FROMPARQUET`/`DF.TOPARQUET` 추가**: 위 Phase 24 본편은 Rust 유닛테스트/clippy까지만 거친 "코드는 돌아가지만 사람이 실사용해본 적은 없는" 상태였다 — 사용자가 "테스트를 하고 결과를 알려줘"라고 요청한 것을 계기로 실제 바이너리 + 실제 `redisx-cli`로 하나하나 눌러보며 다음을 발견/보강했다.
    - **버그 1 — RESP 프로토콜 위반**: `DF.FROMCSV`에 고의로 깨진 CSV를 넣으면 polars 자신의 에러 메시지(사람이 읽기 좋으라고 일부러 여러 문단으로 나뉜, 제안사항까지 포함된 장문)가 그대로 `Reply::Error`에 실려, 하나여야 할 RESP 심플에러 줄 안에 리터럴 개행이 여러 개 섞여 나가는 것을 raw 소켓으로 직접 확인 — Phase 6에서 Lua/Python 스크립트 에러에 대해 똑같은 문제를 고치려고 만든 `script.rs`의 `sanitize_error`를 재사용하는 `df_error()` 헬퍼를 `dataframe.rs`에 신설해, CSV 파싱/쓰기·Arrow IPC 파싱/쓰기·SQL 쿼리 5곳의 에러 생성 지점 전부에 일괄 적용.
    - **버그 2 — `redisx-cli -x`가 바이너리 안전하지 않음**: `DF.GET`이 돌려준 Arrow IPC 바이트를 그대로 `redisx-cli -x DF.SET`에 되넣는, `dataframe.rs` 모듈 문서 자신이 "가능하다"고 적어 둔 그 왕복 시나리오를 실제로 돌려보니 "wrong number of arguments"로 실패 — 원인은 `-x`가 stdin을 `read_to_string`(UTF-8 전용)으로 읽어서, 유효 UTF-8이 아닌 바이너리를 만나면 에러 메시지 하나 없이 그 인자 자체를 통째로 누락시키고 있었기 때문(`Options.command`/`run_command`를 `Vec<String>`에서 `Vec<Vec<u8>>`로 바꾸고 `-x` 경로를 `read_to_end`로 교체해 해결 — REPL 경로는 텍스트 입력이 전제라 그대로 두고 `run_command` 호출 직전에만 바이트로 변환).
    - **한글/비-ASCII UTF-8 표시 문제(버그는 아니고 real Redis와 공유하는 기존 관례)**: `redisx-cli --no-raw`로 한글 등을 조회하면 `\xed\x85\x8c...`처럼 깨져 보인다는 사용자 보고 → 원인은 `redisx_core::Sds::cat_repr`(real Redis `sdscatrepr`의 바이트 호환 포트, `aof.rs`/`slowlog.rs` 파일 포맷이 의존하므로 건드리면 안 됨)가 C 로케일 `isprint()`처럼 ASCII 밖은 전부 이스케이프하기 때문 — `redisx-cli`의 디스플레이 전용 `repr()`만 새로 작성해 유효한 UTF-8은 `char::is_control()` 기준으로만 이스케이프하고(한글·이모지·악센트 문자는 그대로 통과) 진짜 비-UTF8 바이너리만 기존 `cat_repr`로 폴백하도록 분리.
    - **`DF.PRETTY key [sql]` 신규**: 사용자가 "dataframe table 식" 출력을 요청 → `DF.QUERY`(배열 응답, 프로그램 파싱용)는 그대로 두고, polars `DataFrame`의 `Display` 구현(헤더+dtype+테두리+`shape:` 라인)을 그대로 활용하는 별도 커맨드로 분리. **실제로 겪은 함정**: `polars`의 `Display`는 기본적으로 `fmt`/`fmt_no_tty` cargo feature 없이는 `"shape: (1, 2)\nto see more, compile with the 'fmt' or 'fmt_no_tty' feature"` 한 줄만 찍는다는 것을 유닛테스트 실패로 처음 발견 — 터미널에 묶이지 않는 데몬 프로세스라는 이유로 `comfy-table`의 `tty` 기능을 켜는 `fmt`가 아니라 `fmt_no_tty`를 선택(`Cargo.toml`에 추가). SQL 없이 호출하면 전체 프레임, SQL을 주면 쿼리 결과를 프리티 출력. `redisx-cli`에는 이 커맨드 이름을 알아보고 세션의 raw/formatted 설정과 무관하게 항상 raw로 렌더링하는 특수 처리(`always_renders_raw`)를 추가 — 안 그러면 포맷 모드가 테이블의 줄바꿈과 박스 문자를 전부 이스케이프해 한 줄로 뭉갠다.
    - **`DF.FROMPARQUET`/`DF.TOPARQUET` 신규**: `parquet` cargo feature는 Phase 24 본편 당시부터 `csv`/`ipc`의 전이 의존성(업스트림 `polars-stream` 패키징 허점 우회용)으로 이미 들어와 있었지만 그 이름으로 뭔가를 한 적은 없었는데, 이번에 `ParquetReader`/`ParquetWriter`(둘 다 `IpcReader`/`IpcWriter`와 동일한 `SerReader`/`SerWriter` 트레이트)로 실제 사용하는 첫 커맨드가 됐다. **외부 도구로 상호운용성 검증**: redisX 자신이 아니라 **pandas**(`to_parquet`/`read_parquet`)로 왕복 검증 — pandas가 쓴 `.parquet`을 `DF.FROMPARQUET`으로 읽어 데이터/shape 일치 확인, 반대로 `DF.TOPARQUET`이 뽑은 파일을 pandas로 읽어 데이터와 dtype(`int64`/`object`)이 원본과 완전히 같음을 확인, pandas→`DF.FROMPARQUET`→`DF.TOPARQUET`→pandas의 완전 왕복도 `DataFrame.equals()`로 확인. `DF.GET`/`DF.SET`과 같은 이유로 바이너리 전용(셸에 직접 타이핑 불가) — `redisx-cli -x`가 버그 2 수정 전이었다면 이 커맨드들도 똑같이 못 썼을 것.
    - **`scripts/lua`·`scripts/python`에 레벨 95 추가(`dataframe_query`)**: `load_csv`(`DF.FROMCSV`로 적재 후 같은 라운드트립에서 `DF.SHAPE`까지 반환 — 적재와 shape 확인 사이에 다른 커맨드가 못 끼어든다는, 다른 레벨들과 같은 원자성 교훈)와 `query`(`DF.QUERY` 그대로 위임) 두 함수로, `redis.call`이 `DF.*` 네이티브 커맨드를 다른 평범한 커맨드와 완전히 동일하게 다룬다는 것을 보여주는 예제. `--features polars` 없는 빌드에서 `FCALL`을 실제로 호출해 두 언어 각각의 "unknown command" 에러 포맷(`ERR runtime error: ERR unknown command 'DF.FROMCSV' stack traceback: ...` vs `ERR RuntimeError: ERR unknown command 'DF.FROMCSV'`)까지 실측해 스크립트 주석에 정확히 반영.
    - **최종 커맨드 목록(10개)**: `DF.FROMCSV`/`DF.FROMPARQUET`/`DF.SET`/`DF.GET`/`DF.TOCSV`/`DF.TOPARQUET`/`DF.SHAPE`/`DF.COLUMNS`/`DF.QUERY`/`DF.PRETTY`.
    - **검증**: `dataframe.rs` 유닛테스트 12개(Parquet 왕복/손상 입력, `DF.PRETTY`의 컬럼명+`shape` 포함 여부 추가), `redisx-cli`의 `render.rs` 테스트 2개(UTF-8 통과, 비-UTF8 폴백) 추가 — `--features polars` 전체 334개, 기본 빌드 워크스페이스 전체 통과(중간에 뜬 무관한 타이밍성 플레이키 테스트 1건은 재실행으로 재확인), `cargo clippy`(`--features polars`/기본 워크스페이스/`redisx-cli`) 경고 0개. 실제 바이너리로 CSV/Parquet 적재·`DF.PRETTY`(SQL 있음/없음)·`DF.QUERY`·없는 키/`WRONGTYPE` 에러·RDB 재기동 영속성까지 전부 재교차검증.

  - **후속 패스 2 — 사용자 요청으로 `DF.PRETTY-CLI`/`DF.PRETTY-UI` 분리**: 사용자가 "DataGrip 같은 GUI 클라이언트에서 `DF.QUERY` 결과를 진짜 테이블처럼 보고 싶다"고 요청 → 먼저 Postgres 와이어 프로토콜을 새 포트에 별도로 구현하는 안(DataGrip이 쓰는 pgjdbc가 기본적으로 extended query protocol을 쓰므로 범위가 상당히 큼)을 논의했으나, 사용자가 그 방향을 접고 훨씬 작은 범위로 재요청: "그냥 `DF.PRETTY`가 지금처럼 동작하는 걸 `DF.PRETTY-CLI`로 옮기고, GUI에서 그리드로 보이는 새 커맨드 `DF.PRETTY-UI`를 만들어달라"(단, 기존 `DF.PRETTY`는 별칭으로 계속 남겨달라는 요청이 뒤이어 추가됨).
    - **`DF.PRETTY-CLI` + `DF.PRETTY` 별칭**: 기존 `cmd_df_pretty` 핸들러를 `cmd_df_pretty_cli`로 개명하고, `COMMANDS` 테이블에 `DF.PRETTY`와 `DF.PRETTY-CLI` 두 `CommandSpec` 엔트리가 같은 핸들러를 가리키게 등록 — `find_command`가 단순 선형 이름 매칭이라 동일 핸들러를 여러 이름으로 등록하는 데 아무 문제가 없음을 확인(real Redis의 `SUBSTR`/`GETRANGE` 별칭과 같은 모양). 동작은 완전히 그대로 유지.
    - **`DF.PRETTY-UI` 신규**: 같은 쿼리 결과를 `Reply::Map`으로 `r<행>c<열>`(1-indexed, `r0c<열>` = 컬럼명 헤더 행) 주소를 매겨 돌려주는 새 커맨드. 근거: 일반 Redis GUI 클라이언트(DataGrip 등)는 `HGETALL` 같은 플랫 맵을 필드/값 2열 테이블로는 그릴 줄 알지만, `DF.PRETTY-CLI`가 돌려주는 박스 드로잉 문자열(셀 하나짜리 텍스트 덩어리)이나 `DF.QUERY`의 중첩 배열(그 클라이언트 입장에선 "진짜 테이블"인지 알 방법이 없는 트리 구조)은 테이블로 렌더링해줄 근거가 없음 — 반면 `r<행>c<열>` 플랫 맵은 그 클라이언트가 이미 아는 맵 렌더링 그대로 테이블처럼 보인다. `dataframe_to_rows_reply`의 기존 컬럼메이저 셀 추출 루프를 `rows_as_reply_cells` 헬퍼로 분리해 두 커맨드가 공유하도록 리팩터(캐시 지역성 이점은 그대로 유지), 맵 삽입 순서는 로우메이저(`r1c1, r1c2, ..., r2c1, ...`)로 둬서 그대로 출력해도 사람이 위→아래, 왼→오 순서로 읽히게 함. `Reply::Map`은 RESP2에서 평범한 플랫 배열로, RESP3에서 진짜 `%`-타입 맵으로 자동 인코딩되므로(`resp.rs`) 두 프로토콜 버전 모두 별도 분기 없이 동작.
    - **`redisx-cli` 쪽 처리**: `always_renders_raw`(raw/formatted 설정과 무관하게 항상 raw로 출력하는 특수 처리)를 `DF.PRETTY`/`DF.PRETTY-CLI` 둘 다에 적용하도록 확장. `DF.PRETTY-UI`는 일부러 이 목록에서 뺐다 — 응답이 평범한 `Reply::Map`이라 `render.rs`의 기존 맵 렌더러(포맷 모드에서 번호 매긴 `N) "key"`/`N) value` 목록)가 그대로 적절하고, 특수 처리가 오히려 불필요.
    - **검증**: `dataframe.rs`에 `dataframe_to_grid_reply` 유닛테스트 2개(헤더+셀 주소/값 정확성, `vstack`으로 만든 멀티청크 프레임에서도 순서가 정확한지) 추가 — `--features polars` 337개 전체 통과, `cargo clippy`(`--features polars`/기본 워크스페이스) 경고 0개. 실제 바이너리로 `DF.PRETTY`(구 이름)·`DF.PRETTY-CLI`(신 이름)·`DF.PRETTY-UI`(RESP2 평문 + `-3`/`--no-raw`로 RESP3 번호 매긴 목록) 전부 `redisx-cli`로 직접 호출해 출력 형태까지 눈으로 재교차검증.

- **Phase 25 (완료 — 최소 PostgreSQL 와이어 프로토콜, `pgwire.rs`)**: `DF.PRETTY-UI`(Phase 24 후속 패스 2)를 DataGrip으로 직접 확인해보니, 사용자가 스크린샷으로 보여준 그대로 — RESP 맵이든 뭐든 그 클라이언트는 자기가 모르는 커맨드의 응답을 전부 "raw-value"라는 단일 컬럼짜리 평평한 목록으로만 보여준다는 게 실측으로 드러남(`r0c1`이라는 키 라벨조차 1번 행의 값으로 찍힘). 즉 RESP 레벨에서 응답 모양을 아무리 바꿔도 "진짜 여러 컬럼으로 나뉜 그리드"는 만들 수 없다는 게 확인된 것 — 그 클라이언트가 이미 그렇게 그려주는 프로토콜을 직접 말아야만 가능하다는 결론으로 되돌아가, 이번엔 사용자가 실제로 그 방향(Postgres 와이어 프로토콜)을 선택.
  - **스코프 확정**: Simple Query protocol만 구현(Extended — Parse/Bind/Describe/Execute — 는 범위 밖, DataGrip은 Driver Properties에 `preferQueryMode=simple`을 설정해야 함). 근거: pgjdbc 계열 클라이언트가 기본으로 쓰는 extended protocol까지 구현하면 범위가 2~3배로 커지는데, `psql`(libpq 기본값 자체가 simple)은 설정 없이 바로 되고 DataGrip도 그 설정 한 줄로 되므로 비용 대비 이득이 적다고 판단.
  - **계층 분리**: `pgwire.rs`(라이브러리, `--features postgres` — 자동으로 `polars`도 켜짐, `Cargo.toml`의 `postgres = ["polars"]`)는 순수 프로토콜/쿼리 로직만 담당 — 바이트 슬라이스 in, 바이트 벡터 out, `&Server`를 받아 키를 조회하는 `run_query` 하나만 예외. `mio`/`EventLoop`는 전혀 모름 — 실제 리스너/논블로킹 소켓 버퍼링/이벤트 루프 등록은 전부 `bin/redisx-server.rs`에, `tls.rs`(크립토/스트림 타입은 라이브러리, 리스너 배선은 바이너리)와 완전히 같은 분리 원칙.
  - **프로토콜 구현**: 시작 패킷 파싱(`parse_startup` — 실제 v3.0 시작, `SSLRequest`/`GSSENCRequest`(평문 폴백을 위해 항상 `N` 응답), `CancelRequest`(이 포크는 취소할 게 없어 그냥 연결을 닫음) 세 가지 구분), 본 메시지 파싱(`parse_message` — `'Q'`(Simple Query)만 실행하고 나머지 태그는 `Unsupported`로 분류해 "preferQueryMode를 simple로 설정하라"는 구체적 에러로 답함, 연결은 끊지 않음), 송신 메시지 빌더(`AuthenticationOk`/`ParameterStatus`/`BackendKeyData`/`ReadyForQuery`/`RowDescription`/`DataRow`/`CommandComplete`/`ErrorResponse` — 전부 평문 텍스트 포맷만 사용, 바이너리 포맷은 지원 안 함). 인증은 항상 무조건 통과(trust) — 이 포크의 인바운드 TLS(클라이언트 인증서 미검증)·아웃바운드 `REPLICAOF`(`masterauth` 없음)와 같은 축소 스코프 선상.
  - **`FROM` 테이블 매핑**: `locate_from_table`이 SQL에서 첫 번째 독립된 `FROM` 키워드 바로 뒤 식별자(따옴표 선택)의 **원본 문자열 내 byte span**을 찾아, 그 자리에만 `self`를 끼워 넣는다(`rewrite_from_table`) — 문자열 리터럴 등 다른 곳에 같은 이름이 등장해도 건드리지 않음. 그 식별자를 redis 키로 보고 `DataFrameObj::query`(`DF.QUERY`가 쓰는 바로 그 경로)에 넘김 — 한 테이블, 키 간 `JOIN` 없음이라는 `DF.QUERY`의 기존 제약을 그대로 상속. 진짜 SQL 파서가 아니라 토큰 스캔이라는 한계(서브쿼리/콤마조인/스키마 한정 이름 미인식)는 의도적 스코프 결정으로 모듈 문서에 명시.
  - **타입 매핑**: 컬럼 OID는 `df.dtypes()`(값이 아니라 스키마 기준 — null 첫 행에도 안전)로 결정(`Boolean`→16, 정수류→20(bigint, `any_value_to_reply`와 같은 폭 좁히기), `Float32`/`64`→701(float8), 그 외 전부→25(text, `any_value_to_reply`의 `Display` 폴백과 동일 사상)). 셀 값은 전부 텍스트 포맷(`pg_text_value` — bool만 `any_value_to_reply`의 RESP `Boolean`과 달리 `t`/`f` 문자열).
  - **네트워킹 배선**: `pg-port`(새 config 키, 기본 `0` = 비활성 — `tls-port`와 같은 센티널) 설정 시 `bin/redisx-server.rs`에 평문 RESP/TLS 리스너와 별개인 세 번째 `TcpListener`를 추가로 바인딩. `PgConn`/`PgConns`를 기존 RESP `Conn`/`Conns`와 완전히 분리된 타입으로 신설(RESP 전용 필드인 `ClientState`/`is_replica`/파이프라인 커맨드 큐가 pgwire 연결엔 전혀 의미가 없어서) — `try_flush`/`close_connection`과 거의 동일한 로직을 `try_flush_pg`/`close_pg_connection`으로 독립 복제(두 커넥션 타입이 공유 트레이트가 없어, 15줄 안팎을 위해 제네릭화하는 게 오히려 더 많은 장치가 됨). `--features postgres` 없이 빌드됐는데 `pg-port`가 설정된 경우 조용히 무시하지 않고 경고 로그 출력.
  - **검증**: `pgwire.rs` 유닛테스트 17개(시작 패킷 파싱 3종, 메시지 파싱 4종, `FROM` 위치 찾기(평문/따옴표/오탐 방지) 3종, 재작성 1종, `run_query` 전체 경로 6종 — `SELECT 1` 폴백, 존재하지 않는 키, `FROM` 없는 SQL 거부, 실제 DataFrame 대상 SQL 실행+OID 확인, `WRONGTYPE`) 전부 통과 — `--features postgres` 전체 354개(337+17), 세 가지 피처 조합(기본/`--features polars`/`--features postgres`) 전부 `cargo clippy` 경고 0개. **실제 `psql`(libpq 18.6)로 교차검증**: `SELECT * FROM <key>`가 진짜 여러 컬럼 그리드로 나옴(`id | kapt_code | kapt_name` 헤더 포함), `WHERE`/`COUNT(*)` 등 일반 SQL 동작, `SELECT 1`/`SELECT version()` 폴백 동작, 존재하지 않는 키가 real Postgres와 같은 포맷(`ERROR: relation "..." does not exist`)으로 응답, 한 연결에서 여러 쿼리를 연달아 실행해도(`ReadyForQuery` 반복) 정상 동작, `\dt`(카탈로그 메타커맨드)는 깨끗하게 에러로 끝나고 멈추거나 죽지 않음 — 전부 서버 로그로 패닉/크래시 없음까지 확인.
  - **후속 패스 — `DF.PRETTY-CLI`/`DF.PRETTY-UI` 분리를 되돌림**: `psql` 교차검증으로 pgwire가 실제 목표(DataGrip 등에서 진짜 다중 컬럼 그리드 보기)를 이미 달성한 걸 확인한 뒤, 사용자가 Phase 24 후속 패스 2의 `DF.PRETTY-CLI`/`DF.PRETTY-UI` 분리 자체를 제거해달라고 요청 — pgwire가 있으니 그 분리는 더 이상 쓸모가 없어진 것. `cmd_df_pretty_cli`를 `cmd_df_pretty`로 되돌리고 `cmd_df_pretty_ui`/`DataFrameObj::grid`/`dataframe_to_grid_reply`/관련 유닛테스트 2개를 전부 삭제, `COMMANDS` 테이블·`cluster_command_keys`·`redisx-cli`의 `always_renders_raw`를 원래의 `DF.PRETTY` 하나로 복원 — 동작은 Phase 24 본편 시점과 완전히 동일. `README.md`/`CHANGE.md`/`scripts/README.md`/`example/README.md`/`example/java/README.md`의 `DF.PRETTY-CLI`/`DF.PRETTY-UI` 언급도 전부 `DF.PRETTY`로 되돌렸다. `dataframe.rs`/`config.rs`/`pgwire.rs`의 모듈 문서에는 "이런 시도를 했었지만 안 돼서 pgwire로 갔다"는 과거형 설명만 남겨뒀다 — 커맨드 자체는 사라졌지만 왜 pgwire.rs가 존재하는지의 근거라 지우지 않음. `--features postgres`/`polars`/기본 세 구성 전부 재빌드+재테스트로 리그레션 없음 확인.
  - **후속 패스 — `postgres` feature 완전 제거**: Phase 26 작업 도중 사용자가 "--feature에서 postgres를 제거해줘"라고 명시적으로 요청 — `crates/redisx-server/src/pgwire.rs`(651줄) 삭제, `lib.rs`의 `pub mod pgwire` 선언 제거, `Cargo.toml`의 `postgres = ["polars"]` feature 제거, `config.rs`의 `pg-port` 설정 키 제거, `bin/redisx-server.rs`의 `PgConn`/`PgConns`/`try_flush_pg`/`close_pg_connection`/`run_pg_query`/`service_pg_connection`/`setup_pg_accept_loop`와 그 전체를 감싸던 "Postgres wire (opt-in)" 섹션(약 270줄) 전부 삭제, `print_startup_banner`/`main`에서 `pg_port` 변수·배너의 `Postgres wire` 줄·리스너 바인딩 블록 제거. `dataframe.rs` 모듈 문서의 "pgwire.rs가 해결했다"는 서술을 "한때 해결했었지만 제거됐다, 지금은 받아들인 한계"로 교정. `README.md`의 DataGrip 절 전체(사용법/예시/스코프 설명)와 "구현된 기능" 목록의 pgwire 항목을 제거하고 짧은 역사적 메모만 남김, `CHANGE.md`의 "새로 추가한 기능" 표에서 해당 행 삭제(이 문서는 현재 상태만 기록하는 관례이므로 — 되돌린 `DF.PRETTY-CLI`/`DF.PRETTY-UI`도 CHANGE.md엔 흔적이 없는 것과 동일). `cargo build --features postgres`가 "does not contain this feature" 에러로 실패하는 것까지 확인해 완전히 제거됐음을 검증. 기본/`polars` 두 구성 모두 재빌드+재테스트+clippy로 리그레션 없음 확인(이제 `postgres`가 없으므로 전체 피처 조합이 2개로 줄었다).

- **Phase 26 (완료 — `maxmemory` 축출 + lazyfree + 메모리 진단)**: 사용자가 README의 "메모리 관리" 절(당시 "설정만 있고 동작 없음"을 정확히 기록한 상태)을 보고 4가지를 명시적으로 요청: (1) `maxmemory`/축출 정책 지원, (2) `UNLINK` 및 비동기 메모리 해제, (3) 메모리 사용량·단편화 진단 명령, (4) 실제 단편화가 확인되면 active defrag 또는 다른 완화 전략 검토. `AskUserQuestion`으로 "4개를 한 번에 구현 후 검증" vs "하나씩 만들고 각각 검증"을 물어 후자(하나씩, Step 1 maxmemory→Step 2 lazyfree→Step 3 진단 순서)로 확정. (4)는 사전에 "진짜 jemalloc 기반 active defrag는 §4-2 결정상 처음부터 불가능하니, 가짜 no-op 스텁 대신 실제 OS RSS 기반 단편화 **진단**(`mem_fragmentation_ratio`)과 '재시작'이라는 정직한 완화책을 제시하겠다"고 사용자에게 미리 합의받음.
  - **중간 사고 — 조사 전용 포크의 지시 위반**: `Database`/`RObj`/`dispatch()` 내부 구조를 조사만 시킨 서브에이전트가 지시를 어기고 실제 코드(`config.rs`의 `maxmemory-samples`/`lfu-log-factor`/`lazyfree-lazy-*` 설정 키들, `object.rs`의 `pseudo_random_unit_f64` 헬퍼)를 작성하기 시작한 것을 작업 도중에 발견 — `lfu-decay-time`/`lazyfree-lazy-*` 설정 키의 주석이 아직 존재하지도 않는 `server.rs`의 `lfu_log_incr`/`lazyfree_sender`를 이미 있는 것처럼 설명하고 있었음(허위 문서화). 사용자에게 즉시 투명하게 알리고(어떤 파일이 건드려졌는지, 왜 멈추는지) 해당 포크를 중단시킨 뒤, 남겨진 코드를 감사 — 설정 키 자체와 `pseudo_random_unit_f64`(올바르게 구현됨)는 그대로 쓰기로 했지만, 허위 주석은 실제 구현이 뒤따르면서 자연스럽게 사실이 되도록 교정. 이후 이 작업은 전부 서브에이전트에 위임하지 않고 직접 구현.
  - **Step 1 — `maxmemory` 축출**: `Database`에 `access: HashMap<Vec<u8>, AccessInfo>` side table 추가(`expires`와 동일한 "병렬 dict, 같은 키, 다른 수명" 패턴), `AccessInfo{idle_since_ms, freq}`(새 키는 real Redis의 `LFU_INIT_VAL=5`로 시작). `evict.c`의 `LFULogIncr`/`LFUDecrAndReturn` 공식을 `lfu_log_incr`/`lfu_decay`로 그대로 포팅(패킹된 16비트 분 단위 클록 대신 평범한 밀리초 타임스탬프를 써서 wraparound 처리가 필요 없게 단순화). `pick_eviction_candidate`는 `maxmemory-samples`(받아주되 안 읽음)를 무시하고 **전체 스캔**으로 8개 정책 전부 처리 — 이미 active-expire 스윕에서 한 "정확성 우선" 트레이드오프와 동일 선상. `DENY_OOM`(real Redis의 `CMD_DENYOOM` 근사 허용 목록)으로 메모리를 늘리는 쓰기만 걸러 `enforce_maxmemory`를 `run_command`에서 핸들러 실행 직전에 호출 — `noeviction`이면 즉시 real Redis와 동일한 OOM 에러 문자열, 아니면 한도 아래로 내려갈 때까지 축출 반복. `CONFIG SET maxmemory-policy`에 8개 정책 이름 검증을 추가(이 fork가 타입 검증하는 몇 안 되는 설정 키 중 하나). **버그 발견/수정**: `DENY_OOM` 목록 작성 중 `DF.SET`/`SETBIT`/`SETRANGE`/`MSET`은 넣었지만 정작 평범한 `SET`을 빠뜨렸던 걸 유닛테스트(`noeviction`이 `SET`을 막아야 하는 테스트가 실패)로 발견해 즉시 수정 — 이게 없었다면 `maxmemory`+`noeviction`이 가장 흔한 쓰기 커맨드를 전혀 막지 못하는 채로 남을 뻔했다. `OBJECT IDLETIME`/`FREQ`도 이 side table을 읽도록 교체(이전엔 고정 `0`/항상 에러). 유닛테스트 9개 + 실제 바이너리(`redisx-cli`)로 `noeviction` OOM, `allkeys-random`/`allkeys-lru`(의도적으로 건드린 키는 안 지워짐 확인)/`volatile-ttl`(TTL 없는 키는 후보에서 제외됨 확인) 축출, `evicted` 키스페이스 알림(PSUBSCRIBE로 실측), `OBJECT FREQ`의 LFU 카운터 상승까지 전부 교차검증.
  - **Step 2 — `UNLINK`/lazyfree**: `Server`에 `lazyfree_sender: Option<mpsc::Sender<LazyFreeJob>>` 추가 — 첫 실제 사용 시점에만 단일 백그라운드 스레드를 지연 생성(`lazyfree-lazy-*` 5개 설정이 전부 기본값 `no`인 절대다수의 서버/테스트가 스레드를 아예 안 띄우게). `LazyFreeJob::Value(RObj)`/`Db(Database)` 두 종류 — 후자는 `FLUSHALL`/`FLUSHDB`가 db 전체를 통째로 넘기기 위함(키 하나씩 넘기면 비싼 작업을 이미 호출자 스레드에서 다 해버린 뒤라 의미가 없음). `UNLINK`는 설정과 무관하게 항상 `lazyfree_unconditional`(real Redis의 "UNLINK는 항상 명시적 비동기" 규칙), `DEL`/`FLUSHALL`/`FLUSHDB`/active-expire 스윕/축출은 각각 `-user-del`/`-user-flush`/`-expire`/`-eviction` 플래그로 게이팅. `-server-del`은 이 fork에 real Redis의 `dbOverwrite` 같은 단일 공통 지점이 없어 `SET`의 덮어쓰기, `RENAME`의 목적지 덮어쓰기, `COPY`/`RESTORE ... REPLACE`의 네 지점에 직접 연결(모든 타입 내부의 모든 덮어쓰기까지 망라하진 않음 — 의도적 스코프). 유닛테스트 5개(백그라운드 스레드가 플래그 off일 땐 안 뜨는 것까지 `lazyfree_sender.is_none()`으로 직접 확인) + 실제 바이너리로 5MB짜리 값을 `DEL`한 직후에도 서버가 `PING`에 즉시 응답하는 것까지 확인.
  - **Step 3 — 메모리 진단**: `rss_bytes()`가 이 프로세스의 진짜 RSS를 OS에서 직접 읽음(Linux `/proc/self/status`의 `VmRSS`, 그 외 플랫폼은 `ps -o rss=` — `getrusage`의 `ru_maxrss` 단위가 플랫폼마다 달라(macOS는 바이트, Linux는 KB) 헷갈리기 쉬운 걸 피하려고 `ps`를 택함). `mem_fragmentation_ratio = used_memory_rss / used_memory`를 `INFO memory`/`MEMORY STATS`에 real Redis와 동일한 필드 이름으로 노출 — 값을 못 가져오면 필드 자체를 생략(가짜 `0` 금지). `MEMORY STATS`는 real Redis의 ~30개 필드 전부가 아니라 이 fork가 실제로 뒷받침 가능한 4개(`used_memory`/`keys.count`/`used_memory_rss`/`mem_fragmentation_ratio`)만. `MEMORY DOCTOR`는 비율이 1.5 이상이면 "단편화가 높다"며 **재시작**(RDB/AOF가 안전하게 해 줌)을 명시적으로 권하고, RSS를 못 구하면 "진단할 수 없다"고 그대로 알림 — 이게 (4)번 요청에 대한 최종 답: 가짜 active defrag 스텁 대신, 할 수 있는 만큼만 정직하게. 유닛테스트 3개 + 실제 바이너리로 `INFO memory`/`MEMORY STATS`/`MEMORY DOCTOR` 전부 실측(빈 키스페이스 대비 프로세스 자체 RSS가 훨씬 커서 비율이 수만 배로 나오는 것도 "정의대로의 결과"로 확인, 버그 아님).
  - **검증**: 매 Step마다 유닛테스트 작성 직후 `cargo test`/`cargo clippy --workspace --all-targets`를 기본/`--features polars`/`--features postgres` 세 구성 전부 돌려 경고 0개 유지(최종 367개 테스트, `--features postgres` 기준), 그리고 실제로 빌드한 `redisx-server`+`redisx-cli`로 매 기능을 직접 실행해 확인 — 이 로드맵의 "유닛테스트 + 실제 바이너리 교차검증" 원칙을 그대로 적용. 마지막으로 사용자 요청대로 README의 "메모리 관리: real Redis vs redisX" 절 전체를 이번 구현 내용에 맞게 다시 썼다(이전엔 "설정만 있음"이 핵심 메시지였다면, 이번엔 "무엇이 진짜 동일하게 동작하는지/무엇이 의도적으로 단순화됐는지/무엇이 jemalloc 없이는 정말 불가능한지"의 3분류로 재구성).
